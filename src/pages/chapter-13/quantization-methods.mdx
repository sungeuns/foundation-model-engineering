# 13.2 Quantization Methods

Quantization represents weights, activations or KV state with fewer bits. Quality loss is not determined by bit width alone: calibration data, scale granularity, outliers, architecture and kernels matter. GPTQ and AWQ are PTQ algorithms; GGUF is a file format and runtime ecosystem.

---

## 1. GPTQ: Error Compensation via the Hessian

Introduced in late 2022, **GPTQ** (Accurate Post-Training Quantization for Generative Pre-trained Transformers) [[1]](#ref-1) revolutionized model compression by proving that 175-billion parameter models could be quantized to 3 or 4 bits on a single GPU in just a few hours, with negligible perplexity degradation.

### The Mathematics of Optimal Brain Surgeon
GPTQ does not simply quantize weights in isolation. It treats quantization as an optimization problem: *If I introduce an error by rounding Weight A, how can I adjust Weight B to cancel out that error?*

This concept originates from a classic neural network pruning technique called Optimal Brain Surgeon (OBS). GPTQ minimizes the squared error between the output of the full-precision layer and the quantized layer. To do this efficiently, it uses second-order information—specifically, the **Hessian matrix** (the matrix of second derivatives of the loss function).

For a given weight matrix $W$ and input $X$, the objective is to find a quantized matrix $\hat{W}$ that minimizes the squared error:
$$ \arg\min_{\hat{W}} ||WX - \hat{W}X||_2^2 $$

GPTQ processes the weight matrix row by row. When a weight $w_i$ is quantized to $\hat{w}_i$, an error $\delta = w_i - \hat{w}_i$ is generated. GPTQ updates all the *remaining* unquantized weights in that row to compensate for $\delta$, using the inverse of the Hessian matrix ($H^{-1}$) of the layer's activations.

### Engineering the GPTQ Loop

Below is a conceptual PyTorch implementation of the core GPTQ algorithm. In a production environment, this is heavily optimized using block-wise updates and Cholesky decomposition to avoid numerical instability when inverting massive matrices.

> **Educational single-layer example.** Uses CPU FP32 operations. Calibration-data selection, group-scale search, packing/kernels, distributed execution and model-level quality validation are omitted.

```python
import torch

@torch.no_grad()
def gptq_core_loop(W, H, bits=4, damping=0.01):
    """Educational FP32, per-output-row symmetric quantization; no packing."""
    if W.ndim != 2 or H.shape != (W.shape[1], W.shape[1]):
        raise ValueError("incompatible W/H shapes")
    if not 2 <= bits <= 8 or damping <= 0:
        raise ValueError("invalid quantization settings")
    work = W.detach().float().clone()
    hessian = H.detach().to(device=W.device, dtype=torch.float32).clone()
    ridge = damping * hessian.diag().mean().clamp_min(1e-6)
    hessian.diagonal().add_(ridge)
    # U.T @ U = inverse(H); not the unchanged raw inverse Hessian.
    chol = torch.linalg.cholesky(hessian)
    inverse = torch.cholesky_inverse(chol)
    U = torch.linalg.cholesky(inverse, upper=True)
    qmax = 2 ** (bits - 1) - 1
    scales = (work.abs().amax(dim=1) / qmax).clamp_min(1e-8)
    quantized = torch.zeros_like(work)
    for i in range(work.shape[1]):
        column = work[:, i]
        q = (column / scales).round().clamp(-qmax, qmax) * scales
        quantized[:, i] = q
        error = (column - q) / U[i, i]
        work[:, i+1:] -= error[:, None] * U[i, i+1:][None, :]
    return quantized

torch.manual_seed(7)
W = torch.randn(16, 32)
X = torch.randn(32, 64)  # calibration features x samples
H = 2 * X @ X.T / X.shape[1]
W_q = gptq_core_loop(W, H)
print("Calibration reconstruction MSE:", ((W - W_q) @ X).square().mean().item())
```

GPTQ is highly effective but requires a careful calibration phase to compute the Hessian. If the calibration data is skewed, the Hessian will prioritize compensating for the wrong features, leading to poor generalization.

## 2. AWQ: Activation-aware Weight Quantization

While GPTQ focuses on mathematical error compensation, **AWQ** (Activation-aware Weight Quantization) [[2]](#ref-2) takes a deeply empirical approach. The authors of AWQ made a critical observation: **Not all weights are equally important.**

Approximately 1% of the weights in an LLM are "salient." If you skip quantizing this 1%, the model retains nearly all of its full-precision accuracy. However, keeping 1% of weights in FP16 while the rest are INT4 creates a nightmare for hardware execution, requiring complex sparse-matrix multiplication kernels.

### The Salience Paradox
How do we identify these salient weights? Weight magnitude alone can miss activation-dependent sensitivity. A large weight might multiply against an activation that is always zero, rendering it useless. AWQ uses **activation statistics** to identify channels worth protecting in its evaluated quantization scheme. This does not prove that weight magnitude is useless for every compression method.

### The Scaling Trick
To protect these salient weights without using mixed-precision hardware kernels, AWQ uses a mathematical equivalence trick.

For a linear operation $Y = WX$, we can introduce a scaling vector $S$:
$$ Y = WX = (W \cdot S) (X \cdot S^{-1}) $$

AWQ calculates a per-channel scaling factor $S$ that scales *up* the weights corresponding to large activations. By scaling the salient weights up, they occupy a larger portion of the INT4 quantization bins, drastically reducing their relative quantization error. During inference, the activations are scaled *down* by $S^{-1}$ before the matrix multiplication, ensuring the final mathematical output remains identical.

> **Educational single-layer example.** Uses CPU FP32 operations. Calibration-data selection, group-scale search, packing/kernels, distributed execution and model-level quality validation are omitted.

```python
import torch

@torch.no_grad()
def awq_scale_weights(W, X, s_x=0.5):
    """Illustrate reciprocal channel scaling, not the AWQ scale search."""
    if W.ndim != 2 or X.ndim != 3 or W.shape[1] != X.shape[-1]:
        raise ValueError("incompatible calibration shape")
    if not 0 <= s_x <= 1:
        raise ValueError("s_x must be in [0,1]")
    magnitudes = X.float().abs().mean(dim=(0, 1)).clamp_min(1e-6)
    scales = magnitudes.pow(s_x)
    scales = scales / torch.sqrt(scales.max() * scales.min())
    return W.float() * scales[None, :], scales

W = torch.randn(16, 32)
X = torch.randn(2, 8, 32)
X[..., 0] = 0  # inactive channels must not cause division by zero
scaled_W, scales = awq_scale_weights(W, X)
assert torch.allclose(X @ W.T, (X / scales) @ scaled_W.T, atol=1e-5)
```

AWQ and GPTQ spend work on different calibration operations. Compare their implementations on the same model, calibration set, precision and hardware rather than assuming a universal runtime or quality ranking.

## 3. TurboQuant: rotation and residual correction

TurboQuant studies online vector quantization for mean-squared and inner-product error. It uses scalar quantization optimized for the rotated distribution and a QJL residual correction for inner-product estimation. A Hadamard rotation followed by uniform rounding is not the complete algorithm. [[3]](#ref-3)

Orthogonal rotation preserves inner products before quantization, not after introducing quantization error. Reported KV quality concerns the tested models and tasks. Concurrency depends on weights, KV, temporary buffers, metadata and kernel costs together; bit width alone cannot establish a doubling. Section 13.5 develops these distinctions.


## 4. GGUF and llama.cpp

GGUF is a container for tensors and metadata, not a single quantization algorithm. Block size, scales, offsets and code representation depend on tensor type; not every block stores a zero-point.

Separate a block format from a converter's mixed-tensor policy. A label such as `Q4_K_M` does not specify every layer's precision: type selection depends on converter version and architecture. Inspect actual tensor types and sizes, record converter commit/configuration and weight hashes, and validate quality and performance on the intended backend.


## 5. The Datatype War: FP8 vs INT4

Historically, PTQ relied entirely on Integer formats (INT8, INT4). However, the release of NVIDIA's Hopper architecture (H100) introduced native hardware support for **8-bit Floating Point (FP8)**, fundamentally altering the quantization landscape [[4]](#ref-4).

### Why Floating Point?
Integer quantization distributes its bins uniformly. The distance between 1 and 2 is the same as the distance between 100 and 101. LLM weights, however, follow a normal (Gaussian) distribution: most values are clustered near zero, with a few extreme outliers.

Floating-point formats use an exponent and a mantissa. This allows them to allocate high precision near zero (where the majority of weights live) while simultaneously maintaining a massive dynamic range to represent outliers without clipping them.

### E4M3 vs E5M2
The 2022 FP8 proposal describes two encodings; E5M2 follows IEEE 754 special-value conventions, which does not make this an “IEEE FP8 standard”:
1.  **E4M3 (4 Exponent bits, 3 Mantissa bits)**: Provides higher precision but lower dynamic range. It is the standard choice for quantizing **Weights** and **Activations** during forward-pass inference.
2.  **E5M2 (5 Exponent bits, 2 Mantissa bits)**: Sacrifices precision for a massive dynamic range. It is primarily used to store **Gradients** during training, which can fluctuate wildly.

FP8 range does not guarantee quality or memory savings. Validate scaling, accumulation precision, calibration, overflow and kernel support. Replacing a 16-bit tensor with 8-bit storage halves its raw payload; KV state, activations, buffers and metadata mean total VRAM need not halve. [[4]](#ref-4)

## 6. Formats and deployment budgets

GGUF/GPTQ/AWQ tags alone do not determine online/static batching performance or hardware suitability. Pin the checkpoint, group size, scale/zero-point format, packing order and runtime kernel. GGUF quant formats and per-tensor bit allocations differ; not every block uses the same metadata.

For $P$ weights at $b$ bits, ideal payload is $Pb/8$ bytes. An 8B model therefore has 16/8/4/2GB decimal payload at 16/8/4/2 bits, respectively. These are not minimum GPU capacities or quality guarantees. Add scales/indices, unquantized tensors, KV/recurrent state, activations, workspaces, allocator reserve and concurrency separately. Measure peak memory at the intended context and batch instead of applying a universal 20% multiplier.

## Quizzes

<details>
<summary>Quiz 1: Why does AWQ use the magnitude of the activations rather than the magnitude of the weights to identify "salient" weights?</summary>
*A weight with a large magnitude might be multiplied by an activation that is consistently near zero, rendering its actual contribution to the model's output negligible. The true importance (salience) of a weight is determined by how much data flows through it, which is measured by the magnitude of its corresponding activations.*
</details>

<details>
<summary>Quiz 2: In the GPTQ algorithm, how is the quantization error of a specific weight handled to prevent overall model degradation?</summary>
*When a weight is quantized, GPTQ calculates the exact numerical error introduced by the rounding. It then uses the inverse Hessian matrix of the activations to mathematically project that error onto the remaining unquantized weights in the same row, adjusting their values to compensate for the lost precision.*
</details>

<details>
<summary>Quiz 3: Does a Q4-family GGUF name mean every tensor is exactly four bits?</summary>
*No. Block metadata, format-specific super-block structure and per-tensor mixed precision affect storage. Inspect the format, conversion settings and runtime, then measure size and quality.*
</details>

<details>
<summary>Quiz 4: Is FP8 always better than INT8, and does it halve total VRAM?</summary>
*No. Results depend on value distributions, scaling, accumulation and kernels. Its raw payload is half a 16-bit tensor’s, but other state and metadata remain. Validate quality and measured peak memory on the same workload.*
</details>

<details>
<summary>Quiz 5: Mathematically formalize the quantization scale factor $S$ for symmetric per-tensor quantization versus dynamic per-token quantization for an activation matrix $X \in \mathbb{R}^{T \times D}$.</summary>
*For symmetric INT8 quantization (clipping boundaries [-128, 127]), the scale factor maps the absolute maximum activation to discrete boundaries. In per-tensor quantization, a single static scale factor is derived across the entire matrix: $S_{tensor} = \frac{\max_{t, d} |X_{t, d}|}{127}$. In dynamic per-token (per-row) quantization, a scaling vector $S \in \mathbb{R}^T$ is calculated independently for each token trajectory $t$: $S_{token}(t) = \frac{\max_d |X_{t, d}|}{127}$. Dynamic per-token quantization yields higher accuracy by localized scaling, ensuring that an outlier in one token sequence does not coarse-grain the grid precision of unrelated token sequence dimensions.*
</details>
