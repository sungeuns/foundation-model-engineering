# 5.2 Routing Algorithms

A router allocates a finite expert-compute budget. Think of it as a dispatcher: sending every job to one worker leaves other workers idle, but enforcing equal counts does not necessarily minimize end-to-end latency. Token affinity, expert capacity, communication, and causal consistency all matter.

## Token choice and load balancing

For token representation $x$ and router matrix $W$, standard token-choice routing selects $k$ experts from $p(x)=\operatorname{softmax}(xW)$. The selected weights may be renormalized before combining outputs. Collapse is a possible feedback loop—underused experts receive fewer updates—not an inevitable event after a fixed number of steps.

Noisy top-$k$ encourages exploration; a balancing penalty changes the training objective to $L=L_{LM}+\alpha L_{bal}$. The coefficient $\alpha$ trades modeling behavior against load. Evaluate validation loss and routing load jointly; experts do not necessarily specialize into clean human subjects such as mathematics and literature. [[1]](#ref-1)

## Expert choice: fixed expert capacity

Expert Choice reverses the selection axis: each expert selects a fixed number of tokens from a routing group. A capacity factor is a multiplier; the resulting integer capacity is a token count. Equal counts do not guarantee equal wall-clock work. A token can receive several expert outputs or none. With $y=x+\operatorname{MoE}(x)$, a token receiving no expert output still retains its residual representation. [[2]](#ref-2)

The important causal issue is competition across the routing group. If future tokens participate in the selection, changing a suffix can change how an earlier token is routed. A causal decoder therefore needs an explicitly causal grouping or routing design; merely retaining a KV cache does not solve this.

> **Educational selection example.** This CPU tensor example returns indices and weights only. It omits expert computation, residual/scatter combination, causal grouping, distributed dispatch, and training. Capacity is clamped to the available token count.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F

class ExpertChoiceRouting(nn.Module):
    def __init__(self, d_model, num_experts, capacity_factor):
        super().__init__()
        if num_experts < 1 or capacity_factor <= 0:
            raise ValueError("positive expert count and capacity factor required")
        self.num_experts = num_experts
        self.capacity_factor = capacity_factor

        # Router network
        self.router = nn.Linear(d_model, num_experts, bias=False)

    def forward(self, x):
        """
        x shape: [batch_size, seq_len, d_model]
        """
        batch_size, seq_len, d_model = x.shape
        num_tokens = batch_size * seq_len

        # Calculate fixed capacity per expert
        # E.g., if capacity_factor=2.0, an expert processes twice the average token share
        if num_tokens == 0:
            raise ValueError("empty routing group")
        expert_capacity = min(num_tokens, max(1, int(
            (num_tokens / self.num_experts) * self.capacity_factor)))

        x_flat = x.reshape(-1, d_model) # [num_tokens, d_model]

        # 1. Compute affinity logits: [num_tokens, num_experts]
        logits = self.router(x_flat)

        # 2. Convert to routing weights (Softmax over experts)
        weights = F.softmax(logits, dim=-1)

        # 3. TRANSPOSE: Let experts view all tokens -> [num_experts, num_tokens]
        weights_t = weights.t()

        # 4. Expert Choice: Each expert picks its top `expert_capacity` tokens
        # top_weights, top_indices shape: [num_experts, expert_capacity]
        top_weights, top_indices = torch.topk(weights_t, expert_capacity, dim=-1)

        # (In a full implementation, tokens would now be gathered using top_indices,
        # processed by their respective experts, and scattered back)

        return top_indices, top_weights

# Example usage
layer = ExpertChoiceRouting(d_model=1024, num_experts=8, capacity_factor=1.5)
dummy_input = torch.randn(2, 128, 1024) # 256 total tokens
indices, weights = layer(dummy_input)

# Each of the 8 experts exactly selected 48 tokens (256 / 8 * 1.5)
print(f"Indices shape: {indices.shape}") # Expected: [8, 48]
```

## Soft MoE: differentiable slots

Soft MoE forms weighted token mixtures for expert input slots and combines expert outputs back into token representations. Sparse computation is performed over these combined slots. The original study evaluates vision models; the central obstacle to naive causal reuse is mixing across future positions, not a claim that soft assignments necessarily eliminate all compute savings. [[3]](#ref-3)

## Dynamic selection bias in DeepSeek-V3

DeepSeek-V3 separates expert selection from output weighting. For token $t$, expert vector $e_i$, affinity $s_{i,t}$, and load-controller bias $b_i$, the simplified selection rule is:

$$
s_{i,t}=\sigma(x_t^\top e_i),\qquad
I_t=\operatorname{TopK}_i(s_{i,t}+b_i),\qquad
g_{i,t}=\frac{\mathbf{1}[i\in I_t]s_{i,t}}{\sum_{j\in I_t}s_{j,t}}.
$$

The bias shifts selection **after sigmoid**; selected output weights use the unbiased affinities. The load controller decreases overloaded experts' biases and increases underloaded ones. “Auxiliary-loss-free” names this load-control mechanism: the report still includes a small complementary sequence-wise balancing loss. Node limits, routed scaling and shared experts are omitted from this equation. [[4]](#ref-4)

This is one documented design, not proof that every model should remove auxiliary losses. A useful ablation keeps data, compute, expert count, and routing capacity fixed and measures both held-out quality and imbalance.
