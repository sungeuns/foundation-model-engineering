# 7.1 Data Parallelism (DP/DDP)

Two GPUs each see half of a training batch. Where should the two gradients meet, and which copy of the model should the optimizer update? PyTorch offers two ways to organize this step. Both keep a full copy of the model on each device and split the data across devices.

---

## 1. The Naive Approach: `DataParallel` (DP)

PyTorch’s `DataParallel` uses one process. On each forward pass it scatters the batch across devices, replicates the module, runs each replica on its slice, then gathers the outputs on the configured output device. During backward, autograd **sums** the replica gradients into the original module on the first device. The optimizer updates that module. Its updated parameters are the source for the replicas on the next forward pass. [[3]](#ref-3)

<a id="dp-ddp-gradient-trace"></a>

Take one scalar weight $w=1$ and two target values $y_0=0$ and $y_1=4$, one per device. Let the prediction be $w$ and each example’s loss be $\ell_i=(w-y_i)^2/2$. Its gradient is $w-y_i$, giving $+1$ and $-3$. Our training objective is the mean of the two example losses, so its gradient must be $-1$. Follow where the factor of two enters each implementation. [[3]](#ref-3) [[4]](#ref-4)

### Why DDP is preferred
PyTorch recommends DDP for multi-GPU training, including on one machine. Rebuilding replicas each forward adds work in DP. Gathering large outputs can also raise memory use on the output device. DDP keeps replicas between steps and can overlap gradient communication with backward computation. To compare the two on a workload, record peak memory per device, step time and time spent waiting for gradient synchronization. [[3]](#ref-3) [[4]](#ref-4)

## 2. The Standard: Distributed Data Parallel (DDP)

In the usual one-process-per-GPU configuration, each process has a rank, one model replica, and its own optimizer. The training code assigns inputs to ranks, for example with a `DistributedSampler`. DDP synchronizes initial module state by default and then synchronizes gradients in backward. Each optimizer applies the same update locally. Buffers such as BatchNorm statistics can also be broadcast depending on configuration. [[2]](#ref-2) [[4]](#ref-4)

<a id="ddp-valid-targets"></a>

### Two ranks, four valid tokens. Which gradient reaches the optimizer?

Give each rank three positions. Keep one target on rank 0 and all three on rank 1. At $w=1$, the four valid targets contribute gradients $+1,-3,-3,-3$. Averaging within each rank first gives $(1-3)/2=-1$. Giving each target one vote gives $(1-3-3-3)/4=-2$. A learning rate of 0.5 turns that choice into two different weights after a single SGD step.

These are CPU measurements with PyTorch 2.15, two Gloo processes and a Boolean loss mask. Every row starts at $w=1$. The last column computes the mean over the same valid positions together on one CPU. Each entry gives **(gradient, updated weight)**.

| Valid targets on ranks 0, 1 | DDP with rank means | DDP with global token mean | Unsharded reference |
| --- | --- | --- | --- |
| 1, 1 | (−1, 1.5) | (−1, 1.5) | (−1, 1.5) |
| 1, 3 | (−1, 1.5) | (−2, 2) | (−2, 2) |
| 0, 3 | (−1.5, 1.75) | (−3, 2.5) | (−3, 2.5) |
| 0, 0 | (no gradient, 1) | (no gradient, 1) | (no gradient, 1) |

The mean of an empty rank is undefined. In the third row, the rank-mean baseline gives the empty rank a zero contribution. DDP then averages zero with −3 and halves the update. For the global token mean, sum the valid counts across ranks first. On each rank, backpropagate its **sum** of valid losses times `world_size / total_valid`. Default DDP's gradient averaging then yields the four-token mean in row two and the three-token mean in row three. [[4]](#ref-4)

An empty rank still runs forward and backward if its peer has data. In the script, `losses[valid].sum()` remains connected to the model even when the mask selects nothing. When both masks are empty, the shared count is zero and both ranks skip the forward pass and optimizer step. <a href={gradientCheck} download="verify-dp-ddp-gradients.py">Download the two-rank check</a> and run `python verify-dp-ddp-gradients.py` to reproduce all four rows.

### Did every validation example get one vote?

Five examples have permanent IDs 0 through 4. Only the prediction for ID 0 is wrong. With shuffling off, PyTorch’s default `DistributedSampler` assigns `[0, 2, 4]` to rank 0 and `[1, 3, 0]` to rank 1. Both ranks process three examples. Summing correct predictions and visits across them gives **4/6**, although the five distinct examples scored **4/5**. The extra visit pads the shorter shard. [[5]](#ref-5)

The sampler’s `drop_last=True` drops ID 4 in this example. Leaving the sampler alone and setting `drop_last=True` on a loader with local batch size two also omits ID 4, this time when each rank drops its last partial batch. Either way, four observed IDs are too few to score this five-example set. [Run the CPU sampler audit and inspect every delivered batch](../../articles/ddp-sampler-audit/).

### The Mathematics of Ring All-Reduce
An all-reduce specifies the result that each rank receives. The backend chooses how to move the data. Ring, tree and hierarchical implementations are possible. [[2]](#ref-2)

Consider $N$ ranks with $M$ bytes of gradients per rank. In a centralized reduction, a designated rank receives $M(N-1)$ bytes from peers. In the ring algorithm, each rank sends and receives only part of the gradient at each step. [[1]](#ref-1)

In Ring All-Reduce, the GPUs are logically arranged in a circle. The algorithm operates in two phases:
1. **Reduce-Scatter:** The gradient tensor is chunked into $N$ blocks. Each GPU sends one block to its right neighbor and receives a different block from its left neighbor, continuously accumulating the values. After $N-1$ steps, every GPU holds the fully aggregated sum for exactly *one* of the $N$ blocks.
2. **All-Gather:** The fully aggregated blocks are circulated around the ring again. After another $N-1$ steps, every GPU has the complete, aggregated gradient tensor.

Each rank sends the following number of bytes and receives the same amount.
$$ \text{Volume} = 2 \times \frac{N - 1}{N} \times M $$

Bytes approach $2M$ as $N$ grows, but latency is not independent of rank count. With startup cost $\alpha$ per phase step and effective bandwidth $B$,

$$ T_{ring}\approx 2(N-1)\alpha + \frac{2(N-1)M}{NB}. $$

Topology, congestion and stragglers add costs; large-scale efficiency still requires measurement.

## 3. Engineering the Overlap: Gradient Bucketing

Waiting until the final parameter gradient is ready leaves all communication on the critical path. DDP groups parameter gradients into buckets. Once a bucket is ready and its turn arrives in the reduction order, its collective can overlap computation of later gradients. Small buckets can start earlier but require more collective launches. Large buckets amortize launch overhead but take longer to fill. [[2]](#ref-2) [[4]](#ref-4)

> **CPU teaching example.** The inputs are 1,024 generated sequences of 32 integer IDs. The target at each position is the input ID plus one, modulo 256. The model has an embedding and two linear layers. Every position counts towards cross-entropy. The example omits checkpointing, variable-length masks and recovery from a failed rank. The optional CUDA/NCCL path has not been run here.

Save the linked file and run `torchrun --standalone --nproc-per-node=2 ddp_token_training.py` with PyTorch 2.15. Each CPU rank receives eight sequences per full batch. In this run 1,024 divides evenly across the two ranks, so the epoch total is $1{,}024 \times 32 = 32{,}768$ token visits. The script sums both loss and token visits across ranks before the global rank 0 prints their ratio. A different dataset size can add visits through sampler padding.

In ordinary DDP, the required gradient synchronization completes with backward, so each local optimizer updates from the synchronized gradients. `optimizer.step()` is not itself a distributed barrier. A slow rank can delay peers at collectives; accumulation with `no_sync()` requires synchronization on the final backward.

## Summary

DDP retains model replicas and overlaps data-parallel computation with gradient communication. Benefits depend on the compute-to-communication ratio and stragglers. Bucketing can reduce exposed communication; it guarantees neither linear scaling nor complete latency hiding.

In ordinary, unsharded DDP, each GPU holds model weights, gradients and its local optimizer state. Adding GPUs leaves this per-replica requirement in place.

One illustrative mixed-precision Adam budget uses 2 bytes for BF16 weights, 2 for BF16 gradients, 4 for FP32 master weights and 8 for two FP32 moments: 16 bytes per parameter. Implementations with FP32 gradients differ. Add sequence- and batch-dependent activations, temporary buffers, collectives, checkpoint and evaluation overhead; there is no universal parameter cutoff for an 80GB device.

## Before adapting this skeleton to training

Pin the input manifest, tokenizer and model/config hashes; compare averaged gradients against a single-device reference on the same data. Batch 8, AdamW learning rate $10^{-4}$ and three epochs above are synthetic demonstration settings. A real run must specify effective global token batch, precision, accumulation and loss masks.

Record token-normalized train/validation loss and domain slices, nonfinite/overflow counts, gradient/activation norms, throughput/MFU, data wait, collective time and stragglers, and reconstructable batch IDs. Abort coherently across ranks on nonfinite loss or collective failure and restore the last validated checkpoint. Save model, optimizer, scheduler and precision state, step/tokens, RNG, sampler, exact data cursor and hashes. Release only after continuation-equivalence checks, isolated offline quality/safety/performance evaluation and rehearsal of switching back to the last known-good bundle.

## Quizzes

<details>
<summary>Quiz 1: The two example gradients are +1 and −3. Why do DP and default DDP both produce −1?</summary>
*In DP, the global mean loss scales the contributions to +0.5 and −1.5 before they are summed. In default DDP, each rank has one example, and the reducer averages +1 and −3.*

</details>

<details>
<summary>Quiz 2: How do ring bytes and latency differ at 10 and 1,000 ranks?</summary>
*Transmitted bytes rise from $1.8M$ to $1.998M$, about 11%. Startup cost rises from $18\alpha$ to $1998\alpha$, so similar byte counts do not imply similar latency.*
</details>

<details>
<summary>Quiz 3: What is the primary purpose of "Gradient Bucketing" in DDP?</summary>
*A ready bucket can begin synchronizing while backward computes later gradients. Any communication still running after compute finishes adds to step time.*
</details>

<details>
<summary>Quiz 4: If you have a 100-billion parameter model and a cluster of 1,024 GPUs (each with 80GB VRAM), can you train it using standard DDP? Why or why not?</summary>
*No, you cannot. Standard DDP requires a full replica of the model weights, gradients, and optimizer states to reside in the VRAM of every single GPU. A 100B parameter model in mixed precision requires roughly 1.6 Terabytes of VRAM for the weights, gradients and Adam state under the 16-byte budget above, which vastly exceeds the 80GB limit of a single GPU. This necessitates advanced techniques like ZeRO or Tensor Parallelism.*
</details>

<details>
<summary>Quiz 5: Two ranks report four correct predictions in six visits. What would you need to recover accuracy on five examples?</summary>
*Match each visit to a stable example ID and check all five expected IDs are present. Repeated visits must agree on label and prediction in this fixed-output experiment. Counting each ID once gives 4/5. If an ID is missing, its prediction is still needed.*
</details>
