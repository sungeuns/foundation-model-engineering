# 12.2 PagedAttention (vLLM)

The previous section counted how much KV state a request needs. This section asks where that growing state lives. Even when the payload fits in aggregate, a serving engine can waste capacity by reserving space that requests never use or by leaving gaps that its allocator cannot reuse.

The PagedAttention paper studied these problems in the serving systems it evaluated in 2023 [[1]](#ref-1). A contiguous cache that reserves each request's maximum length is easy to address, but the final output length is unknown at admission. Reserving the maximum is one design choice, not a requirement of every inference backend.

PagedAttention borrows the separation between logical and physical memory from operating-system paging. A request sees its tokens in sequence order; a block table lets the attention kernel find their KV rows in non-contiguous storage. The gain comes from allocating and reusing blocks as requests grow and finish.

---

## 1. Count Reserved Space and Unusable Gaps

A contiguous allocation strategy can lose usable capacity in two ways:

1. **Unused reservation inside a request:** suppose a request reserves 2,048 token slots, receives a 512-token prompt, and generates 20 tokens. It uses 532 slots and leaves **1,516 slots unused**. Count the prompt as well as the output. Over-reservation for possible future tokens is distinct from padding waste in an allocator's final block.
2. **External fragmentation:** after requests finish, a contiguous allocator may have several free regions whose total size is sufficient but whose largest individual region cannot hold a new request. Whether this happens depends on the allocator and its compaction strategy.

The original vLLM release reports that 60%–80% of KV-cache memory was wasted in the existing systems it analyzed [[2]](#ref-2). That historical observation motivates the design; it is not a measured waste rate for every current engine or workload.

---

## 2. The OS Inspiration: Paging and Block Tables

In modern Operating Systems, physical RAM is not allocated to applications in large, contiguous chunks. Instead, memory is divided into fixed-size "pages." The application sees a contiguous *logical* memory space, but the OS maps this to non-contiguous *physical* pages using a Page Table.

PagedAttention applies this exact paradigm to the KV cache:
-   **Logical Blocks:** The sequence of tokens in a user's request is divided into logical blocks (e.g., 16 tokens per block).
-   **Physical Blocks:** The GPU VRAM is pre-divided into a massive pool of fixed-size physical blocks.
-   **Block Table:** A mapping table tracks which physical block corresponds to which logical block for a given request.

When a request begins, the engine only allocates enough physical blocks to hold the initial prompt. As the model generates new tokens autoregressively, the system allocates new physical blocks *on demand*.

Within the fixed-size KV block pool, any free block is reusable, avoiding external fragmentation there. This does not describe all GPU allocations. Internal waste in final blocks depends on block size and the request-length distribution.

## 3. Engineering PagedAttention (PyTorch Simulation)

In a production environment, PagedAttention is implemented as a highly optimized, fused custom CUDA kernel. The kernel reads the Block Table directly and fetches the non-contiguous Key and Value tensors on the fly during the matrix multiplication.

The following educational simulation reconstructs contiguous keys and values from a block table so the address mapping is visible.

> **Deliberately simplified implementation.** This CUDA-only example is not a production allocator and has not been GPU-smoke-tested for this revision. It omits KV writers, ownership and double-free checks, reference counting, concurrent requests, copy-on-write, and cache recovery. It copies blocks into contiguous tensors; a real paged kernel avoids that reconstruction. The float16 pool and query must share device and dtype.

```python
import torch
import torch.nn.functional as F

class KVCacheMemoryPool:
    def __init__(self, num_blocks, block_size, num_heads, head_dim, dtype=torch.float16):
        self.num_blocks = num_blocks
        self.block_size = block_size

        # Physical VRAM Pool: [num_blocks, 2 (K&V), num_heads, block_size, head_dim]
        self.physical_memory = torch.zeros(
            (num_blocks, 2, num_heads, block_size, head_dim),
            dtype=dtype,
            device='cuda'
        )
        self.free_blocks = list(range(num_blocks)[::-1]) # Stack of free block indices

    def allocate_block(self):
        if not self.free_blocks:
            raise RuntimeError("Out of Memory: No free KV blocks available.")
        return self.free_blocks.pop()

    def free_block(self, block_idx):
        self.free_blocks.append(block_idx)

def paged_attention_simulated(query, physical_pool, block_table, context_len):
    """
    Simulates the PagedAttention kernel logic in pure PyTorch.
    query: [1, num_heads, 1, head_dim] (The current token's query)
    physical_pool: The KVCacheMemoryPool object
    block_table: List of physical block indices for this specific sequence
    context_len: Total number of valid tokens in the sequence
    """
    num_heads = query.size(1)
    head_dim = query.size(3)
    block_size = physical_pool.block_size

    # 1. Reconstruct the contiguous K and V tensors from the non-contiguous physical blocks
    # Note: In the actual CUDA kernel, this explicit reconstruction is bypassed,
    # and the dot product is computed directly block-by-block to save memory bandwidth.
    keys = []
    values = []

    for block_idx in block_table:
        # Fetch physical block: [num_heads, block_size, head_dim]
        k_block = physical_pool.physical_memory[block_idx, 0]
        v_block = physical_pool.physical_memory[block_idx, 1]
        keys.append(k_block)
        values.append(v_block)

    # Concatenate blocks along the sequence dimension
    # Shape: [num_heads, total_allocated_len, head_dim]
    contiguous_k = torch.cat(keys, dim=1)
    contiguous_v = torch.cat(values, dim=1)

    # 2. Truncate the padded tokens in the final block using context_len
    contiguous_k = contiguous_k[:, :context_len, :]
    contiguous_v = contiguous_v[:, :context_len, :]

    # 3. Add batch dimension for PyTorch compatibility
    contiguous_k = contiguous_k.unsqueeze(0)
    contiguous_v = contiguous_v.unsqueeze(0)

    # 4. Compute standard scaled dot-product attention
    # FlashAttention can be applied here in a real scenario
    attn_output = F.scaled_dot_product_attention(query, contiguous_k, contiguous_v)

    return attn_output
```

*The original implementation reads physical blocks through the block table and combines partial attention results without constructing the full contiguous KV tensors shown here [[1]](#ref-1). This removes the simulation's reconstruction buffers; it does not make cache storage or kernel workspace free.*

## 4. Advanced Memory Management: Copy-on-Write (CoW)

Separating logical blocks from physical storage also lets multiple requests reference the same immutable prefix blocks.

Consider **Parallel Sampling** or **Beam Search**, where a single prompt is passed to the model, and the model generates multiple different candidate responses simultaneously. An implementation that copies the full cache for each candidate duplicates their shared prompt; reference-counted blocks can avoid those copies.

With PagedAttention, vLLM implements **Copy-on-Write (CoW)**:
1.  All candidate sequences share the exact same logical-to-physical block mapping for the prompt. The physical blocks simply maintain a *reference count*.
2.  As the sequences begin generating new tokens, they share the physical blocks until a sequence diverges.
3.  When a sequence needs to write a new token to a shared block, the system detects the reference count is $>1$, allocates a *new* physical block, copies the shared data, and updates that specific sequence's Block Table.

The 2023 vLLM release reports up to **55%** lower memory use from sharing in its parallel-sampling and beam-search experiments [[2]](#ref-2). The gain depends on how much prefix remains shared, the number of candidates, and block occupancy.

## 5. Reading a case study: benchmark throughput versus deployment cost

The 2023 vLLM release reports up to 24× HF and 3.5× TGI throughput in tests using ShareGPT input/output lengths, LLaMA-7B on A10G and LLaMA-13B on A100 40GB. These are configuration-specific laboratory results. Separately, it reports a 50% reduction in GPUs used by the LMSYS deployment. That does not establish a 50% reduction in all operating costs or unchanged TTFT for every request. [[2]](#ref-2)

For adoption, match model, lengths, concurrency, precision and completion count, then compare throughput, TTFT, inter-token latency, failures and total cost together.


## 6. Summary and Open Questions

Paged allocation makes free blocks reusable within the KV pool and supports prefix sharing. It still leaves tail-block waste, metadata, kernel workspaces, and finite cache capacity. Evaluate those costs under the actual request-length distribution instead of treating paging as a promise that every allocation or latency problem disappears.

However, as we efficiently pack more requests into a batch, we encounter a new problem: **Scheduling**. If Request A generates 10 tokens and Request B generates 1,000 tokens, how do we efficiently swap requests in and out of the GPU without stalling the entire batch? This leads us directly to the concept of **Continuous Batching**, which we will explore in the next section.

## Quizzes

<details>
<summary>Quiz 1: How does PagedAttention specifically resolve the issue of *External Fragmentation* in the KV Cache?</summary>
*External fragmentation occurs when free memory is split into small, non-contiguous chunks that cannot accommodate a large contiguous allocation. Because PagedAttention allocates memory in fixed-size, non-contiguous physical blocks and maps them logically via a Block Table, any free physical block can be utilized by any request, regardless of where it resides in VRAM. This avoids external fragmentation inside the fixed-size KV block pool; it does not cover unrelated GPU allocations.*
</details>

<details>
<summary>Quiz 2: How much tail waste remains with block size B?</summary>
*Fewer than B token slots per sequence can be unused. With B=16 and length 3, thirteen slots are empty, so fractional overhead can be large. Aggregate overhead depends on length distribution and block size.*
</details>

<details>
<summary>Quiz 3: Why is the Copy-on-Write (CoW) mechanism particularly advantageous for Beam Search decoding?</summary>
*In Beam Search, multiple candidate sequences share the exact same initial prompt and often share early generated tokens before diverging. CoW allows all these sequences to map to the same physical memory blocks for the shared context. A write to a shared partial block requires a private copy; a write past a full block requires a new block. This can save memory compared with copying the entire history for every candidate.*
</details>

<details>
<summary>Quiz 4: Does PagedAttention guarantee bitwise-identical logits?</summary>
*It computes the same attention in exact arithmetic with a different storage layout. Kernel and operation-order changes can alter finite-precision results. Verify numerical tolerances and generation quality rather than assuming bitwise equality.*
</details>

<details>
<summary>Quiz 5: Formulate the mathematical internal fragmentation overhead of PagedAttention. Let the block size be $B$ tokens, sequence length of request $i$ be $S_i$, and the memory footprint per token be $M$ bytes. Derive the exact fragmented memory formula for a batch of $N$ requests.</summary>
*In PagedAttention, memory is allocated in fixed-size blocks of $B$ tokens. Internal fragmentation occurs only in the last allocated block of a sequence if it is not completely filled. The number of wasted token slots for request $i$ is $(B - (S_i \pmod B)) \pmod B$. Therefore, the exact fragmented memory footprint in bytes for request $i$ is: $W_i = M \times ((B - (S_i \pmod B)) \pmod B)$. For a batch of $N$ requests, the total internal fragmentation overhead is $W_{total} = \sum_{i=1}^N W_i$. For independent allocations with no shared or pre-reserved blocks, and assuming the residues $S_i \pmod B$ are uniform over $0,\ldots,B-1$, the average wasted tokens per request is $(B-1)/2$. Thus, the average total overhead for $N$ requests is approximately $N \times M \times \frac{B-1}{2}$ bytes.*
</details>
