# 5.1 희소 모델과 밀집 모델

DeepSeek-V3를 올리려는 엔지니어가 가중치용 메모리로 74 GB를 잡았습니다. 기술 보고서에 토큰당 활성 파라미터가 370억 개라고 쓰여 있고, 파라미터 하나에 2바이트를 잡았으니 곱셈은 맞습니다. 그런데 같은 정밀도로 주 모델의 가중치만 담아도 왜 약 **1.34 TB** 가 필요할까요? 기술 보고서에 나온 주 모델의 전체 파라미터 수는 6,710억 개입니다. 다음 토큰은 지금과 다른 가중치를 쓸 수 있습니다 [[3]](#ref-3).

## 토큰 하나가 층을 지나는 과정

“We sat on the river bank”에서 마지막 `bank`는 강둑이고, “For a loan, I visited the bank”에서는 은행입니다. 인과적 디코더가 `bank` 위치의 경로를 고를 때 앞에 나온 단어들은 이미 읽은 상태입니다. 앞선 층을 지나면서 같은 단어도 두 문맥에서 서로 다른 은닉 벡터로 표현될 수 있습니다. 밀집 피드포워드 신경망(FFN)은 두 벡터에 같은 행렬을 적용해 서로 다른 출력을 냅니다. 희소 **전문가 혼합(MoE)** 에서는 이 벡터가 어느 FFN을 실행할지 결정하는 데도 쓰입니다. 두 경우 모두 공통 어텐션 층은 그대로 실행합니다.

여기서 **전문가** 는 번호가 붙은 학습 가능한 신경망입니다. 설계자가 미리 ‘금융 담당’ 같은 주제를 지정할 필요는 없습니다. Shazeer 등의 연구팀은 희소 트랜스포머가 널리 쓰이기 전에 순환 언어 모델에 이런 조건부 연산을 적용했습니다 [[1]](#ref-1). Mixtral 8x7B에서는 각 층의 라우터가 토큰마다 전문가 FFN 여덟 개 중 두 개를 고릅니다 [[2]](#ref-2). 토큰마다 선택이 다르면 배치 전체에서는 여덟 개를 모두 쓸 수도 있습니다.

## Top-2 라우팅을 손으로 계산하기

토큰 하나의 은닉 벡터를 $x$, 라우터가 계산한 로짓을 $z=xW_g$, 로짓이 가장 큰 $k$개 전문가의 번호 집합을 $S$라고 하겠습니다. 여기서 사용하는 Mixtral 방식은 선택된 전문가끼리 가중치를 나눕니다. 전문가 $i$의 가중치가 $w_i$이고 출력이 $E_i(x)$일 때, 각 출력 벡터에 가중치를 곱하고 같은 좌표끼리 더합니다 [[2]](#ref-2).

$$
w_i=\begin{cases}
\frac{\exp(z_i)}{\sum_{j\in S}\exp(z_j)} & i\in S,\\
0 & i\notin S,
\end{cases}
\qquad y=\sum_{i\in S}w_iE_i(x).
$$

강둑 예문에서 로짓이 `[3, 2, 0, −1]`이라고 합시다. $k=2$이면 0번과 1번 전문가가 각각 약 0.731과 0.269의 가중치를 받습니다. 두 출력 벡터의 첫 좌표가 2와 −2라면 합친 좌표는 약 **0.924** 입니다. 아래에서 은행 예문으로 바꿔 보세요. 라우터 선택이 결과에 미치는 영향을 볼 수 있도록 로짓만 바꾸고 전문가 출력의 예시 좌표 네 개는 고정했습니다.

## 가중치 저장에 필요한 메모리 계산하기

모든 토큰이 쓰는 공통 가중치가 2억 개이고, 가중치 1억 개짜리 전문가가 여덟 개 있다고 합시다. 같은 모델이라도 무엇을 세느냐에 따라 답이 달라집니다.

| 알고 싶은 값 | 계산 | 읽는 법 |
| --- | --- | --- |
| 모델의 전체 가중치 수 | 2억 + 8 × 1억 = **10억** | 가중치 하나에 2바이트면 전체를 담는 데 **2 GB** 가 듭니다. |
| Top-2 토큰 하나가 쓰는 가중치 수 | 2억 + 2 × 1억 = **4억** | 이 경로에 있는 밀집 행렬 연산이 토큰 처리에 필요한 계산량의 상당 부분을 차지합니다. |
| 두 토큰이 겹치지 않는 전문가 쌍을 골랐을 때 쓰는 서로 다른 가중치 수 | 2억 + 4 × 1억 = **6억** | 공통 가중치는 두 번 계산에 쓰여도 메모리에서는 한 번만 셉니다. |

표의 GB는 십진 단위이며 가중치만 셉니다. KV 캐시, 활성값, 통신 버퍼, 메모리 할당 여유분, 양자화에 필요한 메타데이터는 별도로 잡으세요. 앞에서 계산한 1.34 TB도 가중치마다 일률적으로 2바이트를 잡은 값입니다. 배포된 체크포인트에는 개발팀이 별도로 집계한 다중 토큰 예측 모듈의 파라미터 140억 개도 들어 있습니다. 실제 파일 크기는 저장 정밀도에 따라 달라집니다 [[6]](#ref-6). 전문가는 여러 장치에 나눠 올릴 수 있고, 호스트 메모리에 뒀다가 불러올 수도 있습니다. Eliseev와 Mazur의 Mixtral 실험에서 보듯 오프로딩은 장치 메모리를 아끼는 대신 전송 시간이 듭니다 [[4]](#ref-4).

행렬과 벡터를 곱할 때 가중치 하나에 곱셈과 덧셈이 한 번씩 든다고 보면 약 2 FLOP입니다. 실제 지연 시간을 알려면 같은 행렬을 몇 토큰이 재사용하는지, 전문가가 어느 장치에 있는지, 토큰을 그곳까지 보내는 데 얼마나 걸리는지도 알아야 합니다. 2026년 Alfarizy 등의 프리프린트는 M2 Pro와 Jetson Orin Nano에서 `llama.cpp`로 OLMoE와 밀집 모델들을 비교했습니다. 두 장치 모두에서 밀집 모델인 Llama-3.2-1B의 디코딩이 OLMoE보다 빨랐고, Jetson에서 차이가 더 컸습니다. 이 결과는 해당 MoE 모델과 두 장치에서 얻은 측정값입니다. 실제 장비에서는 서비스할 문맥 길이와 동시 요청 수를 정한 뒤 프롬프트 처리와 디코딩을 나눠 측정하세요 [[5]](#ref-5).

## PyTorch에서 선택된 행만 전문가에게 보내기

**CPU 순전파 예제입니다.** FP32 토큰 두 개, 주어진 로짓, 선형 전문가 네 개로 행의 이동을 확인합니다. 실제 MoE 블록에서는 라우터와 비선형 FFN을 학습합니다. 여기서는 학습, 전문가별 수용량 제한, 장치 간 통신을 생략했습니다. 토큰 하나가 두 전문가의 출력을 받으므로 어느 행에 더하는지가 중요합니다.

```python
import torch
from torch import nn


def dispatch(x, logits, experts, k):
    # x: [tokens, width], logits: [tokens, experts]
    scores, choices = logits.topk(k, dim=-1)
    weights = scores.softmax(dim=-1)
    combined = torch.zeros_like(x)
    for expert_id, expert in enumerate(experts):
        token, slot = torch.where(choices == expert_id)
        if token.numel():
            values = expert(x[token])
            combined.index_add_(0, token, weights[token, slot, None] * values)
    return combined, choices, weights


# Two contextual representations of "bank", four toy expert projections.
x = torch.tensor([[1., 1.], [1., -1.]])
logits = torch.tensor([[3., 2., 0., -1.], [0., -1., 2., 3.]])
experts = nn.ModuleList(nn.Linear(2, 2, bias=False) for _ in range(4))
with torch.no_grad():
    for expert, scale in zip(experts, [2., -2., 6., 10.]):
        expert.weight.copy_(scale * torch.eye(2))
    y, choices, weights = dispatch(x, logits, experts, k=2)
    print(choices.tolist())       # [[0, 1], [3, 2]] at k=2
    torch.testing.assert_close(weights.sum(dim=1), torch.ones(2))
    print(y[:, 0].tolist())  # approximately [0.9242, 8.9242]
```

`torch.where`가 돌려주는 `token`은 입력의 행 번호이고, `slot`은 그 토큰의 상위 $k$개 결과에서 차지하는 열 번호입니다. 가중치 하나를 찾으려면 **토큰과 슬롯** 을 모두 알아야 합니다. `index_add_`는 가중치를 곱한 각 출력을 원래 토큰의 행에 더합니다. 위 실습과 함수 호출에서 `k`를 1이나 4로 바꿔 결과를 비교해 보세요. 강둑 예문에서는 어느 쪽으로 바꿀 때 출력이 더 많이 달라지나요?

<span id="다음-장을-향하여"></span>

토큰 $T$개가 각각 서로 다른 전문가 둘을 고르고 배정을 버리지 않으면 전문가별 배정 건수의 합은 $2T$입니다. 한 전문가가 토큰 $T$개를 전부 받더라도 각 토큰에는 두 번째 목적지가 있습니다. 메모리가 충분해도 바쁜 전문가를 기다리느라 다른 장치가 멈출 수 있습니다. [라우팅 알고리즘](../routing-algorithms/)에서는 학습 중 이 분포가 어떻게 달라지는지, [전문가 병렬화](../expert-parallelism/)에서는 토큰이 장치 사이를 어떻게 이동하는지 살펴봅니다.
