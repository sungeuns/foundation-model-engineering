# 5.4 전문가 붕괴와 부하 분산

개별 routing 선택은 합리적으로 보여도 분산 시스템 전체는 심하게 불균형해질 수 있습니다. 일부 expert에 토큰이 몰리고 다른 expert에는 학습 신호가 부족하며, 가장 느린 rank가 step 시간을 결정합니다. **전문가 붕괴** 는 가능한 피드백 실패이지 모든 MoE가 반드시 겪거나 모든 토큰이 한 expert에 도달하는 현상은 아닙니다.

목표는 **용량·통신 예산 안에서 유용한 전문화** 를 만드는 것입니다. 균등한 트래픽은 활용도의 대리 지표이지 최적 품질의 보장은 아닙니다. 부하 편중·토큰 drop·품질·straggler 시간을 함께 측정합니다.

## 1. 보조 부하 분산 손실

흔히 쓰는 균형 항은 할당 빈도와 평균 routing 확률을 결합합니다 [[1]](#ref-1).

$$
\mathcal L_{aux}=\alpha E\sum_{e=1}^{E}f_eP_e.
$$

$E$ 는 expert 수, $\alpha$ 는 계수, $f_e$ 는 관측된 할당 비율, $P_e$ 는 평균 routing 확률입니다. 정규화 규칙을 정의해야 합니다. top-1은 토큰을 세지만 top-$k$ 변형은 $T$ 개 유효 토큰의 $Tk$ 개 할당을 셀 수 있습니다. 이에 따라 scale이 달라집니다. padding은 제외하고 분산 통계의 범위를 의도한 균형 영역과 맞춥니다.

보조 손실의 가중치가 지나치면 과업 그래디언트와 경쟁할 수 있습니다. 반대로 심한 과소 활용을 막아 학습에 도움이 될 수도 있습니다. 이를 피할 수 없는 “정렬 세금”으로 부르면 10장의 정렬 trade-off와 routing 정규화를 혼동하게 됩니다. 보편적인 승자를 가정하지 말고 계수를 바꾸며 과업 손실·도메인 구간·부하 편중·처리량을 평가합니다.

## 2. 용량·drop·dropless 실행

top-$k$ 라우터의 단순한 평균 부하 기반 용량 모델은 다음과 같습니다.

$$
C_e=\left\lceil c\,\frac{Tk}{E}\right\rceil,
$$

$c$ 는 용량 계수, $C_e$ 는 expert당 할당 slot입니다. 실제 구현은 반올림·용량 집계 범위·dispatch 구조·동적 할당 방식이 다를 수 있습니다. $k$ 가 없는 top-1 식을 top-$k$ 트래픽에 그대로 적용하면 안 됩니다.

고정 용량 구현은 **초과 할당** 을 버리거나 reroute하거나, 잔차 경로를 남기고 일부 expert 기여를 생략할 수 있습니다. top-$k$ 에서는 할당 하나가 버려졌다고 해당 토큰의 모든 expert 기여가 없어지는 것은 아닙니다. drop은 토큰을 시퀀스에서 삭제하지 않으며 특정 장문 실패를 직접 증명하지도 않습니다. 도메인·토큰 위치·레이어·expert별 drop 비율을 측정합니다.

MegaBlocks 같은 dropless 시스템은 block-sparse 연산으로 고정 expert padding과 할당 drop을 피합니다 [[4]](#ref-4). 실제 routing 트래픽을 담을 메모리는 여전히 필요하며 부하 편중·통신 병목도 남습니다. dropless는 무제한 용량이라는 뜻이 아닙니다.

## 3. 라우터 Z-loss

ST-MoE는 수치 안정성을 위한 router z-loss를 연구합니다 [[2]](#ref-2).

$$
\mathcal L_z=\beta\frac{1}{T}\sum_{t=1}^{T}
\left(\log\sum_{e=1}^{E}\exp z_{t,e}\right)^2.
$$

$z_{t,e}$ 는 routing logit, $\beta$ 는 계수입니다. 보통 FP32로 안정적인 log-sum-exp를 계산합니다. 이는 log normalizer를 정규화하며 모든 logit을 개별적으로 제한하거나 학습 발산을 막는 보장은 아닙니다.

## 4. 보조 손실 없는 균형화

loss-free 균형화 연구는 동적으로 갱신되는 expert bias를 제안합니다 [[5]](#ref-5). DeepSeek-V3는 관련 선택 제어기를 사용하면서 작은 시퀀스 단위 보조 항도 유지합니다 [[3]](#ref-3). 따라서 loss-free라는 말이 전체 학습 목적에 균형 regularizer가 전혀 없다는 뜻은 아닙니다.

친화도 점수 $s_{t,e}$ 와 제어기 bias $b_e$ 로 다음 expert를 선택합니다.

$$
\mathcal E_t=\operatorname{TopK}_e(s_{t,e}+b_e).
$$

공개된 V3 설계에서 선택한 expert의 혼합 가중치는 bias를 더하지 않은 친화도 점수를 사용합니다. 관측 부하에 따라 과부하 expert의 bias를 낮추고 부족한 expert의 bias를 높입니다. **선택 점수** 와 **혼합 가중치** 를 구분해야 합니다. bias는 과업 그래디언트로 학습되지 않지만 선택이 바뀌면 토큰·그래디언트를 받는 expert도 달라집니다. “순수한 친화도” 학습이나 보조 손실에 대한 보편적 우월성이 증명되는 것은 아닙니다.

## 5. 교육용 손실 계산

> **의도적으로 단순화한 PyTorch 예제.** padding을 제외한 유효 토큰 배치의 정규화된 top-$k$ 할당 변형을 계산합니다. dispatch, 용량/drop 정책, expert 병렬 전역 집계, bias 갱신, 혼합 정밀도 최적화, 전체 학습 루프는 빠져 있습니다. smoke test를 통과한 운영 구현이 아닙니다.

```python
import torch
import torch.nn.functional as F


def compute_moe_losses(router_logits, top_k_indices, alpha=1e-2, beta=1e-4):
    # logits: [T, E]; indices: [T, k]; padding already excluded
    tokens, experts = router_logits.shape
    if tokens == 0 or top_k_indices.size(0) != tokens:
        raise ValueError("require a non-empty matching token batch")
    logits = router_logits.float()  # stable probability/normalizer arithmetic
    assignment_fraction = F.one_hot(
        top_k_indices, num_classes=experts
    ).float().mean(dim=(0, 1))  # includes every selected assignment
    mean_probability = logits.softmax(dim=-1).mean(dim=0)
    aux = alpha * experts * (assignment_fraction * mean_probability).sum()
    z_loss = beta * logits.logsumexp(dim=-1).square().mean()
    return aux, z_loss
```

이 예제의 할당 비율 합은 1입니다. 토큰 수로 정규화하는 구현에서는 합이 $k$ 가 되어 계수의 의미도 달라집니다. 분산 구현은 device/group 내부 또는 전역 중 어느 범위에서 균형을 계산할지, 그래디언트와 유효 토큰 수를 어떻게 일치시킬지 정해야 합니다.

## 6. 학습·복구 계약

모델/라우터 설정, 토크나이저·데이터 manifest, 필터/혼합 버전, sample/shard hash, 그룹 분할, 평가 격리를 고정합니다. top-$k$, expert 수, 용량 계수, drop 정책, 친화도/가중치 정규화, 보조·z-loss 계수, bias 갱신 속도, optimizer schedule, 토큰 배치, 정밀도, sharding, seed를 명시합니다.

모든 expert 파라미터·gradient/optimizer 상태·activation·dispatch 버퍼·collective·체크포인트·평가를 따로 계산합니다. 활성 expert는 토큰당 연산을 줄이지만 비활성 가중치를 저장 공간에서 없애지는 않습니다. expert별 할당 수, drop 비율, router entropy/log-normalizer, 토큰 정규화 학습·검증 손실과 도메인 구간, nonfinite/overflow, gradient/activation norm, 처리량, MFU, 데이터 대기, collective/straggler 시간, 재구성 가능한 batch ID를 기록합니다.

지속적인 수치 오류, 사전에 정한 drop/편중 경계, 검증 품질 저하, 관측 구간 밖 처리량 손실이 있으면 중단합니다. sharded 모델/optimizer, scheduler, scaler/FP8 상태, 전역 step/토큰 수, RNG, sampler/데이터 커서, 제어기 bias, 데이터/토크나이저/config hash를 checkpoint합니다. checksum·완료 표식을 갖춰 원자적으로 공개하고 보존·원격 복제·world-size 제한·학습 연속성 동등성 복원 훈련을 정의합니다.

도메인 품질·기존 역량 유지·안전·형식/도구·지연·비용·오류율 출시 조건을 짝지은 불확실성이나 근거 있는 표본 수로 통과한 뒤 불변 묶음을 배포합니다. 책임자·정상 동작이 확인된 이전 설정·rollback 훈련을 지정합니다. 좋은 부하 histogram만으로 출시할 수는 없습니다.

<summary>Quiz 1: 균등한 expert 트래픽이 최적 routing을 증명하지 않는 이유는 무엇인가요?</summary>
*균등 분배는 활용도를 높일 수 있지만 유용한 전문화와 충돌할 수 있습니다. 품질·부하 편중·drop·step 시간을 함께 평가해야 합니다.*
</details>

<details>
<summary>Quiz 2: 용량 추정에 top-k를 포함해야 하는 이유는 무엇인가요?</summary>
*유효 토큰마다 k개 expert 할당을 만듭니다. top-1 추정을 그대로 쓰면 평균 dispatch 부하를 k배 적게 셀 수 있습니다.*
</details>

<details>
<summary>Quiz 3: loss-free 선택은 DeepSeek-V3의 모든 균형 손실을 없애나요?</summary>
*아닙니다. 보고서는 작은 시퀀스 단위 보조 항도 유지합니다. 동적 선택 bias와 미분 가능한 regularizer는 별도 메커니즘입니다.*
</details>

<details>
<summary>Quiz 4: 제어기 bias를 checkpoint에 넣어야 하는 이유는 무엇인가요?</summary>
*이후 expert 선택에 영향을 주기 때문입니다. 제어기 상태 없이 가중치만 복원하면 dispatch·활용도·학습 연속성이 바뀔 수 있습니다.*
</details>
