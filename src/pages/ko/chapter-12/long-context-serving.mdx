# 12.5 긴 문맥 서빙

모델이 긴 요청을 받았다는 사실은 입력 계약을 통과했다는 뜻일 뿐입니다. 서빙 시스템에는 메모리 용량, 예측 가능한 지연, 복구 가능한 상태, 그리고 모델이 입력 정보를 실제로 활용한다는 근거가 필요합니다. 바쁜 작업장에 큰 일감이 들어온 상황을 떠올려 보세요. 작은 단위로 나누면 다른 일의 대기 시간을 조절할 수 있지만 총작업량이 사라지지는 않습니다.

## 1. 아키텍처가 실제로 저장하는 상태를 계산한다

균일한 attention 스택의 논리적 KV 용량은 다음과 같습니다.

$$
M_{KV}=2bL n_{layers} n_{KV} d_{head} s.
$$

$b$는 배치 크기, $L$은 시퀀스당 캐시 토큰 수, $n_{layers}$는 attention 층 수, $n_{KV}$는 **KV 헤드 수**, $d_{head}$는 헤드 차원, $s$는 저장 스칼라당 바이트 수입니다. 앞의 2는 key와 value를 셉니다. Query 헤드 수는 연산량에 관여하지만 GQA 메모리 식의 KV 헤드 수를 대신할 수 없습니다.

가상의 32층 모델이 query 헤드 32개, KV 헤드 8개, $d_{head}=128$, BF16 저장, 단일 시퀀스를 사용한다고 합시다. 4,096토큰의 논리적 KV 용량은 **0.5 GiB**, 131,072토큰은 **16 GiB**입니다. KV 헤드를 32개로 계산하면 네 배가 됩니다. 이는 계산 예시이며 특정 모델의 지원 문맥 길이를 뜻하지 않습니다.

> **용량 계산 예제의 한계:** 아래 표준 라이브러리 함수는 정수 계산과 입력 검증을 smoke test했습니다. 실제 메모리 할당·수용량 시험은 아닙니다. 파라미터·활성화·임시 버퍼·페이지와 scale 메타데이터·단편화·그래프 풀·collective·체크포인트 및 복구 비용을 제외합니다. 하이브리드 스택은 층별 KV와 순환 상태를 따로 계산하고, 장치별 용량에는 샤딩·복제 방식을 반영해야 합니다.

```python
def kv_payload_bytes(*, layers, kv_heads, head_dim, tokens,
                     batch=1, bytes_per_value=2):
    values = (layers, kv_heads, head_dim, tokens, batch, bytes_per_value)
    if any(type(value) is not int or value <= 0 for value in values):
        raise ValueError("All dimensions and byte widths must be positive integers")
    return 2 * layers * kv_heads * head_dim * tokens * batch * bytes_per_value

# Hypothetical uniform GQA model, BF16, one sequence.
size = kv_payload_bytes(layers=32, kv_heads=8, head_dim=128, tokens=131072)
print(size / 2**30)  # 16.0 GiB of logical KV payload
```

Prefill은 대개 연산 집약도가 높고, 소배치 dense decode는 낮습니다. 하지만 보편적인 구분은 아닙니다. 길이·배치·attention 희소성·양자화·전문가 통신·커널 구현에 따라 병목이 바뀝니다. 한 단계는 전적으로 연산, 다른 단계는 전적으로 대역폭 병목이라고 단정하지 말고 목표 부하에서 측정해야 합니다.

## 2. 스트리밍 안정성과 전체 이력 회상은 다르다

StreamingLLM은 초기 attention-sink 토큰과 최근 윈도우를 유지해 실험 설정에서 스트리밍을 안정화합니다 [[1]](#ref-1). 상태 크기를 고정한다고 윈도우 밖에서 버린 임의의 근거까지 보존되지는 않습니다. 안정적인 손실 곡선은 전체 이력 이해의 증거가 아닙니다.

YaRN은 평가한 모델에서 유효 문맥을 늘리도록 RoPE 스케일링을 수정합니다 [[2]](#ref-2). 무한 문맥을 만들거나 외삽을 보장하지는 않습니다. 목표 길이·위치 분포·출력 예산에서 검색, 근거 통합, 생성을 검증해야 합니다.

## 3. 청크 분할은 간섭을 조절한다

Sarathi는 청크 단위 prefill과 decode의 교차 실행을 연구합니다 [[3]](#ref-3). 청크를 줄이면 기존 요청이 새 프롬프트 뒤에서 기다리는 시간을 줄일 수 있지만, 커널 효율과 긴 요청 자체의 TTFT는 나빠질 수 있습니다. 청크 attention도 앞선 prefix의 key를 참조해야 하므로, 독립적인 정사각 행렬 곱의 시간을 재는 것은 충실한 서빙 시뮬레이션이 아닙니다.

도착 이력에 따라 부하를 주고 TTFT·토큰 간 지연의 p50/p95/p99, 큐 체류 시간, prefill 적체, tokens/s, 거절률을 측정합니다. 부하 시험 전에 수용 한도와 기한을 정합니다. 최대 처리량뿐 아니라 지연·정확성 계약을 만족한 요청의 **유효 처리량(goodput)** 을 비교해야 합니다.

## 4. 분리형 서빙에는 전송·소유권 계약이 필요하다

Splitwise와 DistServe는 prefill·decode 자원 풀을 분리하는 방법을 연구합니다 [[4]](#ref-4) [[5]](#ref-5). 하드웨어는 측정한 용량·대역폭·연산·인터커넥트 요구에 따라 선택합니다. “Decode에는 저렴한 GPU를 쓴다”는 보편 법칙은 아닙니다.

전송 시간의 유용한 하한은 $t_{transfer}\geq M_{wire}/B_{effective}$입니다. $M_{wire}$는 실제 전송 바이트 수, $B_{effective}$는 달성한 대역폭입니다. 준비·패킹·혼잡·동기화·스케줄링 비용이 추가되므로 payload를 절반으로 줄여도 전체 지연이 절반이 되지는 않습니다.

캐시 버전의 소유자와 인계 완료 시점을 정의합니다. 수신자는 요청·prefix 식별자, 모델·토크나이저·템플릿 해시, 위치 offset, 캐시 layout/dtype, 완료 상태를 확인한 뒤 decode를 시작합니다. 불일치하면 재계산하거나 거절합니다. 텐서 모양이 같다는 이유만으로 캐시를 연결하면 안 됩니다. 양자화는 전송량뿐 아니라 수치적 동작도 바꾸므로 과업 평가가 필요합니다.

## 5. 문맥 수용량과 추론 품질은 다르다

**2026-10-18 기준**, Gemini 4 Argon API는 **입출력 통합** 1,048,576토큰 윈도우, 기본 동기 출력 최대 65,536토큰, 별도의 long-decode 경로를 명시합니다 [[6]](#ref-6). 가득 찬 입력 윈도우에 최대 출력량을 추가로 더할 수는 없습니다. 정확한 endpoint 계약에 따라 요청한 출력 예산을 예약해야 합니다.

10월 15일 LURCH 프리프린트는 근거·추론 그래프를 가진 질의로 장문 난도를 근거 범위·근거 분산·추론 깊이로 구분합니다 [[7]](#ref-7). 결과는 해당 평가 설정의 근거이며, 이 속성들은 유용한 평가 축이지 보편적인 용량 법칙은 아닙니다.

실무 시험은 **토큰 길이를 고정하고** 이 축들을 바꾼 뒤, 과제 구조를 고정한 채 길이를 바꿔야 합니다. 정답 근거를 직접 제공하는 조건으로 검색과 추론을 분리하고, 인용 정확성과 답변 보류도 평가합니다. 단일 needle 검색 성공만으로 분산된 근거의 다단계 종합 능력을 입증할 수는 없습니다.
