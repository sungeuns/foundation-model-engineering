# 12.3 연속 배칭: 요청 교체와 청크 프리필

세 요청이 함께 토큰을 생성하고 있습니다. 하나는 decode를 두 번 반복하면 끝나지만, 다른 하나는 여섯 번이 필요합니다. 네 번째 요청은 빈자리를 쓰기 위해 네 번을 더 기다려야 할까요? **연속 배칭(continuous batching)** 은 토큰·KV 캐시 예산이 허용하면 바로 다음 반복 경계에서 새 요청을 받습니다.

앞 절에서는 계속 늘어나는 KV 상태를 어디에 저장하는지 살펴봤습니다. 이번에는 어떤 요청을 다음에 실행할지 결정합니다. 메모리 블록을 재사용할 수 있으면 새 요청을 받기 쉬워지지만, 메모리 할당자만으로 실행 순서가 정해지지는 않습니다.

## 1. 세 슬롯에서 여섯 요청 따라가기

이 절에서는 같은 설명용 워크로드를 사용합니다. 요청 A–F의 **남은 decode 토큰은 각각 4, 2, 6, 3, 5, 2개** 입니다. 모두 실행 전에 대기열에 도착했고 슬롯은 세 개입니다. 선택된 요청은 반복마다 토큰 하나를 생성합니다. 요청을 받는 규칙만 비교하도록 prefill은 제외했습니다. 아래 숫자는 반복 횟수이며 밀리초 측정값이 아닙니다.

**여기서 정의한 정적 정책** 은 A, B, C를 한 그룹으로 묶습니다. 완료한 요청은 결과를 반환하고 메모리를 해제할 수 있습니다. 다만 그룹 전체가 끝나기 전에는 빈자리에 새 요청을 넣지 않습니다. 구현에 따라 완료한 행을 마스킹하거나 배치에서 줄일 수 있습니다. 따라서 정적 배칭이라고 반드시 메모리를 계속 잡아두거나 더미 연산을 해야 하는 것은 아닙니다.

연속 정책은 매 반복 경계에서 빈 슬롯에 대기 요청을 넣습니다. 표는 각 반복에서 실행되는 요청입니다. 체크 표시는 해당 요청이 그 반복의 **끝에서 완료** 된다는 뜻이며, 새 요청은 다음 행부터 그 자리를 쓸 수 있습니다.

| 반복 | 정적: 슬롯 1 / 2 / 3 | 연속: 슬롯 1 / 2 / 3 |
|---|---|---|
| 1 | A / B / C | A / B / C |
| 2 | A / B ✓ / C | A / B ✓ / C |
| 3 | A / — / C | A / D / C |
| 4 | A ✓ / — / C | A ✓ / D / C |
| 5 | — / — / C | E / D ✓ / C |
| 6 | — / — / C ✓ | E / F / C ✓ |
| 7 | D / E / F | E / F ✓ / — |
| 8 | D / E / F ✓ | E / — / — |
| 9 | D ✓ / E / — | E ✓ / — / — |
| 10 | — / E / — | 전체 요청 완료 |
| 11 | — / E ✓ / — | 전체 요청 완료 |

B는 반복 2에서 끝납니다. 연속 배칭에서는 반복 3에 D가 그 슬롯을 쓰지만, 정적 배칭에서는 반복 7까지 기다립니다. 같은 decode 토큰 22개를 **11회 대신 9회** 에 모두 처리합니다. 이것만으로 GPU 속도 향상 비율을 구할 수는 없습니다. 배치 구성, 문맥 길이, 커널에 따라 반복 한 번의 시간이 달라집니다. 연속 배칭도 대기열이 비면 빈 슬롯이 생깁니다.

### 완료되는 경계를 직접 확인하기

반복 2와 3을 비교하며 B의 자리에 D가 들어오는지 확인하세요. 이어서 반복 5의 대기열과 반복 9의 완료 상태를 비교해보세요. 카드는 방금 완료한 요청을 포함해 각 반복의 끝을 보여줍니다. 0단계는 아직 요청을 배정하지 않은 상태입니다.

## 2. 빈 슬롯 외에도 확인할 입장 조건

Orca는 요청 그룹 전체가 끝나기를 기다리는 대신 반복 단위로 실행을 스케줄링하는 방법을 연구했습니다 [[1]](#ref-1). 일반적인 자기회귀 decode에서는 선택된 요청마다 한 단계에서 새 토큰 하나를 만듭니다. 하지만 prefill 청크는 프롬프트를 끝까지 처리하기 전까지 출력 토큰을 내지 않을 수 있고, 투기적 디코딩은 여러 토큰을 한꺼번에 확정할 수 있습니다. 반복은 스케줄링 단위이지 언제나 “모든 활성 요청이 토큰 하나씩 생성하는 단계”는 아닙니다.

반복 경계에서 스케줄러는 완료·취소 요청을 반영하고, 미완료 요청의 상태를 유지한 뒤 다음 작업을 고릅니다. 요청의 KV 참조를 해제해도 다른 요청이나 prefix cache가 같은 블록을 참조한다면 물리 블록이 바로 반환되지는 않습니다. 새 요청은 요청 수 제한, 토큰 예산, 남은 KV 용량, 스케줄링 정책을 모두 만족해야 합니다.

반복당 입력 토큰 예산을 $B$, 선택된 일반 decode 요청 수를 $D$, 선택된 prefill 토큰 수를 $P$ 라 합시다. Decode 요청마다 입력 토큰 위치 하나를 쓰는 단순한 정책에서는

$$
D+P\le B.
$$

이것은 **한 번에 실행할 작업량** 이지 KV 캐시에 저장된 전체 토큰 수가 아닙니다. 토큰 하나를 decode하는 요청도 문맥 수천 토큰을 이미 보관할 수 있습니다. 요청 슬롯이 남아 보여도 KV 용량이 부족하면 새 요청을 받을 수 없습니다. 반대로 대기열이 비었다면 어떤 정책도 남은 용량을 채울 수 없습니다.

## 3. Prefill이 지연 시간의 절충을 바꾸는 이유

Prefill은 프롬프트를 처리하고 해당 토큰의 KV 상태를 만듭니다. 한 순전파 안에서 여러 프롬프트 위치를 병렬로 계산할 수 있습니다. 마지막 프롬프트 위치의 logits로 첫 출력 토큰을 뽑고, 그 뒤에는 캐시된 상태를 사용해 decode 단계마다 시퀀스를 늘립니다.

긴 prefill은 산술 집약도가 높은 경우가 많고, 작은 배치의 decode는 가중치와 KV 상태를 읽는 데 많은 시간을 쓰기 쉽습니다. 다만 배치 크기, 문맥 길이, 모델 구조, 커널 설계에 따라 병목이 달라집니다. Decode에는 투영·attention 등 여러 연산이 들어갑니다. 언제나 Tensor Core를 쓰지 못하는 GEMV 하나로 설명할 수는 없습니다.

공유 실행 자원에서 긴 prefill을 먼저 수행하면 기존 decode 요청의 다음 토큰이 늦어집니다. **첫 토큰 지연(TTFT)** 은 새 요청이 대기하고 프롬프트를 처리한 뒤 첫 토큰을 전달받기까지의 시간입니다. **토큰 간 지연(ITL)** 은 생성 중인 응답에서 연속된 두 토큰을 전달받는 시간 간격입니다. 하나가 좋아져도 다른 하나가 자동으로 좋아지지는 않습니다. 전송 지연도 영향을 줄 수 있으므로 서버 기준인지 클라이언트 기준인지 함께 명시해야 합니다.

## 4. 청크 프리필: 작업량을 나누고 시간을 측정하기

SARATHI는 prefill을 청크로 나누고 decode와 함께 배치하는 설계를 제시했습니다 [[2]](#ref-2). 청크를 나누면 긴 프롬프트를 처리하는 도중에도 스케줄링 경계가 생깁니다. 프롬프트 처리 비용이 없어지거나 스트리밍이 항상 매끄러워지는 것은 아닙니다.

작은 수치 예제로 $B=10$ 이고 진행 중인 decode 세 요청에 토큰 위치 세 개를 먼저 배정한다고 합시다. 20토큰 프롬프트는 매 반복에서 남은 일곱 위치를 사용할 수 있습니다.

| 반복 | Decode 입력 토큰 | Prefill 입력 토큰 | 아직 처리하지 않은 프롬프트 토큰 |
|---|---|---|---|
| 1 | 3 | 7 | 13 |
| 2 | 3 | 7 | 6 |
| 3 | 3 | 6 | 0 |

세 decode 요청이 계속 실행되고 KV 메모리가 충분하다고 가정한 계산입니다. 프롬프트의 마지막 위치를 처리하는 반복 3에서 첫 출력 토큰을 뽑을 수 있습니다. 앞의 두 청크에서 사용자에게 보여줄 토큰이 하나씩 나오는 것은 아닙니다. 토큰 예산을 늘리면 프롬프트를 더 빨리 끝낼 수 있지만 기존 decode 요청이 겪는 각 단계의 시간이 늘어날 수 있습니다. 토큰 수만으로 밀리초를 예측할 수는 없습니다.

**2026-11-25 기준**, vLLM V1 최적화 문서는 decode 작업을 우선 배정하고 `max_num_batched_tokens` 의 남은 예산에 prefill을 넣으며, 들어가지 않는 prefill은 청크로 나누는 정책을 설명합니다 [[3]](#ref-3). 이 토큰 예산과 요청 수 제한인 `max_num_seqs` 는 다릅니다. 엔진 버전과 실제 적용한 설정을 기록하세요. 위 예제는 산술 모형이며 운영 환경의 권장 설정이 아닙니다.

### 공유 실행 타임라인 읽기

## 5. Decode 전용 스케줄 직접 실행하기

> **Python 표준 라이브러리만 쓰는 의도적으로 단순화한 CPU 시뮬레이션.** FIFO 입장 순서와 고정된 남은 decode 길이로 첫 번째 표를 재현합니다. 모든 요청은 실행 전에 도착했고 decode 준비가 끝났다고 취급합니다. Prefill, 실제 토큰 샘플링·EOS, KV 할당, 토큰 예산, 취소, 우선순위·공정성, 동시성, GPU 시간 측정을 생략합니다. 서빙 지연을 시뮬레이션하거나 운영용 구현을 제시하는 코드가 아닙니다.

```python
from collections import deque


def schedule(requests, capacity=3, continuous=True):
    """Decode-only FIFO model; requests are (ID, remaining_decode_tokens)."""
    if capacity <= 0 or any(length <= 0 for _, length in requests):
        raise ValueError("capacity and decode lengths must be positive")
    if len({name for name, _ in requests}) != len(requests):
        raise ValueError("request IDs must be unique")
    waiting = deque(requests)
    active = [None] * capacity
    trace, finished = [], {}
    while waiting or any(request is not None for request in active):
        # A static group admits replacements only when its survivors are gone.
        if continuous or all(request is None for request in active):
            for slot in range(capacity):
                if active[slot] is None and waiting:
                    name, length = waiting.popleft()
                    active[slot] = [name, length]
        iteration = len(trace) + 1
        trace.append(tuple(request[0] if request else "-" for request in active))
        for slot, request in enumerate(active):
            if request is not None:
                request[1] -= 1  # one decode token for this active request
                if request[1] == 0:
                    finished[request[0]] = iteration
                    active[slot] = None  # reusable at the next boundary
    return trace, finished


requests = [("A", 4), ("B", 2), ("C", 6), ("D", 3), ("E", 5), ("F", 2)]
static, static_end = schedule(requests, continuous=False)
continuous, continuous_end = schedule(requests, continuous=True)
assert (len(static), len(continuous)) == (11, 9)
assert static_end == {"A": 4, "B": 2, "C": 6, "D": 9, "E": 11, "F": 8}
assert continuous_end == {"A": 4, "B": 2, "C": 6, "D": 5, "E": 9, "F": 7}
assert static[2] == ("A", "-", "C")
assert continuous[2] == ("A", "D", "C")
print(f"static={len(static)}, continuous={len(continuous)} iterations")
for iteration, slots in enumerate(continuous, start=1):
    print(iteration, " ".join(slots))
```

예상 출력:

```text
static=11, continuous=9 iterations
1 A B C
2 A B C
3 A D C
4 A D C
5 E D C
6 E F C
7 E F -
8 E - -
9 E - -
```

완료 시점 검사는 두 입장 정책의 차이를 확인합니다. 마지막 요청이 끝나면 루프도 바로 종료하므로 빈 “GPU 반복”을 한 번 더 실행하지 않습니다. 빈 입력은 빈 실행 기록을 반환하며, 슬롯 수가 0이거나 decode 길이가 양수가 아니면 거부합니다. 남은 길이나 슬롯 수를 바꿔 실행하기 전에 어떤 요청이 더 일찍 들어갈지 먼저 설명해보세요.

## 6. 실제 요청 분포에서 스케줄러 검증하기

프롬프트·출력 길이와 순간적인 요청 집중을 유지한 도착 기록을 재생합니다. 모델, 하드웨어, 정밀도, 품질 설정을 고정하세요. **정한 지연 시간 예산을 지키는 범위에서** 처리량을 비교하고, TTFT·ITL 분포, 대기 시간, KV 점유율, 선점, 취소, 오류를 함께 봅니다. 긴 프롬프트와 짧은 프롬프트, 낮은 부하와 높은 부하를 나눠 확인해야 합니다. 평균이 좋아도 일부 요청이 계속 밀리거나 꼬리 지연이 나빠질 수 있습니다.

요청 기록의 식별자, 모델·런타임 버전, 스케줄러 설정, 입장 제한을 결과와 함께 저장합니다. 초당 토큰 수가 늘어도 미리 정한 꼬리 지연·오류 기준을 넘으면 변경을 받아들이지 않습니다. 이전 설정은 롤백할 수 있도록 보관합니다. 다음 절에서는 반복당 작업량을 바꾸는 다른 방법인, 여러 후보 토큰을 함께 검증하는 투기적 디코딩을 살펴봅니다.

*각 반복의 배치 구성·문맥 길이·실행 시간이 다를 수 있기 때문입니다. 이 예제는 prefill, KV 제한, 스케줄러 비용도 제외했습니다. 조건을 맞춘 워크로드를 측정해야 하며, 슬롯이 차 있는 비율은 GPU 활용률 측정값이 아닙니다.*
</details>

<details>
<summary>Quiz 3: 토큰 예산이 10이고 decode 세 요청이 계속 실행된다면 20토큰 프롬프트는 어떻게 처리하나요?</summary>
*예제의 정책에서는 세 반복에 걸쳐 prefill 위치를 7, 7, 6개 배정합니다. 마지막 프롬프트 위치를 처리할 때 첫 출력 토큰을 뽑을 수 있습니다. 입력 위치 일곱 개가 남았다는 말이 KV 위치도 일곱 개만 필요하다는 뜻은 아닙니다. 기존 문맥은 계속 저장됩니다.*
</details>

<details>
<summary>Quiz 4: Prefill 청크를 줄이면 ITL은 좋아지지만 TTFT는 나빠질 수 있나요?</summary>
*그렇습니다. 기존 요청의 다음 decode 앞에 놓이는 작업을 줄일 수 있지만, 새 프롬프트는 더 많은 청크를 배정받거나 더 오래 기다려야 할 수 있습니다. 부하와 커널에 따라 결과가 달라지므로 두 지연 분포를 모두 측정해야 합니다.*
</details>

<details>
<summary>Quiz 5: 대기 요청이 있는데도 연속 배치에 빈 슬롯이 남을 수 있는 이유는 무엇인가요?</summary>
*토큰·KV 예산이 부족하거나 입장 우선순위 때문에 작업이 미뤄질 수 있습니다. 요청 수 슬롯은 여러 제약 중 하나일 뿐입니다. 대기열 자체가 비었다면 어떤 스케줄러도 모든 슬롯을 계속 채울 수 없습니다.*
</details>
