# 12.4 투기적 디코딩 (Speculative Decoding)

같은 문장을 여러 번 이어 쓴다고 합시다. 다음 토큰 후보는 A와 B뿐이고, 원래 모델은 A를 B보다 세 배 자주 고릅니다. 더 작은 모델이 다음 토큰들을 미리 써 줄 수 있지만, 이 모델에서는 반대로 B가 세 배 자주 나옵니다. 초안을 활용하면서도 원래의 75 대 25 비율을 지킬 수 있을까요? 이 절에서는 투기적 디코딩 중 확률적으로 토큰을 뽑는 **투기적 샘플링(speculative sampling)** 을 다룹니다. [[1]](#ref-1) [[2]](#ref-2)

## 목표 모델을 한 번 실행해 어디까지 검증할 수 있을까?

작은 배치에서 토큰을 하나 생성할 때는 목표 모델의 가중치를 읽는 데 시간이 많이 들 수 있습니다. 더 가벼운 초안 모델이 토큰 $K$ 개를 차례로 제안하면, 목표 모델은 기존 문맥에 이 토큰열을 붙여 여러 위치의 점수를 병렬로 계산합니다. 인과 마스크를 적용하므로 각 후보의 점수는 그 앞의 토큰에만 의존합니다. 검증에는 원래 문맥의 다음 토큰 분포, 각 후보를 받아들인 뒤의 다음 토큰 분포, 마지막 후보까지 받아들였을 때 추가 토큰을 뽑을 분포가 필요합니다. 첫 분포는 앞선 목표 모델 계산에서 이미 구해 두었을 수 있습니다. [[1]](#ref-1)

채택 여부는 앞에서부터 결정합니다. 아래 확률 검사를 통과하면 초안 토큰을 그대로 씁니다. 처음 거절한 위치에서는 **잔여 분포** 에서 대체 토큰을 하나 뽑고, 그 뒤의 후보는 버립니다. 확정한 토큰열에서 다음 주기를 시작합니다. 후보 $K$ 개를 모두 채택하면 목표 분포에서 토큰 하나를 더 뽑을 수 있습니다. 종료 토큰이나 출력 길이 제한에 걸리면 거기서 멈춥니다. 첫 후보에서 거절하면 한 주기의 출력은 1개, 모두 통과하면 최대 $K+1$ 개입니다.

## 거절했을 때 목표 분포에서 다시 뽑으면 왜 틀릴까?

앞의 두 토큰으로 돌아가 봅시다. 초안 분포 $q$ 에서 A와 B가 나올 확률은 각각 25%, 75%입니다. 목표 분포 $p$ 에서는 75%, 25%입니다. 초안의 A는 전부 쓰고 B는 3분의 1만 받아들입니다. 전체 시행을 기준으로 A와 B가 각각 25%씩 확정됩니다. 목표 비율을 채우려면 남은 50%가 전부 A여야 합니다.

거절한 50%를 원래 목표 분포에서 다시 뽑으면 그중 4분의 3만 A가 됩니다. 최종 A 확률은 $0.25 + 0.5 \times 0.75 = 0.625$입니다. 아래에서 초안의 A 확률을 목표의 A 확률보다 높여 보세요. 이번에는 어느 토큰을 보충해야 할까요?

초안이 $q(x)>0$ 인 토큰 $x$ 를 제안하면 그 토큰을 $\min(1,p(x)/q(x))$ 의 확률로 채택합니다. $x$ 가 제안되어 그대로 채택될 확률은 $\min(p(x),q(x))$ 입니다. 각 토큰 $y$ 에서 부족한 확률 질량은 $r(y)=\max(0,p(y)-q(y))$ 이고, 이를 어휘 전체에서 합한 값 $R$ 은 거절 확률과 같습니다. 거절한 경우에는 $r(y)/R$ 의 확률로 $y$ 를 뽑습니다. 채택과 보충을 더하면 $\min(p(y),q(y))+r(y)=p(y)$ 로 원래 목표 확률이 나옵니다. $R=0$ 이면 모든 초안을 채택하므로 대체 토큰을 뽑을 필요가 없습니다. [[1]](#ref-1) [[2]](#ref-2)

이 계산은 확정된 문맥마다 반복됩니다. 이때 쓰는 확률은 온도나 top-p 같은 서빙 설정을 적용한 **뒤의 분포** 입니다. 두 방법에서 보존되는 것은 토큰열의 확률 분포입니다. 같은 난수 시드를 쓰더라도 난수를 소비하는 순서가 달라 실제 문장은 달라질 수 있습니다.

## 초안을 한 토큰 더 쓰는 편이 이득일까?

비용을 계산하는 예로 $K=2$ 이고 각 후보가 독립적으로 $\alpha=0.5$ 의 확률로 채택된다고 가정합시다. 조기 종료가 없다면 한 주기에서 첫 출력은 항상 나오고, 두 번째 출력이 나올 확률은 0.5, 세 번째는 0.25입니다. 따라서 **주기당 평균 출력은 1.75토큰** 입니다. 일반 디코딩이 토큰당 10ms라면 같은 수의 토큰을 생성하는 데 평균 17.5ms가 걸립니다. 가령 초안과 검증을 포함한 한 주기가 14ms면 빨라지고, 20ms면 같은 채택률에서도 느려집니다. 실제 판단에는 서비스에서 측정한 시간이 필요합니다. [[1]](#ref-1)

<a id="kv-캐시-동기화"></a>

초안의 몇 번째 토큰까지 채택됐는지, 몇 개를 버렸는지, 검증과 상태 복원에 시간이 얼마씩 들었는지 기록하세요. 거절 뒤에는 두 모델 모두 확정된 문맥에 맞는 상태에서 다시 시작해야 합니다. 버린 후보에 대해 임시로 계산한 상태가 이후 예측에 쓰여서는 안 됩니다. 같은 프롬프트, 샘플링 설정, [배치 스케줄링](/ko/chapter-12/continuous-batching) 조건에서 종단 간 지연 시간의 백분위수와 초당 전달 토큰 수를 비교합니다. 연속해서 채택되는 토큰이 늘어도 초안을 만드는 데 시간이 더 들면 일반 디코딩보다 느릴 수 있습니다.

## 교육용 검증 참조

다음 Python 코드는 초안 토큰열 하나를 같은 문맥에서 구한 목표 분포와 대조합니다. 마지막 줄은 고정된 시드로 한 주기를 실행해 확정한 토큰들과, 그중 초안에서 채택한 개수를 출력합니다.

> 두 모델이 같은 어휘를 사용하고 이미 정규화된 확률을 받는 Python 표준 라이브러리 예제입니다. 모델 실행, 로짓 필터, 텐서 배치, 종료 토큰과 길이 제한, KV 캐시, 분산 스케줄링은 생략했습니다.

```python
import math
import random


def validate_distribution(probabilities):
    if not probabilities or any(not math.isfinite(p) or p < 0 for p in probabilities):
        raise ValueError("require finite nonnegative probabilities")
    if not math.isclose(sum(probabilities), 1.0, abs_tol=1e-8):
        raise ValueError("probabilities must sum to one")


def draw(probabilities, rng):
    threshold = rng.random() * math.fsum(probabilities)
    cumulative = 0.0
    for token, probability in enumerate(probabilities):
        cumulative += probability
        if threshold < cumulative:
            return token
    # Rounding can leave the running sum just below the threshold.
    return max(token for token, probability in enumerate(probabilities) if probability > 0)


def verify_draft_tokens(draft_probs, target_probs, draft_tokens, rng):
    # One sequence: q has K rows; p has K+1 rows, including the bonus.
    # Each p row is target-verified under the corresponding draft prefix.
    k = len(draft_tokens)
    if k < 1 or len(draft_probs) != k or len(target_probs) != k + 1:
        raise ValueError("require K draft rows and K+1 target rows")
    vocab = len(target_probs[0])
    for row in [*draft_probs, *target_probs]:
        validate_distribution(row)
        if len(row) != vocab:
            raise ValueError("draft and target must share a token space")

    output = []
    for i, token in enumerate(draft_tokens):
        if not 0 <= token < vocab or draft_probs[i][token] <= 0:
            raise ValueError("proposal must have positive draft probability")
        q = draft_probs[i][token]
        p = target_probs[i][token]
        if rng.random() < min(1.0, p / q):
            output.append(token)
        else:
            residual = [max(pj - qj, 0.0)
                        for pj, qj in zip(target_probs[i], draft_probs[i])]
            mass = sum(residual)
            if mass <= 0:
                raise ArithmeticError("rejection with no residual mass")
            output.append(draw([value / mass for value in residual], rng))
            return output, i  # accepted draft count; no bonus after rejection

    output.append(draw(target_probs[k], rng))
    return output, k  # bonus only when all K draft tokens were accepted


rng = random.Random(7)
q = [[0.25, 0.75]]
p = [[0.75, 0.25], [0.5, 0.5]]
proposal = [draw(q[0], rng)]  # sample from q, not argmax(q)
output, accepted_drafts = verify_draft_tokens(q, p, proposal, rng)
print(output, accepted_drafts)
```

## 트리형 speculative decoding에는 분기별 상태 격리가 필요하다

**2026-11-25 기준 연구 스냅샷.** 9월 DeepSeek-V4-Flash 연구는 압축 어텐션에 트리형 speculation을 적용하면서 분기별 검증, 임시 상태 격리, 채택한 경로의 상태 갱신을 사용합니다 [[3]](#ref-3). 분기가 갈라진 뒤에는 압축 상태도 달라질 수 있습니다. 어느 경로를 채택할지 결정될 때까지 검증 과정에서 각 분기의 상태를 따로 유지해야 합니다. 연구에서는 채택 길이가 늘어도 처리량이 포화되는 경우를 보고합니다.

실무 검증은 같은 raw logits만 비교하지 말고 같은 temperature·top-k/top-p가 적용된 실제 분포에서 일반 샘플링과 비교합니다. 모든 깊이에서의 거절, 전부 채택됐을 때의 bonus, EOS·취소·가변 배치 길이, 압축/recurrent 상태 복원을 검사합니다. 채택한 **draft** 토큰을 대체·bonus 토큰과 구분하고, draft·검증·상태 갱신·스케줄링을 포함한 총시간을 보고합니다. 채택 길이가 길어졌다고 서비스가 반드시 빨라지는 것은 아닙니다.

*첫 토큰은 반드시 나옵니다. 두 번째 출력이 나오려면 한 번, 세 번째는 두 번 연속 채택해야 하고 $K+1$ 개가 나오려면 모두 채택해야 합니다. 기대값은 $1+\alpha+\cdots+\alpha^K$ 입니다. $\alpha<1$ 이면 $(1-\alpha^{K+1})/(1-\alpha)$ 이고 $\alpha=1$ 이면 $K+1$ 입니다. 실제 서비스에서는 종료 정책을 적용했을 때 각 깊이까지 도달한 비율을 측정합니다.*
</details>
