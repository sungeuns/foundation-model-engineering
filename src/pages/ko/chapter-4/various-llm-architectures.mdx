# 4.5 다양한 LLM 아키텍처

이쯤 오면 아키텍처 논쟁은 끝났다고 느끼기 쉽습니다. decoder-only가 이겼고, 모두가 GPT를 조금씩 변형하는 정도라고 생각하기 쉽죠. 하지만 실제 엔지니어링은 그 지점에서 시작됩니다. 컨텍스트를 더 길게 가져가야 하고, 서빙 비용은 낮춰야 하고, 처리량은 높여야 하며, tool use나 reasoning 같은 능력도 챙겨야 하기 때문입니다.

교통수단에 비유하면 이해가 쉽습니다. 화물선, 경주용 자동차, 통근 열차는 모두 무언가를 이동시키지만 최적화 대상이 완전히 다릅니다. 현대 LLM도 비슷합니다. 모두 자기회귀적으로 텍스트를 생성하지만, KV cache 성장, attention 복잡도, routing 효율, 학습 안정성 중 무엇이 더 아픈 병목인지에 따라 내부 설계가 달라집니다.

이 절에서는 최신 모델 이름을 외우는 대신, 어떤 압력이 어떤 설계를 낳았는지를 먼저 보겠습니다.

[11월 24일 업데이트](#glm-54-레이어-재사용으로-깊이와-용량을-구분하기)에서는 GLM-5.4의 레이어 반복 구조와 GPT-6.2의 공개된 인터페이스를 추가합니다. 앞선 날짜가 붙은 표는 당시의 기록입니다.

## 아키텍처가 계속 갈라지는 이유

Chapter 3에서 본 표준 Transformer는 출발점입니다. 실제 시스템은 다음과 같은 압박을 반복해서 받습니다.

1. 긴 컨텍스트에서는 full attention 비용이 급격히 커집니다.
2. 자기회귀 서빙에서는 KV cache가 메모리와 대역폭을 압박합니다.
3. dense FFN은 모델이 커질수록 비용이 빠르게 증가합니다.
4. next-token prediction 하나만으로는 처리량이나 reasoning을 최적화하기 어려운 경우가 있습니다.

최근 아키텍처 변화의 대부분은 이 네 가지 병목에 대한 대응으로 이해할 수 있습니다.

### 1. 하이브리드 및 선형 어텐션 (Hybrid & Linear Attention)
표준 self-attention은 시퀀스 길이에 대해 제곱 비용이 들기 때문에, 컨텍스트가 길어질수록 부담이 커집니다. 그래서 최근에는 **Hybrid Attention** 스택이 자주 등장합니다.

핵심 아이디어는 간단합니다. 모든 레이어에 똑같이 비싼 full attention을 쓰지 말고, 일부 레이어만 강한 전역 상호작용을 담당하게 하고 나머지는 linear attention, local attention, state-space 계열 업데이트처럼 더 저렴한 메커니즘으로 대체하는 것입니다.

즉, 모든 레이어가 동일한 수준으로 “멀리 보고 정확하게 찾는” 일을 할 필요는 없다는 판단입니다.

최근 공개된 open-weight 모델들은 이 흐름을 꽤 선명하게 보여줍니다. MiniMax-Text-01은 7개의 Lightning Attention 레이어 뒤에 1개의 Softmax attention 레이어를 두는 hybrid stack에 MoE를 결합해 매우 긴 컨텍스트를 지원했습니다 [[4]](#ref-4). Kimi Linear는 여기서 한 발 더 나아가 **Kimi Delta Attention (KDA)** 라는 gated-delta 계열 linear attention을 도입하고, 이를 global MLA layer와 3:1 비율로 섞었습니다. 모델 카드에서는 1M context에서 KV cache를 최대 75% 줄이고 decoding throughput을 최대 6배 높인다고 보고합니다 [[5]](#ref-5). Qwen3.6-35B-A3B도 같은 방향을 더 작은 open-weight 패키지로 보여줍니다. 총 35B 파라미터 중 3B만 활성화하고, `3 x Gated DeltaNet + 1 x Gated Attention` 패턴을 반복하며, 각 attention block 뒤에 MoE를 붙이고, multi-token prediction과 native 262K context를 제공합니다. YaRN 확장을 쓰면 약 1M token까지 늘릴 수 있습니다 [[6]](#ref-6). 2026년 4월 open model로 공개된 Ling-2.6-flash도 같은 흐름의 최신 사례입니다. 기존 GQA 설계를 1:7 MLA + Lightning Linear hybrid로 바꾸고 highly sparse MoE와 결합해, 단순히 chain-of-thought를 더 길게 쓰는 대신 agent-style inference를 더 빠르고 토큰 효율적으로 만드는 쪽을 겨냥합니다 [[7]](#ref-7).

중요한 업데이트는 softmax attention이 사라졌다는 뜻이 아닙니다. 오히려 최근 패턴은 **선택적 full attention** 에 가깝습니다. 소수의 global attention layer는 고정밀 retrieval과 composition checkpoint로 남기고, 대부분의 장문 상태 전달은 linear attention layer가 맡는 식입니다. 그래서 hybrid linear attention은 이제 특이한 연구 아이디어라기보다, agentic workload와 long-context serving을 위한 실제 production architecture 후보로 보이기 시작했습니다.

### 2. KV Cache 압축과 메모리 친화적 어텐션
자기회귀 모델의 서빙 비용은 계산량만으로 설명되지 않습니다. 생성이 길어질수록 KV cache가 커지고, 이 캐시를 계속 읽고 쓰는 메모리 이동 비용이 매우 중요해집니다.

DeepSeek-V3의 **Multi-head Latent Attention(MLA)** 은 토큰마다 압축된 내용과 위치 정보를 담은 키를 따로 보관합니다. 각 헤드는 같은 캐시에 자신만의 투영을 적용합니다. [4,096토큰 요청의 용량을 계산하고, 캐시를 두 가지 방식으로 읽어 같은 결과가 나오는지 확인해 봅시다](#mla-cache-example) [[1]](#ref-1).

### 3. 피드포워드 스택의 MoE
또 다른 큰 레버는 feed-forward block입니다. dense FFN은 전체 파라미터를 항상 활성화하지만, **Mixture of Experts (MoE)** 는 토큰마다 일부 expert만 활성화합니다.

MoE의 매력은 분명합니다. dense 모델과 같은 비용을 모두 치르지 않으면서 총 용량은 크게 늘릴 수 있습니다. 다만 그 대가로 routing, load balancing, expert parallelism, 통신 오버헤드 같은 시스템 문제가 핵심 이슈로 올라옵니다. 다시 말해, 계산 비용 일부를 시스템 복잡도로 바꾸는 선택이라고 볼 수 있습니다.

### 4. 멀티 토큰 예측 (Multi-Token Prediction, MTP)
보통 언어 모델은 다음 토큰 하나만 예측하도록 학습됩니다. **Multi-Token Prediction (MTP)** 은 이 목표를 바꾸어, 여러 미래 위치를 한 번에 예측하게 합니다.

이 방식은 학습 효율을 높일 수 있고, 이후 추측 해독(speculative decoding) 같은 빠른 서빙 경로와도 잘 연결됩니다. 아키텍처는 레이어 구조만이 아니라 학습 목표까지 포함한다는 점을 보여주는 좋은 예입니다.

### 5. 광학적 컨텍스트 압축 (Optical Context Compression)
앞의 예시들은 토큰이 이미 Transformer 안에 들어온 뒤, 모델이 그 토큰을 어떻게 처리할지 바꿉니다. 그런데 최근에는 더 낯선 질문도 등장했습니다. 긴 텍스트 컨텍스트가 애초에 긴 1D token sequence로 모델에 들어가야만 할까요?

DeepSeek-OCR은 이 질문을 보여주는 좋은 사례입니다. 이름만 보면 단순히 "더 좋은 OCR"처럼 보이지만, 더 흥미로운 지점은 **contexts optical compression** 입니다. 텍스트가 많은 문서를 2D 시각 표현으로 매핑하고, page image를 적은 수의 vision token으로 인코딩한 뒤, language decoder가 그 내용을 복원하거나 추론하는 방식입니다 [[3]](#ref-3). 텍스트가 빽빽한 한 페이지를 수천 개의 text token으로 넣는 대신, vision encoder를 통과시켜 더 적은 token budget으로 표현할 수 있다는 발상입니다.

직관은 어렵지 않습니다. 긴 문단을 스크린샷으로 찍으면 줄바꿈, 표, 수식, 공간적 배치가 하나의 압축된 물체처럼 보존됩니다. DeepSeek-OCR은 이 직관을 모델 pipeline으로 바꿉니다.

1. 문서를 image-like 2D signal로 렌더링하거나 입력받습니다.
2. vision encoder인 DeepEncoder가 page를 제한된 수의 vision token으로 압축합니다.
3. DeepSeek3B-MoE-A570M language decoder가 압축된 표현을 디코딩합니다.
4. OCR text, markdown, layout-aware output, document-grounded response를 생성합니다.

이 말은 시스템이 text를 버렸다는 뜻은 아닙니다. 출력은 여전히 text이고, decoder도 language model입니다. 달라지는 부분은 입력 경계입니다. text를 바로 token sequence로 넣기 전에, 광학적으로 압축할 수 있는 대상으로 다루는 것입니다.

실무적으로 중요한 값은 compression ratio입니다.

$$
r = \frac{N_{\text{text tokens}}}{N_{\text{vision tokens}}}
$$

예를 들어 원래 2,000개의 text token을 먹는 문서를 200개의 vision token으로 표현할 수 있다면 $r = 10$입니다. DeepSeek-OCR 논문은 이 비율이 대략 $10\times$ 미만일 때 OCR precision이 약 97% 수준을 유지하고, $20\times$ 근처에서는 약 60%까지 떨어진다고 보고합니다 [[3]](#ref-3). 핵심은 바로 이 trade-off입니다. Optical compression은 context length를 벌어줄 수 있지만, text tokenization의 무손실 대체재는 아닙니다.

기술적으로 보면 이 접근은 부담의 일부를 sequence modeling에서 visual representation learning으로 옮깁니다. Encoder는 글자 모양, reading order, table structure, layout geometry를 보존하면서도 일반 OCR 또는 문서 파싱 pipeline보다 훨씬 적은 token을 만들어야 합니다. Decoder는 이 압축된 visual token을 다시 정확한 symbol이나 structured text로 바꿔야 합니다. 이것은 일반 image captioning과 다릅니다. 코드, 수식, 법률 문서, 표에서는 한 글자나 한 숫자 오류도 치명적일 수 있기 때문입니다.

더 깊은 함의는 "context length"가 더 이상 attention만의 문제가 아니라는 점입니다. Long-context system은 여러 층위에서 공략할 수 있습니다.

- hybrid linear attention으로 긴 token sequence 위의 attention을 더 싸게 만들기;
- generation 중 KV cache를 더 싸게 만들기;
- MoE로 computation을 sparse하게 routing하기;
- 여러 token을 한 번에 예측하거나 검증하기;
- 또는 입력 표현이 token sequence가 되기 전에 압축하기.

Optical context compression은 마지막 범주에 속합니다. 스캔 문서, PDF, 표, 영수증, 역사적 아카이브, layout-rich corpus에는 매력적입니다. 반면 source code patch, formal proof, 계약서, safety-critical numeric table처럼 정확한 byte-level fidelity가 중요한 workload에서는 더 조심스럽습니다. 실제 production system이라면 confidence scoring, text OCR로의 selective fallback, 원본 document image와의 verification을 함께 두는 편이 안전합니다.

### GLM-5.2: attention 결과가 아니라 indexer를 공유한다

GLM-5.2의 흥미로운 장문 설계는 **IndexShare**입니다. Sparse attention에는 과거의 어느 위치에 비싼 attention을 쓸지 결정하는 indexer가 필요합니다. GLM-5.2는 네 개 레이어 묶음에서 학습된 sparse indexer 하나를 공유합니다. 선택된 위치를 처리하는 attention projection은 각 레이어가 따로 가질 수 있고, 공유되는 것은 검색 *결정 장치*입니다. Z.ai는 1M-token 경로에서 token당 FLOPs가 2.9배 줄었다고 보고합니다 [[8]](#ref-8).

설정 파일에는 의도적인 단계 구성이 드러납니다. 처음 세 dense layer가 초기 표현을 만들고, 이후 레이어는 항상 켜지는 shared expert 하나와 routed expert 8개를 선택하는 fine-grained MoE를 사용합니다. MTP layer 하나는 speculative decoding용 draft signal을 만듭니다. 출시 글은 IndexShare/KVShare, rejection sampling, end-to-end total-variation objective로 평균 accept length가 4.56에서 5.47 token으로 늘었다고 설명합니다 [[8]](#ref-8). 이는 accepted draft length가 약 20% 늘었다는 뜻이지, end-to-end latency가 자동으로 20% 줄었다는 뜻은 아닙니다. Verification, memory traffic, batching, scheduler overhead가 남아 있기 때문입니다.

Post-training pipeline도 눈여겨볼 만합니다. Z.ai는 열 개가 넘는 expert policy를 약 이틀 안에 합치는 parallel on-policy distillation, 압축된 장기 trajectory를 위한 critic-based PPO, 길이가 다른 trajectory의 불균형을 다루는 token-level loss normalization, 두 단계 anti-reward-hacking filter를 설명합니다. 의심스러운 tool call을 차단할 때 episode를 버리지 않고 dummy result를 반환해 rollout을 계속합니다. 덕분에 실패 뒤 회복하는 행동 자체가 학습 데이터가 됩니다 [[8]](#ref-8). 이제 “agent model”은 아키텍처 하나가 아니라 rollout compression, verifier, serving kernel까지 결합한 시스템입니다.

### Kimi K3: 공개된 세 가지 아이디어와 중요한 분모

K3는 recurrent/linear 경로인 Kimi Delta Attention, 레이어 사이 표현을 attention 방식으로 섞는 Attention Residuals, Stable LatentMoE를 결합합니다. Router는 896개 expert 중 16개를 선택합니다. 이는 **expert pool의 약 1.8%**이지, 전체 parameter의 1.8%만 활성화된다는 증거가 아닙니다. Embedding, attention, shared component, expert 크기를 알아야 진짜 active-parameter ratio를 계산할 수 있습니다. Moonshot은 K2 대비 2.5배 높은 scaling efficiency를 보고합니다. 이후 공개된 technical artifact로 architecture와 systems claim을 검사할 수 있게 됐지만, 정확한 training-data mixture는 여전히 미공개입니다 [[11]](#ref-11) [[14]](#ref-14).

K3에는 흥미로운 제품 제약도 있습니다. Reasoning session에서는 thinking history를 보존해야 하며, 대화 도중 mode를 바꾸면 trajectory가 불안정해질 수 있습니다. 대화 상태가 UI 장식이 아니라 inference contract의 일부라는 뜻입니다.

### Qwen3.8: 아티팩트가 도착하면 주장의 경계도 바뀐다

Qwen3.8은 출시 과정 자체가 근거 규율을 가르쳐 준다는 점에서 유용합니다. Preview 시점에는 Alibaba가 2.4T 모델과 향후 open weights만 발표했으므로, 내부 구조는 Qwen3.7의 세부 정보를 물려받지 않고 **미공개**로 남겨야 했습니다 [[13]](#ref-13). 이후 Qwen3.8-2.4T-A95B repository가 공개되면서 주장의 경계가 바뀌었습니다. 이제 weights와 configuration은 total/active parameter와 native/확장 문맥의 구분을 뒷받침합니다 [[15]](#ref-15). 그러나 정확한 corpus mixture와 전체 filtering·post-training recipe까지 공개된 것은 아닙니다. 살아 있는 기술 비교는 미래 약속이 처음 올라온 날이 아니라, 실제 artifact가 바뀐 날에 맞춰 수정되어야 합니다.

### 자기회귀 생성과 decoder-only는 같은 말이 아니다

V4.1 Flash는 causal encoder 뒤에 decoder를 둡니다. 모델 카드는 전역 decoder KV를 decoder 각 레이어에서 별도로 만드는 대신 encoder의 최종 상태에서 투영한다고 설명합니다 [[16]](#ref-16). 이는 T5의 양방향 source encoder와 다르면서도 텍스트를 자기회귀로 생성합니다. 출력 확률의 분해 방식, 어텐션의 가시 범위, prefill/decode 실행 경로는 별도 설계 선택입니다.

### 조건부 메모리는 다른 희소성 축이다

Engram은 토큰 조건의 lookup을 MoE 연산과 함께 사용하는 방향을 연구합니다 [[21]](#ref-21). 결정적인 주소는 미리 가져오기를 가능하게 하지만 lookup에도 저장 용량·host 대역폭·전송 겹침·miss 처리가 필요합니다. RAG의 외부 갱신 가능한 문서 index와도 다릅니다. 배포 비교에서는 신경망 연산, lookup 저장 공간, KV 상태, 통신을 나누어 봅니다. 활성 파라미터 비율 하나로 네 항목을 설명할 수 없습니다.

### 호스팅 Qwen3.8과 다운로드한 모델은 별도 아티팩트다

로컬 Qwen3.8 설정은 `max_position_embeddings: 262144` 를 선언합니다 [[22]](#ref-22). 모델 카드는 native 262,144 위치와 1,010,000 토큰까지의 확장을 설명하며, 호스팅 Qwen3.8-Max는 추가 기능과 다른 기본 문맥을 갖습니다 [[15]](#ref-15). 스케일링 설정을 고정하고 목표 길이에서 검색·여러 문서 추론·위치 민감도·메모리·지연을 평가합니다. “1M 문맥”은 설정과 평가에 대한 주장이지 모든 서빙 경로가 자동으로 물려받는 보장이 아닙니다.

## DeepSeek-V3의 어텐션 층은 다음 토큰을 위해 무엇을 보관할까요?

한 요청에서 이미 4,096토큰을 처리했다고 합시다. DeepSeek-V3는 토큰마다 키와 값의 내용을 압축한 512차원 벡터와, 회전 위치 임베딩(RoPE)을 적용한 64차원 키를 보관합니다. 한 층의 헤드 128개가 이 두 벡터를 공유합니다. 각 원소를 2바이트로 저장한다고 가정하면 **요청 하나, 층 하나** 에서 캐시에 필요한 용량은 $4096 \times (512+64) \times 2 = 4{,}718{,}592$바이트, 즉 **4.5 MiB** 입니다. 압축된 내용만 세면 위치 키가 차지하는 0.5 MiB가 빠집니다. 두 벡터의 정의와 차원은 DeepSeek-V3 기술 보고서 2.1.1절과 4.2절에서 확인할 수 있습니다 [[1]](#ref-1).

같은 벡터를 읽어도 헤드마다 다른 결과가 나오는 이유는 무엇일까요? 행렬 $C$의 각 행에는 토큰 하나의 압축된 내용이 들어 있습니다. 한 헤드가 사용하는 키·값 투영 행렬을 $U_K$, $U_V$, 내용 쿼리를 $q$라고 합시다. 모든 키를 먼저 복원해 $(CU_K)q$를 계산해도 되고, 쿼리를 먼저 투영해 $C(U_Kq)$를 계산해도 내용 점수는 같습니다. 여기에 위치 점수를 더한 뒤 스케일링과 소프트맥스를 적용합니다. 이렇게 얻은 가중치가 $a$라면, 값을 복원해 가중합을 구한 $a^T(CU_V)$와 압축 벡터의 가중합을 먼저 구한 $(a^T C)U_V$도 같습니다.

> **CPU 예제의 범위.** 패딩이 없는 시퀀스 하나에 토큰을 한 자리씩 추가합니다. FP32 텐서로 학습된 투영과 RoPE를 거친 값을 대신하고, 헤드마다 두 계산 순서의 출력을 대조합니다. 실제 모델의 가중치, 최종 출력 투영, 메모리 할당 비용과 최적화 커널은 생략했습니다. `torch.cat`으로 행을 추가할 때는 텐서 복사가 일어납니다.

```python
import math
import torch

rng = torch.Generator().manual_seed(7)

def sample(*shape):
    return torch.randn(*shape, generator=rng, dtype=torch.float32, device="cpu")

# Two heads, each projecting a 3-coordinate latent to 4 content coordinates.
key_up = sample(2, 3, 4)
value_up = sample(2, 3, 4)
latent = sample(0, 3)
position_keys = sample(0, 2)
scale = math.sqrt(4 + 2)

for _ in range(4):
    latent = torch.cat((latent, sample(1, 3)))
    position_keys = torch.cat((position_keys, sample(1, 2)))
    for wk, wv in zip(key_up, value_up):
        query = sample(4)
        position_scores = position_keys @ sample(2)
        keys, values = latent @ wk, latent @ wv
        weights = (((keys @ query) + position_scores) / scale).softmax(dim=0)
        reference = weights @ values

        latent_query = wk @ query
        weights = ((latent @ latent_query + position_scores) / scale).softmax(dim=0)
        result = (weights @ latent) @ wv
        torch.testing.assert_close(result, reference, atol=1e-5, rtol=1e-5)

print(tuple(latent.shape), tuple(position_keys.shape), latent.nbytes + position_keys.nbytes)
```

출력은 `(4, 3) (4, 2) 80`입니다. 네 위치에 각각 압축된 내용 세 값과 위치 키 두 값을 FP32로 저장해서 총 80바이트가 됩니다. 비교를 위해 복원한 키와 값은 임시로 사용합니다. 토큰 네 개를 차례로 추가하면서 두 헤드의 출력을 매번 대조하므로, 여덟 번의 검사를 모두 통과해야 이 숫자가 출력됩니다.

## GLM-5.4: 레이어 재사용으로 깊이와 용량을 구분하기

**As of 2026-11-24.** Z.ai의 11월 23일 발표는 사전 학습된 GLM-5 기반 모델을 변환한 **750B 규모** 의 Loop Transformer를 설명합니다. **공유 레이어 28개를 두 번 실행** 합니다 [[37]](#ref-37). 정확한 전체·활성 매개변수 수, 전체 학습 데이터 혼합, 향후 공개할 가중치의 라이선스는 미공개입니다.

수정한 초고에 같은 편집 절차를 다시 적용한다고 생각해 봅시다. 절차는 재사용하지만 두 번째 적용은 달라진 표현을 입력으로 받으며, 여전히 작업이 필요합니다. 간단한 실행 횟수 식으로 이 차이를 구분할 수 있습니다. 원래 레이어 수를 $L$, 공유 블록의 레이어 수를 $k$, 반복 횟수를 $r$이라고 하겠습니다. 나머지 레이어를 한 번씩 실행한다면, 한 번의 순전파에서 실행하는 레이어의 총횟수는 다음과 같습니다.

$$
D = (L-k) + rk = L + (r-1)k.
$$

$D$는 별도로 저장하는 레이어 가중치 수가 아니라 실행 횟수입니다. 공개된 $k=28$, $r=2$를 대입하면 $L+28$이지만, 이것으로 모델의 전체 레이어 수가 밝혀지는 것은 아닙니다. FLOP 배수도 바로 계산할 수 없습니다. 어텐션, 전문가 라우팅, 게이트, 캐시 읽기, 커널 실행의 비용이 서로 다르기 때문입니다. 행렬 재사용은 그 행렬의 중복 저장을 줄이지만, 다시 적용하는 연산까지 없애지는 않습니다.

발표가 설명하는 지원 장치는 세 가지입니다 [[37]](#ref-37).

| 장치 | 공개된 동작 |
|---|---|
| 반복별·토큰별 게이트 | 잔차 갱신량을 제어해 반복 연산을 안정화 |
| 전역 KV 공유와 지역 윈도 | 두 번째 실행은 첫 실행의 희소 KV를 재사용하고 자체 슬라이딩 윈도 KV도 유지 |
| 희소 인덱스 재사용 | 두 번째 실행은 첫 실행에서 고른 검색 위치를 재사용 |

공개된 통제 실험은 **30B 모델** 에서 **학습 연산을 약 10% 더 사용** 한 비교이며, **200K 문맥 SFT** 후 추론 모드를 켜서 평가했습니다. 플래그십의 벤치마크 결과가 아닙니다. 반복 횟수를 적응적으로 조절하는 방식은 향후 연구로 남아 있습니다 [[37]](#ref-37). 자체 평가에서는 도구 접근, 추론 강도, 문맥, 중단 규칙을 고정하고 과업 성공률, 전체 생성 토큰, 꼬리 지연 시간, 예산 소진을 측정하세요. 출력 토큰이 줄어도 내부 연산이 감소했다고 단정할 수 없습니다.

**접근 범위:** Coding Plan·ZCode·Z.ai Chat은 사용 가능하며, 일반 종량제 API와 가중치는 공개 예정입니다 [[37]](#ref-37). Coding Plan 통합 문서는 **1M 문맥**, 이미지 입력, low/high/max 추론 강도를 명시하며, 추론을 끄는 설정도 low로 변환합니다 [[38]](#ref-38). 이는 다운로드 가능한 구성 파일이 아니라 호스팅 서비스의 사용 조건입니다. [17.6절](/ko/chapter-17/commercial-model-benchmarks)에서 공개 상태와 평가 근거를 따로 추적합니다.

### 토큰 위치는 하나인데 왜 캐시 항목은 두 개일까요?

2026-11-25에 확인한 Z.ai의 구조 설명에 따르면, 두 번째 실행은 한 토큰 위치에서 첫 실행의 표현과 지역 윈도에서 갱신한 표현을 함께 참조할 수 있습니다 [[43]](#ref-43). 첫 실행의 인덱스가 **1, 5, 7번** 위치를 고르고 두 번째 실행의 지역 윈도가 **6, 7번** 위치를 포함한다고 가정해 봅시다. 위치 번호는 계산을 위해 정한 예시입니다.

| 키와 값을 가져오는 곳 | 이 쿼리가 읽는 토큰 위치 |
| --- | --- |
| 첫 실행에서 재사용하는 항목 | 1, 5, 7 |
| 두 번째 실행의 지역 윈도 | 6, 7 |

쿼리는 **네 위치에서 다섯 항목** 을 읽습니다. 7번 위치라는 이유로 최신 항목 하나만 남기면 첫 실행에서 만든 표현을 잃습니다. 여기서 센 것은 쿼리 한 번이 읽는 항목 수입니다. 상주 메모리까지 계산하려면 각 버퍼의 크기와 보관 기간도 알아야 합니다. [SmolLM2의 밀집 캐시 실측](/ko/chapter-12/kv-cache-management/#kv-batch-padding)에서는 이와 달리 모든 층이 배치에 할당된 자리마다 키 하나와 값 하나를 저장합니다.

### 디코더 레이어가 24개인데 어떻게 72번 실행할까?

11월 20일 Thinking Machines Lab은 반복 횟수를 바꿀 수 있는 연구 모델의 가중치를 공개했습니다. 이 모델(`TML-d24-varloop-research`)은 추론할 때 디코더의 가운데 블록을 몇 번 실행할지 정할 수 있습니다. 2026-11-25 기준 공개 설정에는 텍스트 레이어가 24개이고 기본 반복 횟수는 세 번입니다. Python 표준 라이브러리로 설정 파일 하나만 받아 실행 순서를 확인해 봅시다. [[44]](#ref-44) [[45]](#ref-45)

```python
import json
from urllib.request import urlopen

repo = "thinkingmachines/TML-d24-varloop-research"
revision = "91a57fe2b779bbd12c0f74d1f518cbd5b84e8d0d"
url = f"https://huggingface.co/{repo}/resolve/{revision}/config.json"
with urlopen(url, timeout=15) as response:
    config = json.load(response)["text_config"]

layers = list(range(config["num_hidden_layers"]))
loop = config["loop_config"]
start, end = loop["core_start"], loop["core_end"]
for passes in (1, loop["num_passes"], 5):
    schedule = layers[:start] + layers[start:end] * passes + layers[end:]
    print(passes, len(schedule), len(set(schedule)))
```

세 열은 차례로 반복 횟수, 토큰 하나가 거치는 레이어 수, 서로 다른 디코더 레이어 수입니다. 출력은 `1 24 24`, `3 48 24`, `5 72 24`입니다. 0~5번 레이어를 한 번 거친 뒤 6~17번을 반복하고, 마지막으로 18~23번을 한 번 거칩니다. 다섯 번 반복하면 가운데 블록에서만 레이어를 60번 실행합니다. 가중치를 재사용해도 디코딩에 필요한 메모리는 늘어납니다. Transformers 구현에서는 반복이 한 번 늘 때마다 12개 레이어에 캐시 항목을 따로 배정합니다. [[46]](#ref-46)

한 번 반복했을 때와 다섯 번 반복했을 때의 정답률을 비교하면 무엇을 알 수 있을까요? 가중치는 같지만 학습 때 가장 많이 접한 조건은 세 번 반복하는 경우입니다. 연구진은 중간 학습 후반에 한 번부터 다섯 번까지의 반복 횟수를 1:2:6:2:1 비율로 뽑았고, 사후 학습에서는 세 번으로 고정했습니다. 같은 문제를 풀게 하면 **이 체크포인트에서** 깊이를 바꿨을 때의 효과를 볼 수 있습니다. 처음부터 어느 깊이로 학습하는 편이 나을지는 별도의 실험이 필요합니다. [[44]](#ref-44)
