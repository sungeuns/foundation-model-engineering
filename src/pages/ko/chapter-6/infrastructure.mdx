# 6.4 인프라

분산 학습은 연산·메모리·통신·데이터 공급·복구 중 가장 느린 유효 경로에 제약됩니다. accelerator를 늘려도 다른 rank를 기다리는 시간이 커지면 용량은 늘고 효율은 낮아질 수 있습니다. 인프라 설계는 가장 큰 클러스터의 광고가 아니라 목표 모델·정밀도·병렬 배치·시퀀스 길이·작업량에서 출발합니다.

**2026-10-13 기준 설계 자료 확인.** 아래 사례는 hardware·network 계약을 설명하며 최신 제품 목록이나 제공사 성능 순위가 아닙니다.

## 1. Scale-up과 Scale-out

Scale-up은 비교적 빠른 공통 fabric 안의 device를 연결하고 scale-out은 node·큰 domain을 network로 연결합니다. 경계는 구현에 따라 다릅니다. rack이 큰 scale-up domain이어도 여러 device가 남으므로 분산 소프트웨어가 필요합니다.

| 참고 설계 | 공개된 특성 | 엔지니어링 경계 |
|---|---|---|
| GB200 NVL72 | Blackwell GPU 72개·Grace CPU 36개·액체 냉각·72-GPU NVLink domain [[1]](#ref-1) | switch fabric의 여러 device/rank이며 하나의 PyTorch device가 아님 |
| Meta의 2024년 설계 | 각각 RoCE·InfiniBand를 사용한 24,576-GPU 설계 둘 [[2]](#ref-2) | 보고한 배포의 근거이며 모든 트래픽에서 같은 동작을 입증하지는 않음 |
| TPU v5p | 공개된 3D torus와 topology를 고려한 slice [[3]](#ref-3) | slice shape·topology가 통신에 영향; 한 세대의 구성을 모든 TPU에 일반화하지 않음 |

NVIDIA의 NVLink 130 TB/s는 **시스템 집계 값** 이지 모든 rank 쌍이 동시에 사용할 수 있는 대역폭이 아닙니다 [[1]](#ref-1). 제공사의 처리량 배수는 workload 각주에 묶입니다. 다른 모델·배치·정밀도·지연 목표에 측정 없이 옮길 수 없습니다.

## 2. 병렬화에 fabric을 맞추기

Tensor parallel은 빈번하고 지연에 민감한 교환, data parallel은 gradient collective, expert parallel은 불균등한 all-to-all, pipeline parallel은 activation 전송·bubble·stage 편중을 만듭니다. 같은 fabric도 모델 배치에 따라 동작이 달라집니다.

RDMA는 모든 payload를 애플리케이션 CPU 복사로 처리하지 않고 이동할 수 있지만 설정·제어·완료 처리·혼잡은 남습니다. InfiniBand와 RoCE 어느 쪽도 모든 network 실패를 없애지는 않습니다. 흐름·혼잡 제어는 처리량을 높이면서 tail latency·blocking 문제를 만들 수도 있습니다.

실제 메시지 크기·collective 지연·겹침·link 활용도·혼잡·재시도·rank 편중·step 시간을 profile합니다. 단독 대역폭 검사뿐 아니라 장애·checkpoint 트래픽도 평가합니다. 빠른 peak link가 빠른 학습 작업을 입증하지는 않습니다.

## 3. 광 재구성과 topology

Optical circuit switching은 물리 경로를 바꾸고 일부 packet switching 비용을 줄일 수 있습니다. 시스템 전력이 0이 되거나 실패한 compute chip의 작업이 자동 대체되는 것은 아닙니다. transceiver·controller·냉각·예비 용량·routing/재구성 정책·job 복구는 여전히 필요합니다.

논리 torus·mesh는 배치 제약입니다. 지원하는 slice topology와 알고리즘 통신에 맞춰 rank를 할당합니다. device 수나 사용 가능한 link가 바뀌면 실행 중 mirror만 조정하는 대신 새 배치와 지원되는 재시작이 필요할 수 있습니다.

그림은 개념도입니다. 표시된 node 수·평면 배치는 제품의 실제 크기·배선이 아닙니다.

## 4. 전력·냉각은 측정한 예산이다

GPU 수만으로 site 전력 수요를 추정하지 않습니다. accelerator·CPU·메모리·network·storage·냉각·시설 overhead에 측정한 활용도와 여유를 더합니다. 전체 시설 전력과 accelerator 명목 전력은 다른 계획 값입니다.

학습 단계의 전력 수요는 함께 움직일 수 있지만 통신 중 모든 GPU가 쉬는 것은 아닙니다. 연산 겹침과 동시 job이 profile을 바꿉니다. 순간 부하·지속 열 특성·throttling·냉각수 조건·power cap 효과를 측정합니다. 배터리 buffering·스케줄 변경도 보편적 클러스터 파형을 가정하기보다 확인한 시설 요구를 해결해야 합니다.

## 5. 학습 인프라 계약

자원을 할당하기 전에 입력 모델/토크나이저/템플릿·불변 데이터 manifest·목적함수·혼합/필터 버전·그룹 분할·평가 격리를 기록합니다. 정밀도·sharding·재계산·시퀀스 길이·토큰 배치·활성 expert 가정·학습률 schedule·허용 장애/복구 동작을 명시합니다.

파라미터·gradient·optimizer 상태·activation·임시 버퍼·collective·로컬/원격 checkpoint·평가를 따로 계산합니다. 사후 학습 rollout이 있으면 data loader·verifier/sandbox 용량도 포함합니다. MoE 활성 연산은 총가중치 저장량이 아니며 긴 입력은 서빙 병목을 캐시 용량·전송으로 바꿀 수 있습니다.

토큰 정규화 학습/검증 손실·도메인 구간·nonfinite/overflow·gradient/activation norm·유효 토큰 처리량·분모를 명시한 MFU·데이터 대기·collective/straggler·메모리 여유·재구성 가능한 batch ID를 관측합니다. device uptime은 유효 학습 처리량이 아닙니다.

수치 오류·품질 저하·반복 link/device 실패·과열·복구 불가능 상태의 pause/abort 경계·책임자·관측 구간·hysteresis를 사전에 정합니다. sharded 모델/optimizer·scheduler·scaler/FP8 상태·전역 step/토큰 수·RNG·sampler/정확한 데이터 커서·데이터/토크나이저/config hash를 저장합니다. 원자적 게시에는 checksum·완료 표식이 필요하고, 보존·원격 복제는 로컬 node/rack 손실에도 살아남아야 합니다.

지원 world size에서 복원 훈련과 학습 연속성 동등성 검사를 합니다. 저장만 하고 복원하지 않은 checkpoint는 검증된 복구가 아닙니다. 승격할 아티팩트도 도메인·기존 역량 유지·안전·도구/형식·지연·비용·오류 기준을 짝지은 불확실성이나 근거 있는 표본 수로 통과하고, 정상 동작이 확인된 이전 묶음과 rollback 훈련이 필요합니다.

## 6. 실무적 결론

측정한 작업 병목과 복구 요구에 따라 인프라를 고릅니다. 큰 scale-up domain·조정한 scale-out fabric·topology를 고려한 accelerator slice는 다른 도구입니다. 가치는 목표 모델·장애 조건에서 지속하는 유효 작업량에 있습니다.

<summary>Quiz 1: 72-GPU NVLink domain에도 분산 소프트웨어가 필요한 이유는 무엇인가요?</summary>
*여러 device와 rank가 남기 때문입니다. 빠른 연결이 device 메모리·동기화·collective를 하나의 일반 PyTorch device로 바꾸지는 않습니다.*
</details>

<details>
<summary>Quiz 2: 집계 fabric 대역폭을 모든 device 쌍에 적용할 수 없는 이유는 무엇인가요?</summary>
*집계 값은 여러 link를 요약합니다. topology·경합·routing·동시 트래픽이 각 쌍과 collective를 제약합니다.*
</details>

<details>
<summary>Quiz 3: Dense 모델을 MoE로 바꾸면 network 조정이 달라질 수 있는 이유는 무엇인가요?</summary>
*expert dispatch가 기존 collective와 다른 메시지 크기·straggler 특성을 가진 불균등한 all-to-all을 만들기 때문입니다.*
</details>

<details>
<summary>Quiz 4: optical circuit switch가 제공하지 않는 것은 무엇인가요?</summary>
*전체 전력 overhead 제거·실패한 compute 용량 대체·topology와 상태 복구 없이 job 재개를 보장하지 않습니다.*
</details>

<details>
<summary>Quiz 5: 분산 checkpoint 복원을 훈련해야 하는 이유는 무엇인가요?</summary>
*저장 성공만으로 완전하고 호환되는 상태나 world-size 변경 지원이 입증되지 않습니다. 복원·학습 연속성 검사가 복구 계약을 확인합니다.*
</details>
