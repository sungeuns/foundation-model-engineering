# 14.4 RAG 오케스트레이션: 라우팅 및 에이전트

“구독을 갱신한 뒤 며칠 안에 취소할 수 있나요?”와 “지난번에 갱신한 제 구독, 지금 취소할 수 있나요?”는 비슷한 질문입니다. 첫 질문에는 현재 약관만 찾아도 답할 수 있습니다. 두 번째 질문에는 고객의 갱신 날짜도 필요합니다. 약관을 두 번 검색해도 그 날짜는 나오지 않습니다.

RAG 오케스트레이션은 질문에 필요한 자료를 정하고, 모델에 전달할 근거를 고르고, 검색을 멈출 시점을 결정하는 일입니다. 가상의 구독 서비스에서 이 세 가지 판단을 따라가 보겠습니다.

## 1. 쿼리 라우팅 (Query Routing)

일반적인 취소 기한을 묻는 고객에게는 약관을 찾아 줍니다. 본인의 갱신 건을 묻는 고객에게는 계정 기록도 읽어야 합니다. 오류 코드가 들어온 경우에는 또 다른 선택지가 있습니다. [앞 절](../advanced-retrieval/)에서는 의미 검색에서 놓친 식별자를 키워드로 찾는 예를 살펴봤습니다.

<a id="renewal-routing"></a>

### LLM 기반 라우팅

라우터 역할을 맡은 모델에는 `policy`, `my_renewal`, `clarify`처럼 선택할 수 있는 경로를 몇 개만 알려 줍니다. 모델이 경로를 제안하면 애플리케이션이 실행 가능 여부를 판단합니다. 모델이 `{"route":"my_renewal"}`을 반환해도 이 값만으로는 고객이 누구인지, 경로를 맞게 골랐을 확률이 얼마인지 알 수 없습니다.

다음 파이썬 코드는 모델의 응답 네 가지를 재현해 실행 계획을 만듭니다. 실제 서비스에서는 서버가 접근 권한을 확인한 결과를 함수에 넘깁니다. 계정 조회 도구는 로그인한 고객의 계정만 읽으며, 모델에서 계정 번호를 입력받지 않습니다.

```python
import json

def plan(reply, *, can_read_own_renewal):
    try:
        decision = json.loads(reply)
    except (TypeError, ValueError):
        return ("clarify",)

    if decision == {"route": "policy"}:
        return ("read_current_policy",)
    if decision == {"route": "my_renewal"}:
        if can_read_own_renewal:
            return ("read_current_policy", "read_own_renewal")
        return ("sign_in",)
    return ("clarify",)

for reply, allowed in [
    ('{"route":"policy"}', False),
    ('{"route":"my_renewal"}', False),
    ('{"route":"my_renewal"}', True),
    ('{"route":"my_renewal","account":"other"}', True),
]:
    print(plan(reply, can_read_own_renewal=allowed))
```

첫 번째 응답에서는 약관만 조회합니다. 두 번째와 세 번째 응답은 같지만, 방문객에게는 `('sign_in',)`을 돌려주고 조회 권한이 있는 고객에게는 약관과 갱신 기록을 모두 읽는 계획을 돌려줍니다. 마지막 응답에는 허용하지 않은 필드가 있어서 결과가 `('clarify',)`입니다. 모델이 답변을 거절하거나, 등록되지 않은 경로를 고르거나, JSON 형식을 지키지 못한 경우에도 대체 경로가 필요합니다. 형식이 맞아도 질문과 무관한 경로를 고를 수 있습니다.

### 라우팅은 단순 분류가 아니라 예산 배분 문제다

개인 갱신 건을 묻는 질문이 일반 약관 경로로 들어갔다고 해 봅시다. 취소 기한이 며칠인지는 찾았지만 갱신 날짜를 모르니, 고객에게 “지금 취소할 수 있다”고 답할 근거는 없습니다. 라우터를 평가할 때는 질문마다 어떤 자료가 필요한지 먼저 표시합니다. 개인 질문에서 계정 조회를 빠뜨린 횟수와 일반 질문에서 불필요하게 로그인을 요구한 횟수를 따로 세세요. 답변 한 건에 든 조회 횟수와 고객이 답을 받을 때까지 걸린 시간도 함께 측정할 수 있습니다.

## 2. 컨텍스트 관리 및 "Lost in the Middle" 현상

두 곳에서 약관 한 구절과 갱신 기록을 가져왔습니다. 모델의 문맥 창이 2,048토큰이고, 지시문과 메시지 형식에 448토큰, 질문과 이전 대화에 256토큰을 쓴다고 합시다. 답변용으로 256토큰을 남기면 **근거에 쓸 수 있는 양은 1,088토큰** 입니다. 약관에 640토큰, 계정 기록에 128토큰을 쓰고 나면 320토큰이 남습니다. 여기에 512토큰짜리 FAQ까지 넣으면 192토큰을 초과합니다. 연습용으로 정한 숫자이므로 실제 서비스에서는 운영 중인 토크나이저와 메시지 템플릿으로 길이를 재야 합니다.

### "Lost in the Middle" 현상 [[1]](#ref-1)

Liu 등의 연구에서는 여러 문서를 읽고 답하는 문제에서 정답이 담긴 문서의 위치를 바꾸고, 키로 값을 찾는 문제에서는 목표 키의 위치를 바꿨습니다. 일부 모델과 실험 조건에서 근거가 가운데에 있을 때 정확도가 낮아졌습니다. 구독 서비스에서도 질문과 나머지 문서, 전체 길이를 그대로 두고 같은 약관 구절을 처음·가운데·끝에 놓아 보세요. 답이 맞는지와 인용한 구절이 그 답을 뒷받침하는지를 함께 확인하면 어느 배치가 유리한지 알 수 있습니다. [[1]](#ref-1)

### 컨텍스트 조립도 하나의 정책 계층이다

배경 자료를 넣기 전에 갱신 기록이 들어갈 자리를 남겨 둡니다. 약관을 줄였다면 요약문에도 갱신과 첫 구매의 차이가 남아 있는지 확인하세요. 취소 기한이 며칠인지는 그대로인데 어느 거래에 그 기한이 적용되는지가 달라질 수 있습니다. 나중에 오답의 원인을 찾을 수 있도록 실제로 전달한 약관 버전과 구절 식별자를 기록합니다.

## 3. 에이전틱 RAG (Agentic RAG): 선형 파이프라인을 넘어

필요한 자료가 약관과 갱신 기록으로 정해져 있으면 접근 권한을 확인한 뒤 두 곳을 바로 조회하면 됩니다. 앞에서 얻은 결과에 따라 다음 조회 대상이 달라질 때 검색을 반복할 이유가 생깁니다.

### ReAct 프레임워크 (Reasoning + Acting)

ReAct는 추론과 행동을 번갈아 수행해 관찰 결과를 다음 행동에 반영합니다. [[2]](#ref-2) 약관에 “제휴사를 통해 구독한 고객에게는 제휴사의 약관이 적용된다”고 쓰여 있다고 해 봅시다. 권한을 확인하고 읽은 갱신 기록에 제휴사 P가 나오면 다음에는 P의 현재 약관을 찾습니다. 직접 구독한 고객이라면 앞에서 읽은 약관으로 답할 수 있어 이 조회를 생략합니다.

### 에이전틱 RAG에는 중단 조건이 필요하다

이 예에서는 질문 한 건에 세 번까지만 조회할 수 있다고 정해 봅시다. 약관과 갱신 기록을 읽는 데 두 번을 썼으니 P의 약관을 찾을 기회는 한 번 남았습니다. 세 번째 조회에서도 예전 약관만 나오면, 현재 적용되는 규정을 확인하지 못했다고 고객에게 알리고 상담 연결을 제안합니다. 처음과 같은 검색을 반복해도 판단에 필요한 정보는 늘지 않습니다. 검색을 멈춘 이유와 주어진 횟수 안에서 근거를 갖춰 답한 비율을 기록하세요.

## 4. 요약

갱신 질문에 대한 답이 틀렸다면 세 군데를 짚어 볼 수 있습니다. 필요한 자료를 조회하도록 경로를 골랐는지, 약관의 예외 조항과 갱신 날짜가 프롬프트에 들어갔는지, 마지막으로 인용한 규정이 이 고객에게 적용되는지 확인합니다. 인용까지 달았는데 답이 틀린 경우는 [환불 약관 사례](../rag-failure-modes-and-operational-design/#trace-a-rag-answer)에서 단계별로 추적할 수 있습니다. [다음 절](../graphrag-and-ontology/)에서는 여러 개체 사이의 관계를 따라가야 근거를 찾을 수 있는 문제를 다룹니다.

<details>
<summary>Quiz 2: 모델이 올바른 JSON 형식으로 개인 갱신 경로를 선택했습니다. 이 결정을 얼마나 믿을 수 있는지 어떻게 평가할까요?</summary>
*각 질문에 필요한 자료를 미리 표시해 두고 모델이 고른 경로와 대조합니다. 표현이 비슷한 일반 질문과 개인 질문을 모두 포함합니다. JSON에 들어 있는 경로 이름만으로는 정답 확률을 알 수 없습니다.*
</details>

<details>
<summary>Quiz 3: 근거를 넣을 자리가 320토큰 남았는데 FAQ가 512토큰입니다. 어떻게 할까요?</summary>
*그대로 넣으면 192토큰을 초과합니다. 약관과 계정 기록만으로 답할 수 있으면 FAQ는 뺍니다. 꼭 필요한 예외 조항이 있다면 해당 구절만 추려서 전체 길이를 다시 잽니다.*
</details>

<details>
<summary>Quiz 4: 세 번째 조회에서 이미 효력이 끝난 제휴사 약관만 나왔습니다. 고객에게 어디까지 말할 수 있을까요?</summary>
*제휴사를 통한 구독이라는 사실과 현재 적용되는 취소 규정을 확인하지 못했다는 점을 알려 주고 상담 연결을 제안할 수 있습니다. 예전 기한을 근거로 지금도 취소할 수 있다고 답할 수는 없습니다.*
</details>
