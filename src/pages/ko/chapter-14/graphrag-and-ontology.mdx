# 14.5 GraphRAG 및 온톨로지

한 엔터프라이즈 어시스턴트가 다음과 같은 질문을 받았다고 생각해 봅시다. *"우리가 라이선스를 받은 모델을 만든 스타트업을 인수한 회사의 CEO는 누구인가?"* 벡터 검색기는 스타트업, 인수, CEO가 등장하는 문서 조각들을 어느 정도 찾아올 수는 있습니다. 하지만 정답에 이르는 관계 자체를 따라가지는 못할 수 있습니다. 유사도 순위만으로는 찾은 회사·인수·CEO가 같은 관계 경로에 속한다는 조건을 명시적으로 강제하지 않기 때문입니다.

이 차이는 중요합니다. 실제 현업의 많은 질문은 "비슷한 문단을 찾아줘"가 아니라 엔티티와 엣지를 따라가야 하는 문제이기 때문입니다. 소유 관계 추적, 장애 타임라인 분석, 의존성 출처 파악, 계약 관계 탐색, 코퍼스 전체의 주제 파악이 모두 여기에 속합니다. **지식 그래프(Knowledge Graph, KG)** 는 이런 관계를 명시적으로 나타냅니다. 그래프를 결합한 검색은 텍스트 검색과 함께 간선을 활용할 수 있습니다. 벡터 검색을 반드시 대체해야 하는 기술이 아니라 평가할 선택지입니다.

## 1. 언제 GraphRAG가 운영 비용을 정당화하는가

GraphRAG는 일반적인 벡터 RAG보다 운영 비용과 복잡성이 높기 때문에, 그만한 값을 해야 합니다. 다음과 같은 트래픽이 많을 때 특히 유리합니다.

- **다중 홉 질문:** 문서 사이의 관계를 따라가야 정답이 나오는 경우
- **전역 요약:** 특정 passage가 아니라 코퍼스 전체의 구조와 주제를 묻는 경우
- **출처 민감 워크플로우:** 답이 어떻게 조립되었는지를 보여 줘야 하는 경우

반대로 사용자 질문의 대부분이 "문서 어디에 X가 적혀 있나?"에 가깝다면, 일반적인 벡터 RAG가 더 싸고 단순한 선택인 경우가 많습니다. GraphRAG는 청크 자체보다 관계와 커뮤니티 구조가 답의 품질을 결정할 때 더 적합합니다.

## 2. 온톨로지와 추출 스키마

온톨로지는 엔터티의 유형, 관계와 의미 제약을 정의합니다. RDF/OWL과 property graph는 서로 다른 표현 선택이며, LLM을 사용한다고 스키마 설계나 관리가 사라지지는 않습니다.

LLM은 텍스트에서 관계 후보를 제안할 수 있습니다. 각 후보에는 원본 문서·구절, 추출기 버전, 유효 시간, 접근 권한을 연결해야 합니다. 형식 검사를 통과한 관계도 사실과 다를 수 있습니다. 엔터티 병합은 이름이나 임베딩 유사도만으로 확정하지 말고 식별자, 시간, 유형, 원문 근거를 검증하며 되돌릴 수 있게 기록합니다.


## 3. 실용적 구현: 엔티티 및 관계 추출 (Extracting Entities and Relationships)

비구조화된 텍스트에서 지식 그래프를 구축하기 위해, 우리는 LLM에 엔티티와 그들의 관계를 식별하도록 프롬프트를 주고, 이를 구조화된 형식(예: JSON)으로 반환하도록 합니다.

아래 Python 예제는 미리 작성한 추출 결과의 구조를 검사합니다.

> **교육용 오프라인 예제.** 추출 결과의 구조만 검사합니다. 실제 추출, 사실 검증, 권한·유효 시간 검사와 영속 저장은 구현하지 않습니다.

```python
# Authored extraction output: this example does not call an LLM.
def validate_graph(graph):
    nodes = graph["entities"]
    ids = [node["id"] for node in nodes]
    if len(ids) != len(set(ids)):
        raise ValueError("duplicate entity IDs")
    allowed_relations = {"ACQUIRED_BY", "HAS_CEO"}
    for edge in graph["relationships"]:
        if edge["source"] not in ids or edge["target"] not in ids:
            raise ValueError("edge references an unknown entity")
        if edge["type"] not in allowed_relations or not edge["source_span"]:
            raise ValueError("unsupported relation or missing evidence")
    return graph  # Structural validation, not verification of factual truth.

graph = validate_graph({
    "entities": [{"id": "Orion"}, {"id": "Northstar"}, {"id": "Mina"}],
    "relationships": [
        {"source": "Orion", "target": "Northstar", "type": "ACQUIRED_BY",
         "source_span": "Fictional memo A: Northstar acquired Orion."},
        {"source": "Northstar", "target": "Mina", "type": "HAS_CEO",
         "source_span": "Fictional memo B: Mina is Northstar's CEO."},
    ],
})
print(len(graph["relationships"]))  # 2
```

## 4. 다중 홉 탐색

가상 문서에서 Orion은 Northstar에 인수되었고 Mina가 Northstar의 CEO라고 합시다. 검색한 엔터티에서 `Orion → Northstar → Mina` 관계를 따라가면 답의 근거 후보를 얻습니다. 그래도 유효 날짜와 원문 근거를 확인해야 하며 생성기가 잘못 답할 수 있습니다.

### 그래프 검색 엔지니어링: 재시작이 있는 무작위 보행 (Random Walk with Restart, RWR)

관계가 정해져 있다면 스키마에 맞는 탐색으로 `ACQUIRED_BY` 같은 간선을 따라갈 수 있습니다. 어떤 이웃이 유용한지 덜 분명할 때는 **재시작이 있는 무작위 보행(Random Walk with Restart, RWR)** 으로 시작 분포 주변 노드의 근접도를 매길 수 있습니다. 이는 선택 가능한 그래프 검색 방법이며, Microsoft GraphRAG의 로컬 검색 자체를 정의하는 알고리즘은 아닙니다.

시작 분포 $\mathbf{p}_0$ (벡터 검색을 통해 찾은 초기 노드들)가 주어지면, 알고리즘은 그래프의 엣지를 탐색하는 무작위 보행자(Random walker)를 시뮬레이션합니다. 보행자가 무관한 영역으로 너무 멀리 표류하는 것을 방지하기 위해, 시작점으로 다시 "순간 이동(Teleporting)"할 확률 $c$ 를 갖습니다.

$$ \mathbf{p}_{t+1}=(1-c)(\mathbf W\mathbf p_t+\mathbf p_0\mathbf d^T\mathbf p_t)+c\mathbf p_0. $$

여기서 $\mathbf p_t$ 는 $t$ 단계 후 각 노드의 확률을 나타내는 벡터이고, $0 < c \leq 1$ 은 재시작 확률입니다. $\mathbf W$ 는 나가는 간선이 있는 열을 정규화하고 dangling 열은 0으로 둔 인접 행렬입니다. $d_j$ 는 노드 $j$ 가 dangling이면 1, 아니면 0입니다. $\mathbf d^T\mathbf p_t$ 는 그 노드들에 놓인 확률 질량이며 초기 분포 $\mathbf p_0$ 로 재분배됩니다. 아래는 이 규칙의 교육용 구현입니다.

Orion을 인수한 회사의 CEO는 누구일까요? 앞의 가상 메모 두 건에 세 번째 메모를 추가합니다. 여기에는 Vendor Z가 Northstar에 장비를 공급한다고 적혀 있습니다. 무작위 보행은 세 간선이 어느 노드를 잇는지만 사용합니다. 관계의 종류와 출처는 답의 근거를 찾을 때 확인합니다.

> **CPU 예제.** PyTorch를 설치한 뒤 아래 블록을 실행하세요. 노드가 $V$개인 밀집 행렬의 저장 공간과 반복당 연산량은 $O(V^2)$입니다. 나가는 간선이 없는 노드의 확률 질량은 시작 분포로 돌려보내며, 20회 반복한 뒤 멈춥니다. 메모 세 건과 추출된 관계는 미리 정해 둔 입력입니다.

```python
import torch

class GraphRetriever:
    """
    재시작이 있는 무작위 보행(RWR)을 사용한 그래프 검색의 PyTorch 구현체입니다.
    초기 시작 분포 주변의 그래프 근접도 점수를 계산합니다.
    """
    def __init__(self, num_nodes: int, edges: torch.Tensor, restart_prob: float = 0.15):
        """
        Args:
            num_nodes: 지식 그래프 내 전체 엔티티 수.
            edges: (2, num_edges) 형태의 텐서. edges[0]은 소스, edges[1]은 타겟.
            restart_prob: 초기 검색 노드로 다시 순간 이동할 확률 (c).
        """
        if num_nodes < 1 or not 0 < restart_prob <= 1:
            raise ValueError("Require nodes > 0 and restart probability in (0, 1]")
        self.num_nodes = num_nodes
        self.restart_prob = restart_prob

        # 인접 행렬 초기화
        self.adj_matrix = torch.zeros(num_nodes, num_nodes)

        # p_{t+1} = W * p_t 인 열 추계적(Column-stochastic) 행렬을 위해,
        # 열은 소스 노드를, 행은 타겟 노드를 나타냅니다.
        self.adj_matrix[edges[1], edges[0]] = 1.0

        # 인접 행렬 정규화 (열 추계적)
        out_degree = self.adj_matrix.sum(dim=0, keepdim=True)
        self.dangling = (out_degree.squeeze(0) == 0)
        out_degree = out_degree.clamp_min(1.0)
        self.trans_matrix = self.adj_matrix / out_degree

    def retrieve_subgraph(self, initial_nodes: torch.Tensor, num_steps: int = 15) -> torch.Tensor:
        """
        Args:
            initial_nodes: 시작 분포를 나타내는 텐서 (num_nodes, 1)
                           (예: 초기 벡터 임베딩 검색을 통해 찾은 노드들).
        Returns:
            그래프 내 모든 노드에 대한 관련성 점수 (Relevance scores).
        """
        # 초기 분포 정규화
        if initial_nodes.shape != (self.num_nodes, 1):
            raise ValueError("Expected initial_nodes shape [num_nodes, 1]")
        if not torch.isfinite(initial_nodes).all() or (initial_nodes < 0).any() or initial_nodes.sum() <= 0:
            raise ValueError("Initial distribution must have finite nonnegative positive mass")
        p_0 = initial_nodes / initial_nodes.sum()
        p_t = p_0.clone()

        # 정해진 횟수만 반복하며 수렴 여부는 검사하지 않습니다.
        for _ in range(num_steps):
            dangling_mass = p_t[self.dangling].sum()
            walk = self.trans_matrix @ p_t + dangling_mass * p_0
            p_t = (1 - self.restart_prob) * walk + self.restart_prob * p_0

        return p_t


def follow(facts, candidates, subject, relation):
    return [(target, memo) for source, kind, target, memo in facts
            if source == subject and kind == relation and target in candidates]


if __name__ == "__main__":
    nodes = ["Orion", "Northstar", "Mina", "Vendor Z"]
    ids = {name: i for i, name in enumerate(nodes)}
    memos = {"A": "Northstar acquired Orion.",
             "B": "Mina is Northstar's CEO.",
             "C": "Vendor Z supplies equipment to Northstar."}
    facts = [("Orion", "ACQUIRED_BY", "Northstar", "A"),
             ("Northstar", "HAS_CEO", "Mina", "B"),
             ("Northstar", "HAS_SUPPLIER", "Vendor Z", "C")]
    edges = torch.tensor([(ids[s], ids[t]) for s, _, t, _ in facts]).T
    retriever = GraphRetriever(len(nodes), edges, restart_prob=0.2)
    initial = torch.zeros(len(nodes), 1)
    initial[ids["Orion"]] = 1.0
    scores = retriever.retrieve_subgraph(initial, num_steps=20).flatten()

    cutoff = torch.topk(scores, k=3).values[-1]
    candidates = {name for name in nodes if scores[ids[name]] >= cutoff}
    for name in sorted(candidates, key=lambda n: (-scores[ids[n]].item(), n)):
        print(f"{name}: {scores[ids[name]]:.6f}")

    for buyer, first_memo in follow(facts, candidates, "Orion", "ACQUIRED_BY"):
        for person, second_memo in follow(facts, candidates, buyer, "HAS_CEO"):
            print(f"{person} | {first_memo}: {memos[first_memo]} "
                  f"| {second_memo}: {memos[second_memo]}")
```

실행하면 Orion은 0.406056, Northstar는 0.324845입니다. Mina와 Vendor Z는 **0.134550** 으로 공동 3위입니다. 두 노드 모두 Northstar에서 나가는 확률의 절반씩을 받고, 나가는 간선도 없습니다. `torch.topk` 에 인덱스 세 개만 요청하면 둘 중 하나만 남습니다. PyTorch는 동점일 때 어느 인덱스를 반환할지 보장하지 않습니다 [[7]](#ref-7). 이 예제는 3위 점수 이상인 후보를 모두 남기므로 네 개가 통과합니다.

마지막 출력은 `Mina | A: Northstar acquired Orion. | B: Mina is Northstar's CEO.`입니다. 메모 A는 인수 기업을, 메모 B는 그 회사의 CEO를 확인해 줍니다. 메모 C가 뒷받침하는 관계는 장비 공급입니다. Vendor Z가 Mina와 같은 점수를 받았어도 CEO라는 근거는 없습니다. 후보를 반드시 세 개만 보낼 수 있다면 동점 처리 기준을 정하고 그 과정에서 답의 근거가 빠지는지 확인하세요.

HippoRAG는 추출한 지식 그래프와 Personalized PageRank를 결합하고, 논문에서 평가한 다중 홉 기준선보다 개선된 결과를 보고합니다 [[3]](#ref-3). 이는 해당 데이터셋과 검색 설정에서 얻은 결과입니다. 위의 작은 RWR 예제는 그 시스템을 재현하지 않으며 비용 우위를 입증하지도 않습니다.

## 5. Microsoft GraphRAG: 질문 전에 만드는 보고서

“누가 Orion을 인수했는가?”와 “이 장애 보고서 전체에 반복해서 나타나는 위험은 무엇인가?”는 필요한 근거가 다릅니다. 첫 질문에는 관계 경로가 유용할 수 있습니다. 두 번째는 여러 문서를 넓게 살펴야 하므로, 비슷한 구절 몇 개만 찾으면 작은 주제를 놓칠 수 있습니다. Microsoft의 GraphRAG 논문은 엔터티 그래프와 미리 만든 커뮤니티 보고서로 이런 질의 중심 요약 문제를 다룹니다 [[1]](#ref-1).

**문서 확인 기준: 2026-11-18.** 아래 그림은 재사용하는 색인과 전역 질문마다 반복하는 작업을 구분합니다 [[4]](#ref-4) [[5]](#ref-5). 커뮤니티를 찾는 것만으로 답변이 생기지는 않습니다.

### 저장되는 것과 질문마다 생성되는 것

색인 단계에서는 원문 근거를 연결한 엔터티와 관계를 추출합니다. 연결된 엔터티를 계층적으로 묶는 커뮤니티 탐지에 Leiden 알고리즘 등을 사용합니다 [[2]](#ref-2). 이어서 파이프라인이 커뮤니티 보고서를 생성합니다. 이 보고서는 특정 사용자의 질문을 받기 전에 이미 정보를 선택하고 압축한 요약입니다 [[4]](#ref-4).

전역 검색은 선택한 계층 수준의 보고서를 문맥에 들어갈 크기로 나눕니다. 각 map 호출이 질문과 보고서 묶음을 받아 답변에 쓸 요점을 제안합니다. 선별·순위화를 거친 요점이 reduce 호출로 전달되고, 최종 응답을 구성합니다 [[5]](#ref-5). 중간 결과의 중요도 점수는 선택 기준이며, 내용이 사실일 확률을 보정한 값은 아닙니다.

이 전역 검색 경로는 보고서를 문맥으로 사용합니다. 그렇다고 모든 GraphRAG 질의가 원문을 무시하는 것은 아닙니다. 공식 로컬 검색 경로는 관련 엔터티 주변의 그래프 기록과 입력 문서의 정보를 결합합니다 [[6]](#ref-6). 그래프를 사용하는 방법을 하나의 알고리즘으로 묶기보다 질문에 맞는 검색 경로를 선택해야 합니다.

### 비용과 누락을 함께 보는 예제

설명용 상황에서 한 계층 수준의 사용 가능한 보고서가 120개라고 합시다. map 호출 하나에 온전한 보고서 네 개씩 들어간다면 map 30회와 reduce 1회가 필요합니다. map 결과 하나가 200토큰씩 기여하면 reduce 단계에는 자체 프롬프트와 답변 예산을 제외하고도 6,000토큰의 후보가 모입니다. 후보용 공간이 3,000토큰뿐이라면 일부를 선별하거나 압축해야 합니다. 이 수치는 교육용 예산이며 GraphRAG의 기본 설정이나 실측 비용이 아닙니다. map 호출을 병렬화하면 경과 시간을 줄일 수 있지만 토큰 연산 자체가 사라지지는 않습니다.

이제 원문 두 개에만 나타나는 안전 문제를 생각해봅시다. 관계 추출, 보고서 요약, map 결과 선택 중 어느 단계에서든 그 문제가 사라질 수 있습니다. 유창한 전역 답변만으로 해당 문제가 검토됐다고 판단할 수는 없습니다. 알려진 사실과 소수 주제를 기준으로 전체 문서의 반영 범위를 평가하고, 선택한 주장을 보고서에서 원문 구간까지 추적해야 합니다.

원문이 바뀌거나 접근 권한이 사라지면, 그 원문에서 파생된 그래프 기록과 보고서도 재사용 전에 무효화하거나 다시 생성해야 합니다. 원문 스냅샷·추출 설정·그래프·보고서·접근 정책을 버전이 있는 검색 산출물로 묶어 관리하세요. 배포 전에는 더 단순한 기준선과 비교해 질의 유형별 근거 충실도와 반영 범위, 색인·갱신 비용, 질의 비용, 지연 시간을 평가합니다. 그래프 구조를 늘리는 것은 그 비교 결과가 유지 비용을 정당화할 때 유용합니다.

## 6. 실무 요점

그래프는 관계 경로를, 커뮤니티 보고서 계층은 더 넓은 정보 범위를 제공할 수 있습니다. 어느 쪽도 추출한 사실이나 생성한 요약을 인증하지는 않습니다. 오래된 근거와 누락을 진단할 수 있도록 원문 출처와 색인·질의 단계의 경계를 명확히 유지하세요.

다음 절인 **14.6 RAG 실패 모드와 운영 설계** 에서는 틀린 답변의 근거를 추적하며 어느 단계를 고쳐야 하는지 확인합니다.

## Quizzes

<details>
<summary>Quiz 1: 소수의 top-k 문서가 전역 요약에 부족할 수 있는 이유는 무엇인가요?</summary>
*관련성이 높은 일부 문서가 전체 주제 분포를 대표하지 않을 수 있습니다. 군집 요약은 범위를 넓힐 수 있지만 누락과 왜곡을 별도로 평가해야 합니다.*
</details>

<details>
<summary>Quiz 2: LLM 추출이 스키마와 검증을 대체하나요?</summary>
*아닙니다. 형식, 엔터티 식별, 관계 의미, 출처, 유효 시간과 권한을 관리해야 합니다. 형식이 맞아도 내용은 틀릴 수 있습니다.*
</details>

<details>
<summary>Quiz 3: 전역 검색이 질문에 답하기 전에 Leiden 커뮤니티 탐지는 어떤 역할을 하나요?</summary>
*연결된 엔터티의 커뮤니티를 찾습니다. 색인 파이프라인은 이를 기준으로 보고서를 구성하며, 질의 시점의 map/reduce가 구체적인 질문에 답해야 합니다. 커뮤니티 탐지 자체가 보고서를 작성하거나 그 안의 사실을 검증하지는 않습니다.*
</details>

<details>
<summary>Quiz 4: 제공된 PyTorch의 재시작이 있는 무작위 보행(RWR) 구현에서 `restart_prob` 매개변수의 역할은 무엇입니까?</summary>
*매 단계마다 확률 질량의 $c$ 비중을 시작 분포에, $1-c$ 비중을 dangling 노드 처리를 포함한 그래프 전이 결과에 배정합니다. 재시작 확률이 높을수록 시작 노드의 비중이 커지고 먼 노드까지 탐색하는 정도는 줄어듭니다. 높은 점수나 잦은 재시작이 해당 노드가 질문에 필요한 사실을 담고 있음을 검증하지는 않습니다.*
</details>

<details>
<summary>Quiz 5: 임베딩 유사도만으로 엔터티를 병합하면 어떤 문제가 생기나요?</summary>
*비슷한 이름이나 설명이 같은 대상을 뜻하지는 않습니다. 식별자·유형·시간·원문을 확인하고 병합 이력을 보존해야 합니다. 병합 후에는 중복 간선과 가중치 의미를 정한 다음 전이 확률을 다시 정규화합니다.*
</details>

<details>
<summary>Quiz 6: 원문이 색인에 남아 있는데도 드문 문제가 답변에서 사라질 수 있는 이유는 무엇인가요?</summary>
*관계를 추출하면서 빠뜨렸거나, 커뮤니티 보고서가 요약하면서 생략했거나, 질의 시점의 map/reduce 예산 때문에 제외했을 수 있습니다. 각 경계에서 근거를 확인해야 합니다. 최종 답변을 길게 만드는 것만으로 모든 입력 보고서에서 빠진 정보를 복원할 수는 없습니다.*
</details>
