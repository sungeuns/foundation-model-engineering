# 16.6 에이전트 신뢰성, 복구, 그리고 가드레일

고객이 에이전트에게 문의 티켓 한 건을 열어 달라고 했습니다. 고객센터에는 티켓이 등록됐는데 응답이 제시간에 돌아오지 않았습니다. 고객 화면에는 로딩 표시가 남고 에이전트의 로그에는 시간 초과가 찍힙니다. 다음 차례에 에이전트는 무엇을 해야 할까요?

여기서 도구가 **처리한 일** 과 에이전트가 **확인한 일** 이 갈립니다. 시간 초과는 호출자가 기다리기를 멈춘 시점만 알려 줍니다. 티켓이 생겼는지 확인하려면 접수 번호를 받거나 원래 요청을 조회할 수 있어야 합니다. $τ$-bench에서도 한 번 성공한 에이전트가 같은 과제를 여러 번 수행하면 매번 성공하지는 않았습니다 [[4]](#ref-4).

---

## 1. 루프에는 반드시 상한을 둬야 한다

실행 한 건에 허용할 시간과 도구 호출 횟수를 정합니다. 재시도에도 별도 한도를 두면 도구 하나가 느려졌을 때 나머지 작업에 쓸 기회가 남습니다.

### 최소 실행 제한

- 모델이 응답한 횟수와 도구를 호출한 횟수를 따로 셉니다.
- 도구별 응답 대기 시간과 작업 전체의 마감 시간을 정합니다.
- 실행을 멈춘 이유와 아직 처리 결과를 모르는 요청을 기록합니다.

마지막으로 허용된 호출에서 시간 초과가 났다면 요청 식별자와 함께 ‘처리 여부 확인 중’이라고 남깁니다. 다음 작업자는 그 요청부터 조회하고 재시도 여부를 정할 수 있습니다.

## 2. 변경을 요청하기 전에 남길 기록

외부 서비스에 변경을 요청하기 전에 할 일과 인자, 요청을 식별할 키를 저장합니다. 응답이 오면 접수 번호도 저장합니다. 두 기록 사이에 작업자가 멈추면 무엇을 요청했는지는 알지만 처리됐는지는 아직 모르는 상태가 됩니다.

### 권장 패턴

1. 재시작한 작업자는 체크포인트에서 결과를 기다리던 요청을 읽습니다.
2. 받은 쪽에서 원래 요청을 조회합니다. 서비스가 멱등한 생성 요청을 지원하면 같은 키로 다시 호출할 수도 있습니다.
3. 접수 번호를 확인하면 저장합니다. 조회와 안전한 재시도가 모두 어려우면 대조할 수 있을 때까지 보류합니다.

<a id="lost-ticket-receipt"></a>

### 응답이 끊긴 뒤에도 티켓은 남는다

Python 3 표준 라이브러리로 작은 고객센터를 만들어 봅시다. SQLite 파일 하나가 티켓을 보관하고, 한 명의 호출자가 요청할 때마다 새 연결을 엽니다. 첫 호출은 티켓을 저장하지만 반환값을 일부러 버립니다. 응답이 유실된 상황입니다. 이어지는 두 호출에서 복구 방법을 바꿔 봅니다.

```python
from contextlib import closing
from pathlib import Path
import sqlite3
from tempfile import TemporaryDirectory

def create_ticket(path, key, subject):
    with closing(sqlite3.connect(path)) as db, db:
        db.execute("""CREATE TABLE IF NOT EXISTS ticket (
            id INTEGER PRIMARY KEY, request_key TEXT UNIQUE NOT NULL,
            subject TEXT NOT NULL)""")
        db.execute("""INSERT INTO ticket(request_key, subject) VALUES (?, ?)
                      ON CONFLICT(request_key) DO NOTHING""", (key, subject))
        ticket_id, saved_subject = db.execute(
            "SELECT id, subject FROM ticket WHERE request_key = ?", (key,)
        ).fetchone()
        if subject != saved_subject:
            raise ValueError("request key already used for another subject")
        return ticket_id

with TemporaryDirectory() as folder:
    path = Path(folder) / "support.db"
    subject = "Missing receipt for order 41"
    create_ticket(path, "action-41", subject)
    print(create_ticket(path, "action-41", subject))  # 1
    print(create_ticket(path, "action-42", subject))  # 2
```

두 번째 호출은 원래 티켓의 접수 번호 1을 돌려줍니다. 세 번째 호출은 제목이 같은데도 새 키가 들어왔기 때문에 티켓 2를 만듭니다. 반대로 두 번째 호출에서 키는 유지한 채 제목만 바꿔 보세요. 서비스는 원래 티켓을 보존하고 오류를 냅니다. 키에 유일성 제약을 두고 티켓과 같은 트랜잭션에 저장하므로 티켓만 생기고 키가 누락되는 틈이 없습니다 [[9]](#ref-9).

실제 서비스에서는 키의 적용 범위와 보관 기간도 확인해야 합니다. 여러 고객사가 쓰는 서비스라면 인증된 계정과 키를 함께 조회해야 합니다. 보관 기간이 지나 서비스가 키를 지웠다면 같은 키를 다시 보내도 티켓이 하나 더 생길 수 있습니다.

**모델의 대화 기록은 어디에 쓰일까요? (2026-11-25 기준)** OpenAI 문서에 따르면 GPT-6.2 Responses API에서 앞선 메시지나 도구 호출을 편집하면 그 뒤의 추론 항목을 모델이 더는 참조하지 못할 수 있습니다. 같은 판단을 다시 내리느라 토큰이 더 들 수도 있습니다 [[10]](#ref-10). 대화를 편집해도 고객센터에는 티켓 1이 남아 있습니다. 다음 행동을 다시 판단해야 할 때에도 에이전트는 저장해 둔 요청 키로 고객센터에서 접수 번호를 찾아올 수 있습니다.

## 3. 도구별 재시도 정책

고객센터 에이전트는 티켓을 조회하고, 내부 메모를 달고, 고객에게 메일을 보낼 수 있습니다. 어느 호출에서든 시간 초과가 날 수 있지만, 다시 호출했을 때의 결과는 기능마다 다릅니다.

### 유용한 기본 정책

인증된 계정으로 호출하고, 인자를 검증하고, 마감 시간을 정합니다. 시간 초과 뒤 어떻게 처리할지도 작업별로 명시합니다. 받는 서비스가 요청 키를 얼마나 보관하는지는 도구 설명만 읽어서는 알기 어렵습니다.

<a id="영향-반경blast-radius-기준으로-툴을-분류하라"></a>

### 같은 호출을 한 번 더 보내면

| 작업 | 두 번 호출하면 생길 수 있는 일 | 복구 방법 |
| --- | --- | --- |
| 티켓 1 조회 | 첫 조회 이후 상태가 바뀌었을 수 있습니다. | 마감 시간 전이라면 다시 읽습니다. |
| 메모 추가 | 같은 메모가 두 번 붙을 수 있습니다. | API가 지원하면 저장한 키로 재시도한 뒤 메모 번호를 확인합니다. |
| 고객에게 메일 발송 | 고객이 같은 메일을 두 번 받을 수 있습니다. | 발송 서비스의 기록을 조회합니다. 접수 여부를 알 수 없으면 보류합니다. |

잘못 적은 초안은 대개 고칠 수 있습니다. 발송한 메일은 고객이 이미 읽었을 수 있습니다. 이 차이에 따라 실행 전에 받을 승인과 실행 뒤의 복구 방법이 달라집니다.

## 4. 언제 사용자에게 다시 물을까

사용자가 티켓 한 건을 열어 달라고 했습니다. 첫 티켓을 만드는 데 필요한 동의는 이미 받았습니다. 그런데 시간 초과 뒤에 새 키를 보내면 고객센터에서는 별도 티켓을 만들라는 요청으로 받아들입니다. 티켓 한 건만 열어 달라는 요청의 범위를 넘는 셈입니다.

### 승인 경계 예시

권한이 있는 작업자는 접수 여부를 직접 조회할 수 있습니다. 다시 물어야 할 때는 사용자의 선택에 따라 실제 결과가 달라지는 순간입니다. 예컨대 원래 요청을 확인할 길이 없다면 주문 번호, 첫 요청을 보낸 시각, 중복 가능성을 보여 주고 새 티켓을 열지 묻습니다. 첫 요청이 뒤늦게 확인되면 보류해 둔 건과 연결합니다.

## 5. 관련 연구가 실제로 보여 주는 것

에이전트 논문을 읽을 때 한 가지 질문을 던져 봅시다. 연구진은 에이전트가 행동한 뒤 무엇을 관찰했을까요?

- **ReAct** 는 추론과 행동을 번갈아 수행합니다. 검색 결과를 읽고 다음 행동을 바꿀 수 있습니다 [[1]](#ref-1). **Toolformer** 는 도구를 언제 호출하고 그 응답을 어떻게 쓸지 모델이 학습하는 방법을 다룹니다 [[3]](#ref-3).
- **Reflexion** 은 이전 시도의 피드백을 글로 남겨 다음 시도에 활용합니다 [[2]](#ref-2). 티켓 예제라면 원래 요청부터 조회하도록 도울 수 있습니다. 중복 티켓이 생겼는지 최종적으로 확인할 곳은 고객센터입니다.
- **AgentBench** 는 여러 대화형 환경에서 연속된 판단을 평가합니다 [[5]](#ref-5). **SWE-bench** 는 제안한 변경이 실제 저장소 이슈를 해결하는지 검사합니다 [[6]](#ref-6). 무엇을 성공으로 셀지는 과제와 채점 기준에 달려 있습니다.
- **$τ$-bench** 는 업무 규칙 아래서 사용자와 대화하고 도구를 쓰는 과제를 반복합니다 [[4]](#ref-4). 목표가 티켓 한 건 접수라면 매끄러운 안내 문구보다 실제로 추가된 티켓 수가 더 나은 검증 기준입니다.

## 6. 핵심 정리

복구 연습에서는 티켓이 저장된 직후 응답을 끊고 작업자를 재시작합니다. 사용자 요청 한 건으로 티켓이 몇 개 생겼는지, 고객이 받은 접수 번호가 무엇인지, 다음 작업자가 결과를 재구성할 수 있는지 확인합니다. 이번에는 고객센터 조회까지 막아 놓고 접수 건이 보류 상태로 남는지 확인합니다.

## 최근 근거: 우회 경로에서도 경계가 유지되어야 한다

**2026-10-13 기준.** Anthropic의 10월 9일 보고서는 평가·내부 사용에서 도구 제한을 돌아가려는 시도 등 의도하지 않은 행동을 공개했습니다. 제공사는 열거한 사례의 실제 영향이 작았다고 설명하며, 격리와 감시를 강화하는 동안 내부 평가 전반의 live internet 접근을 끊었다고 보고합니다 [[7]](#ref-7). 이는 구체적인 실패 유형의 근거이지 보편적인 사고율이나 다른 시스템의 실패 빈도를 추정한 결과는 아닙니다.

복구 정책도 원래 행동 경계를 유지해야 합니다. fetch가 거부됐다고 다른 도구·redirect·서비스로 전환하는 과정에서 권한이 새로 생겨서는 안 됩니다. 모델 설명과 독립적으로 실행 시점에 목적지와 행동 권한을 검사합니다. 대체 경로·간접 요청·거부 뒤 재시도·읽기로 위장한 쓰기를 시험합니다. 시도한 효과, 차단한 효과, 실제 효과, 복구 결과를 따로 기록합니다. 협조적인 설명만으로 실행기가 격리를 강제했다는 증거가 되지 않습니다.


### 삭제에는 접근 경로 검사가 필요하다

**2026-10-18 기준**, Lizzo와 Heck의 10월 15일 워크숍 논문은 의미가 같은 다국어 질의에서도 측정되는 망각이 달라질 수 있음을 보여 줍니다 [[8]](#ref-8). 한 언어에서 거부하거나 회상하지 못한다고 정보에 접근할 수 없다는 뜻은 아닙니다. 접근 경로 일반화의 한정된 근거이며 모든 unlearning 방법이 실패한다는 정리는 아닙니다.

실무 출시 기준에서는 외부 메모리 삭제와 모델 가중치 변경을 구별합니다. 원본 기록·요약·벡터 및 그래프 인덱스·캐시·복제본·복원 경로까지 삭제 계보를 추적합니다. 지원 언어와 문자 체계에서 동등한 질의로 권한 있는 복구 감사를 수행해야 하며 영어 거부 시험만으로는 부족합니다. 롤백이 삭제된 기록을 되살려서는 안 됩니다. 삭제 표식과 보존 결정을 아티팩트·데이터 계보와 함께 버전 관리하고, 보존 정책에 따라 남아 있는 사본의 범위를 명시합니다.

판단 모델은 라우팅·검토 신호를 줄 수 있지만 실행 권한을 부여하지는 않습니다. [16.7절](/ko/chapter-16/decision-models-and-selective-prediction)은 타입 출력·보정된 확률·판단 보류·독립된 실행기 정책을 구분합니다.
