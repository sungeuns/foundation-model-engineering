# 9.4 프롬프팅·ICL·프롬프트 최적화

프롬프팅과 SFT는 모두 과업 행동을 바꿀 수 있지만 수정하는 아티팩트가 다릅니다. SFT는 모델·adapter 파라미터를 바꾸고, 프롬프트는 forward pass의 조건 문맥을 바꿉니다. 실무에서는 어떤 개입이 허용 가능한 최적화·서빙·유지 비용으로 필요한 행동을 만드는지 비교합니다.

In-context learning은 저장된 가중치를 갱신하지 않고도 예시를 활용합니다. 그렇다고 예시를 읽는 frontier Transformer가 실제 gradient 기반 SFT를 실행하는 것과 같지는 않습니다.

## 1. 그래디언트 하강 비유에는 가정이 있다

Dai 등과 von Oswald 등은 어텐션과 최적화의 연결을 연구합니다 [[1]](#ref-1) [[2]](#ref-2). 특정 구성과 실험 조건의 메커니즘을 설명하지만 모든 비선형 어텐션 모델·과업에 같은 구현이 있다는 증명은 아닙니다.

**선형 회귀 설명용 구성** 을 보겠습니다. $k_i\in\mathbb R^d$ 는 입력, $y_i\in\mathbb R^m$ 는 target, $W_0\in\mathbb R^{m\times d}$ 는 초기 예측기, $N$ 은 예시 수, $\eta$ 는 step 크기입니다. 평균 제곱 오차의 gradient 한 step은 다음과 같습니다.

$$
\Delta W=\frac{\eta}{N}\sum_{i=1}^{N}(y_i-W_0k_i)k_i^\top.
$$

질의 $q\in\mathbb R^d$ 에 적용하면

$$
(W_0+\Delta W)q=W_0q+\frac{\eta}{N}\sum_i(y_i-W_0k_i)(k_i^\top q).
$$

오른쪽은 예측 residual을 update value로 쓰는 선형 연상 어텐션과 닮았습니다. 이는 최적화와의 가능한 연결을 설명합니다. 임의의 value가 gradient라거나 사전 학습 모델의 저장된 파라미터가 바뀌었다는 뜻은 아닙니다. 예시 순서·형식·관련성·과업 분포도 동작에 영향을 줍니다.

## 2. 추론 토큰은 연산을 추가하지만 깊이를 보장하지 않는다

생성한 추론 토큰은 다음 모델 step의 문맥이 됩니다. 분해·검사·수정을 도울 수 있지만 반복이나 합리화가 될 수도 있습니다. 레이어 수와 출력 토큰 수의 곱은 반복 forward 연산량이지 유효한 논리적 추론 횟수가 아닙니다. 풀이에 적힌 단계가 레이어보다 많다고 고정 깊이 모델이 반드시 실패하는 것도 아닙니다.

[15.3절](/ko/chapter-15/search-time-compute)에서 추론 예산 배분을, [15.5절](/ko/chapter-15/reasoning-post-training-rlvr)에서 학습된 추론과 test-time prompting의 차이를 확인하세요. 실제 정답률·검증·종료·전체 토큰·지연을 함께 평가합니다.

## 3. 최적화 workflow로서의 프롬프트 컴파일

DSPy는 signature와 program module을 optimizer가 선택하는 지시·예시와 분리합니다 [[3]](#ref-3). 프롬프트 자산을 버전 관리하고 비교하기 쉬워지지만 최적 프롬프트·사람 검토의 불필요성·다른 모델로의 이식성을 보장하지는 않습니다. 재컴파일은 제한된 예산과 선택한 metric의 탐색입니다.

## 4. 재현 가능한 프롬프트 최적화 계약

다음은 개념적 workflow이며 실행 가능한 DSPy script가 아닙니다. 라이브러리 이름과 optimizer signature는 바뀌므로 구현할 때 정확한 버전과 해당 문서를 고정합니다.

| 단계 | 아티팩트와 결정 |
|---|---|
| 기준점 | 모델/제공사 리비전·토크나이저 고유 템플릿·system prompt·도구·검색 리비전·생성/추론 설정 |
| 탐색 데이터 | 출처·허가된 예시·의미 군집 분할·sample ID·평가 격리 |
| 목적 | 가능하면 실행 가능한 정확성 검사, 그렇지 않으면 보정된 rubric, 중요 안전·형식 제약 |
| 탐색 예산 | 후보/시도 한도·예시 수·입력/출력 cap·reflection 호출·총토큰/비용·seed·timeout |
| 개발 | 모든 후보·trace·metric·실패·제외 이유·부모 계보 기록 |
| 최종 평가 | reflection·후보 선택에 노출하지 않은 봉인 holdout, 기준점과 짝지은 비교 |
| 승격 | 버전 관리한 prompt/program 묶음·제한된 canary·책임자·rollback 경계 |

예시의 학습/서빙 포맷 일치를 확인합니다. 고유 role·BOS/EOS·`add_generation_prompt`·잘림·padding을 점검합니다. 나중에 최적화한 프로그램을 SFT로 증류한다면 assistant 구간 loss mask를 명시하고, 도구 결과·padding을 제외하고, packing한 예시 사이의 어텐션을 차단하며, base/reference ID와 응답 길이 정책을 고정합니다. 프롬프트 컴파일 자체가 이 가중치 업데이트를 수행하지는 않습니다.

역전파를 피하더라도 프롬프트 탐색은 추론 자원을 씁니다. prefill·decode·reflection/검증 호출·도구/sandbox·임시 상태·병렬 후보·평가·저장 아티팩트를 별도 계산합니다. 이후 SFT에는 9.1절의 계약에 따라 파라미터·gradient·optimizer 상태·activation·정밀도·sharding·재계산도 추가합니다.

## 5. 평가·복구·출시

도메인·난도별 품질, 예시 민감도, prompt injection 행동, 형식/도구 오류, 출력 길이, 비용, p50/p95 지연, 제공사 오류를 측정합니다. 후보·batch ID로 재구성 가능하게 합니다. 가중치 증류에는 토큰 정규화 학습/검증 손실, nonfinite/overflow, gradient/activation norm, 처리량, MFU, 데이터 대기, collective/straggler, 전체 학습 checkpoint도 추가합니다.

사전 예산에 도달하거나 권한 밖 도구 효과가 반복되거나 평가기 의견이 충돌하거나 불확실성 범위 안에서 holdout 개선이 없으면 탐색을 중단합니다. 재개 가능한 optimizer/search 상태, 후보 계보, RNG, 데이터 커서, 모델/템플릿/데이터/config hash를 저장합니다. SFT checkpoint는 sharded 모델/optimizer·scheduler·scaler/FP8 상태·step/토큰 수·sampler도 포함합니다. checksum과 원자적 게시를 사용하고 보존·복제·복원 검사·분산 학습의 world-size 변경 제한을 정의합니다.

도메인 품질·기존 역량 유지·안전·형식/도구·지연·비용·오류 기준을 짝지은 불확실성이나 근거 있는 표본 수로 통과한 뒤 출시합니다. rollback은 prompt/program/model/tool 전체 묶음을 복원해야 합니다. 책임자·관측 구간을 정하고 전환을 훈련합니다. 개발셋 점수 상승만으로는 부족합니다.
