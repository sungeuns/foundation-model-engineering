# 17.2 LLM을 이용한 평가

유용한 출력 중에는 하나의 정확한 답이 없는 경우가 많습니다. 심판 모델은 요약을 평가하거나 두 응답을 비교하고, 근거 없는 주장을 대량으로 찾을 수 있습니다. 문제는 의도한 품질 대신 문체·모델 계열에 대한 선호·점수표의 표현을 측정하지 않는 것입니다. 심판은 버전이 있는 측정 도구이며 정답의 원천이 아닙니다 [[1]](#ref-1).

## 1. 프롬프트보다 판단 목적을 먼저 정한다

| 평가 방식 | 적합한 상황 | 주요 위험 |
|---|---|---|
| 수치 점수 | 보정된 임계값이 필요할 때 | 척도와 끝점 해석의 변화 |
| 쌍대 선호 | 같은 과제의 후보 중 선택할 때 | 위치 편향·무승부·비추이성 |
| 기준별 체크리스트 | 요구사항을 따로 확인할 때 | 기준 간 상관·누락된 의무 |
| 결함 발견 | 근거가 있는 오류를 찾을 때 | 그럴듯하지만 잘못된 지적 |

사용자 요청·관련 근거·명시적인 루브릭을 제공합니다. 사실적 뒷받침·지시 준수·표현을 구분하고 모든 실패를 보정되지 않은 점수 하나로 합치지 않습니다. 가능한 경우 모델 판정보다 실행·스키마 검증·신뢰할 수 있는 검사기를 먼저 적용합니다.

## 2. 재현 가능한 쌍대 평가

심판 ID·리비전, 프롬프트·루브릭 해시, 도구 접근, 디코딩 설정, 최대 출력, 후보 출처, 평가셋 버전을 고정합니다. 후보의 정체를 숨기고 표시 순서를 무작위화합니다. 같은 쌍을 양쪽 순서로 제시하고 결과를 원래 후보에 다시 연결해 일치·무승부·불일치를 따로 기록합니다.

불일치나 평가 실패를 조용히 버리면 안 됩니다. 어려운 사례가 더 많이 제외될 수 있습니다. 사람에게 넘길지, 미해결 항목으로 남길지, 보수적 무승부로 셀지 사전에 정합니다. 전체 분모와 미해결 비율을 보고합니다.

정책에 따라 모든 사례를 승리 $W$, 패배 $L$, 무승부 $T$로 분류했다면 다음과 같은 기술적 선호율을 쓸 수 있습니다.

$$
\hat w=\frac{W+0.5T}{N},\qquad N=W+L+T.
$$

이는 사실 정확도가 아닙니다. 반복 프롬프트와 관련 후보를 같은 재표집 단위로 유지하며 짝지은 불확실성을 계산합니다. 잘못된 JSON·timeout·거부·재시도 비용·잘린 출력을 정당한 무승부와 구분합니다.

### 계산 예제: “A가 이겼다”가 서로 다른 후보를 뜻할 수 있다

후보가 `new`와 `baseline`이라고 합시다. 첫 호출에서는 A가 `new`, B가 `baseline`입니다. 순서를 바꾼 호출에서는 A가 `baseline`, B가 `new`입니다. 두 호출 모두 “A 승리”를 반환하면 문자열은 같아도 실제로 선택한 후보는 다릅니다. 위치 편향은 MT-Bench 심판 연구가 살펴본 한계 중 하나입니다 [[6]](#ref-6). 순서를 바꾸는 것은 진단 방법이지 편향을 없앤다는 보장은 아닙니다.

아래 예제는 Python만 사용하며 모델을 호출하지 않습니다. 표시 순서는 위와 같다고 가정하고, 형식이 잘못되거나 서로 모순되는 판정은 미해결 상태로 남깁니다. 심판 프롬프트, 재시도, 스키마 강제, 출처 저장, 불확실성 추정은 생략했습니다.

```python
from collections import Counter

def reconcile(forward, reverse):
    first = {"A": "new", "B": "baseline", "tie": "tie"}
    swapped = {"A": "baseline", "B": "new", "tie": "tie"}
    left, right = first.get(forward), swapped.get(reverse)
    if left is None or right is None:
        return "invalid"
    return left if left == right else "inconsistent"

# Authored fixture: 100 questions, two judgments per question.
pairs = ([("A", "B")] * 54 + [("B", "A")] * 26
         + [("tie", "tie")] * 10 + [("A", "A")] * 6
         + [("timeout", "B")] * 4)
counts = Counter(reconcile(a, b) for a, b in pairs)
n = len(pairs)
unresolved = counts["inconsistent"] + counts["invalid"]
known_points = counts["new"] + 0.5 * counts["tie"]
print(counts)
print("unresolved fraction:", unresolved / n)
print("preference bounds:", known_points / n, (known_points + unresolved) / n)
```

결과는 승리 54개, 패배 26개, 무승부 10개, 불일치 6개, 무효 판정 4개입니다. 확인된 선호 점수는 59점입니다. 미해결 질문 10개를 버리면 59/90 ≈ **65.6%** 로 보고하게 되며, 이는 심판이 판정한 질문에 한정한 수치입니다. 각 미해결 질문이 나중에 0점에서 1점 사이를 받을 수 있다고 두고 전체 분모를 유지하면 **59%–69%의 식별 구간** 을 얻습니다. 이 구간은 빠진 판정의 영향을 나타내며, **신뢰구간이 아니고** 사람과의 일치도도 알려 주지 않습니다. 미해결을 무승부로 처리한다는 정책을 미리 정했다면 64%를 보고하되 미해결 10%를 별도로 밝혀야 합니다. 정책마다 답하는 질문이 다르므로 후보에게 유리한 결과를 본 뒤 선택하지 않습니다.

## 3. 계획과 추론은 올바른 루브릭이 있을 때만 도움이 된다

EvalPlanner는 연구한 설정에서 계획·실행·최종 판정을 분리합니다 [[2]](#ref-2). G-Eval은 기준 중심 모델 평가를 연구합니다 [[4]](#ref-4). 어느 쪽도 긴 설명이 더 정확하다거나 생성된 추론이 충실한 인과 설명이라고 입증하지는 않습니다.

프로덕션 심판에는 짧은 기준별 판정과 근거 위치를 요구합니다. 그 근거가 실제로 존재하고 지적을 뒷받침하는지 확인합니다. 숨겨진 정답 사례와 적대적 후보를 사용하고, 유창한 설명이 실행 검사 실패를 덮어서는 안 됩니다.

### 금지 안내가 번역을 거쳐 권유가 된다면

파일 공유 앱은 안내문에서 `{file}` 자리에 실제 파일 이름을 넣습니다. 영어 원문은 해당 파일을 게스트와 공유하지 말라고 경고합니다. 다음 세 문장 중 어느 것을 한국어판에 넣을 수 있을까요? 번역 후보는 이 실습을 위해 작성했습니다.

```python
import re
from collections import Counter

source = "Do not share the file {file} with guests."
candidates = {
    "A": "{file} 파일을 게스트와 공유하세요.",
    "B": "{file} 파일을 게스트와 공유하지 마세요.",
    "C": "{filename} 파일을 게스트와 공유하지 마세요.",
}

def placeholders(text):
    return Counter(re.findall(r"\{[A-Za-z_][A-Za-z_0-9]*\}", text))

for label, text in candidates.items():
    print(label, placeholders(text) == placeholders(source))
# A True, B True, C False
```

이 앱은 `{name}`처럼 중괄호 안에 이름 하나만 쓰는 자리표시자를 사용하고, 이스케이프 문법은 지원하지 않는다고 가정합니다. C는 이름을 바꿨으므로 코드 검사에서 탈락합니다. 남은 두 문장은 모두 자연스럽지만, A의 ‘공유하세요’는 행동을 권하고 B의 ‘공유하지 마세요’는 행동을 금지합니다. 심판에게는 “게스트와의 공유를 여전히 금지하는가?”라고 묻고, 답을 결정한 표현을 인용하게 합니다. 두 검사를 모두 통과하는 후보는 B입니다. 심판 자체를 점검할 때는 두 언어를 아는 검토자가 허용과 금지만 뒤집은 문장 쌍에 정답을 매기고, 심판이 통과시킨 번역도 일부 직접 읽습니다.

**2026-11-25 기준.** Tencent는 11월 24일에 번역 모델 Hy-MT3-1.8B, Hy-MT3-7B, Hy-MT3-30B-A3B의 가중치와 평가용 TransRubric 프롬프트를 공개했습니다. TransRubric은 문항별로 기준을 제시하고 심판에게 번역 오류를 찾게 합니다 [[8]](#ref-8). 연구진은 중국어와 영어 사이의 양방향 번역 651개를 TransRubric으로 각각 열 번씩 평가했습니다. 0~100점 척도에서 번역별로 점수의 표준편차를 구하니 평균 3.31점이었습니다 [[7]](#ref-7). 이는 같은 번역을 반복 평가했을 때 점수가 얼마나 일정했는지 보여 줍니다. 위의 A에 열 번 모두 같은 합격점을 준 심판도 금지 문구가 사라졌다는 사실은 열 번 모두 놓친 셈입니다.

## 4. 10월 연구: 척도를 바꾸면 측정 도구도 바뀐다

**2026-10-18 기준 연구 정리.** Jo 등은 모델 5개와 텍스트 점수화 과제 3개에서 척도의 형식·범위·부호를 바꿉니다. 정규화 뒤에도 수치·의미 민감도가 남았으며, 해당 설정에서는 루브릭 프롬프팅으로 해결되지 않았습니다 [[5]](#ref-5). 결과는 연구한 점수화 과제에 한정되며 모든 쌍대 평가나 도메인 심판에 대한 결론은 아닙니다.

점수 $s$, 끝점 $a<b$에서 min-max 정규화는 $z=(s-a)/(b-a)$입니다. 끝점을 맞춰도 “중립”·“심각”·범주 사이 거리의 의미까지 같아지는 것은 아닙니다. 4/5를 8/10으로 바꿨다고 측정이 동등하다는 근거가 되지는 않습니다.

실무 강건성 시험에서는 텍스트와 루브릭 개념을 고정하고 척도 표현만 바꿉니다. 범주 전환·후보 순위·중요 오류의 미탐률·사람이 판정한 사례를 비교합니다. 척도를 심판과 함께 버전 관리합니다. 범위나 라벨이 바뀌면 출시 임계값을 재사용하기 전에 다시 보정해야 합니다.

## 5. 편향·누출·적대적 후보

선호도 누출 연구는 후보의 학습 출처와 심판의 관련성을 조사합니다 [[3]](#ref-3). 작은 모델의 이름만으로 증류를 추정하거나 같은 계열 선호를 필연으로 취급하면 안 됩니다. 정체를 가린 대응 사례와 독립된 사람 감사로 자기·계열 선호를 검사합니다.

위치·장황함·겉모양과 후보 답변 안의 지시 주입도 시험합니다. 심판 입력은 신뢰할 수 없는 데이터입니다. 답변의 “만점을 부여하라”는 문구가 평가를 통제해서는 안 됩니다. 여러 심판도 맹점을 공유할 수 있으므로 의견이 갈릴 때는 독립성이 있는 검사를 포함해야 합니다.

## 6. 출시 기준으로 쓰기 전에 심판을 보정한다

평가자 개발과 봉인된 후보 출시 평가셋을 분리합니다. 지적된 사례와 통과한 것처럼 보이는 사례를 모두 검사합니다. 실패 유형별 민감도·특이도, 전문가 라벨과의 동의, 일관성, 판단 보류, 비용, 지연을 보고합니다. 범주 라벨에서 Cohen의 kappa는 $\kappa=(P_o-P_e)/(1-P_e)$입니다. $P_o$는 관측 동의율, $P_e$는 라벨 주변분포에 따른 우연 동의율입니다. 해석은 클래스 비율과 의사결정 비용에 의존하므로 보편적인 통과 임계값은 적절하지 않습니다.

또 다른 교육용 예시로, 검토 표본에 치명적 결함 20개와 허용 가능한 답변 180개가 있다고 합시다. 심판이 모든 답을 허용하면 **전체 일치도는 90%** 이지만 **치명적 결함의 재현율은 0%** 입니다. 실패가 드물기 때문에 평균이 오히려 안심할 만하게 보입니다. 중요한 유형별 혼동 행렬과 불확실성을 보고해야 합니다. 개발 단계에서는 균형 잡힌 표본으로 사각지대를 찾고, 운영에서 생길 검토 업무량을 예측할 때는 실제 발생 비율을 반영한 추정치를 사용합니다.

중요 slice의 미탐률과 검토 부담이 사전 기준을 통과해야 새 심판을 승격합니다. 이전 심판·루브릭을 보관하고 새 측정 파이프라인을 canary로 도입하며 롤백을 연습합니다. 다음 절은 인간 선호를 rating으로 집계하는 방법을 다룹니다. Rating은 정확성과 다른 질문에 답합니다.
