# 17.1 학술 벤치마크

한 코드 생성 모델이 같은 문제에 대해 답을 스무 개 냈습니다. 열 개가 테스트를 통과했습니다. 스무 개 중 아홉 개를 뽑았는데 **모두 실패할 확률** 은 얼마일까요? 성공률을 소수점 첫째 자리까지 표시하면 100%로 반올림되지만, 아홉 개 모두 실패하는 조합은 열 가지나 됩니다. 무엇을 한 번의 시도로 세는지 정해야 거의 확실한 사건과 반드시 일어나는 사건을 구별할 수 있습니다. [직접 아홉 개를 뽑아 보기](#pass-at-k-example)

## 프론티어 벤치마크 지도

찾고 싶은 오류부터 정하세요. MMLU는 여러 학문 분야의 객관식 문항을 풉니다 [[1]](#ref-1). HumanEval은 모델이 작성한 함수를 테스트합니다 [[2]](#ref-2). SWE-bench는 저장소와 이슈를 주고 제안된 변경을 검증합니다 [[4]](#ref-4). 함수 하나가 테스트를 통과했는지와 저장소의 이슈가 해결됐는지는 서로 다른 증거로 판단합니다.

| 과제 유형 | 예시 | 점수를 비교하기 전에 확인할 조건 |
|---|---|---|
| 지식과 추론 | MMLU, GPQA | 동일한 문항, 보기 순서, 프롬프트, 채점 방식 |
| 수학 | GSM8K, MATH | 계산기 사용 여부, 같은 뜻의 수식과 단위 처리 |
| 코드 | HumanEval, MBPP, SWE-bench | 테스트 버전, 볼 수 있는 파일, 실행 환경, 시도 횟수 |
| 긴 문맥 | 멀리 떨어진 근거를 찾아 종합하는 과제 | 근거가 있던 위치, 입력을 자를 때 그 부분이 남았는지 |
| 에이전트와 도구 | WebArena, 운영체제 조작 과제 | 초기 상태, 권한, 도구가 실제로 일으킨 변화, 재시도 횟수 |
| 안전성 | 특정 정책에 맞춰 만든 사례 | 위협 모델, 채점 기준, 오류별 심각도 |

모델과 함께 실행한 도구와 제어 코드도 기록하세요. 코드 수정 에이전트에 검색 도구를 추가한 뒤 점수가 올랐다면 그 결과는 검색 도구를 갖춘 시스템의 성적입니다. HELM은 여러 과제에서 정확도와 효율 등 다양한 지표를 같은 평가 절차로 보고한 사례입니다 [[3]](#ref-3).

## 멀티모달 평가

열차 시간표 사진을 보고 9시 40분에 출발하는 열차를 묻는다고 합시다. 질문은 그대로 두고 사진 속 두 행을 바꿔 보세요. 답도 바뀐 시간표를 따라가나요? 사진을 아예 빼고 물었을 때와도 비교하세요. 모델이 사진을 읽었는지, 질문만 보고 그럴듯한 답을 골랐는지 가려낼 단서가 생깁니다.

이미지 해상도, 타일 분할, 자르기 순서, OCR과 압축 설정을 기록하세요. 언어나 접근성에 맞춰 입력을 바꿨다면 그 조건도 남겨 둡니다. 영상은 어떤 프레임과 음성 트랙을 사용했는지 확인합니다. 오답이 나오면 모델이 실제로 받은 입력을 보세요. 글자가 깨져 시간을 읽을 수 없는 경우와 선명한 시간표를 잘못 해석한 경우에는 고칠 곳이 다릅니다. 미디어를 보관할 때는 이용 허가와 보관 기한도 확인합니다.

## 평가 지표 설계

<a id="multiple-choice와-short-answer"></a>

### 객관식과 단답형

모델이 보기 번호를 직접 쓰게 할지, 각 보기 문자열의 로그 확률을 계산할지 먼저 정합니다. 어느 쪽이든 실제 프롬프트와 보기의 토큰을 남기세요. 보기 순서를 섞고 **정답 번호도 함께 바꿔** 채점하면 첫 번째 위치를 선호하는 경향을 검사할 수 있습니다. 답변 보류를 허용한다면 정확도의 분모와 실제로 답을 낸 비율을 함께 보고합니다.

<a id="generated-answer"></a>

### 생성형 답변

정답이 `0.5 kg`인 문제에서 채점기가 `500 g`을 오답으로 처리할 수 있습니다. 단위 변환을 허용할지, 어느 정도의 수치 오차를 인정할지 사전에 정하세요. 답을 뽑아내는 코드, 동치 판정 규칙, 평가자 프롬프트, 인용·형식 요건에 버전을 붙입니다. 채점기들의 판정이 달랐던 사례 중 여러 언어와 형식 오류가 포함된 표본을 골라 직접 확인합니다.

<a id="code와-agent"></a>

### 코드와 에이전트

HumanEval은 생성한 프로그램에 문제별 테스트를 실행해 통과 여부를 확인합니다 [[2]](#ref-2). 문제 $i$의 답을 $n_i$개 생성했고 그중 $c_i$개가 통과했다고 합시다. 이 답들에서 $k$개를 뽑으며 $1\leq k\leq n_i$입니다. 답에 번호를 매기면 번호 $k$개로 만들 수 있는 모든 조합의 확률이 같습니다. 모두 실패하려면 $n_i-c_i$개의 실패 답안 중에서만 골라야 합니다. 각 문제에 같은 가중치를 주고 $T$개 문제를 평가할 때의 추정량은 다음과 같습니다.

$$
\widehat p_i(k)=1-\frac{\binom{n_i-c_i}{k}}{\binom{n_i}{k}},
\qquad
\widehat{\mathrm{pass@}k}=\frac{1}{T}\sum_{i=1}^{T}\widehat p_i(k).
$$

이항계수는 조합의 수입니다. 뽑을 수 있는 답이 $k$개보다 적으면 값은 0입니다. 첫 식은 이미 생성한 답안에서 뽑을 때의 정확한 확률입니다. 각 문제의 답을 같은 디코딩 조건에서 독립적으로 생성했다면, 새로 답을 $k$개 생성할 때 하나 이상 통과할 확률의 불편추정량이기도 합니다. 답 하나만 내보내는 제품에는 그 답을 골라줄 선택기도 필요합니다. 선택기의 성능과 후보 전체의 생성·검증 비용을 함께 측정하세요.

<a id="pass-at-k-example"></a>

### 아홉 번 뽑아도 모두 실패할 수 있을까?

처음 예제에서 스무 답안 중 아홉 개를 뽑는 조합은 167,960가지입니다. 실패한 열 개 중 하나만 빼면 실패 답안 아홉 개가 남습니다. 어떤 답안을 빼느냐에 따라 열 가지이므로 모두 실패할 확률은 약 **0.00595%** 입니다. 아래 실습에서 $k$를 10으로 올려 보세요. 이제 모두 실패하는 조합은 하나뿐입니다. 11로 올리면 그마저 사라집니다.

점수를 보고할 때는 **문제별 확률** 을 평균하세요. A와 B 두 문제에 답을 네 개씩 냈는데 A의 답은 전부 통과하고 B의 답은 전부 실패했다고 합시다. $k=2$일 때 두 확률은 1과 0이므로 평균은 50%입니다. 답안 여덟 개를 먼저 합쳐 같은 식을 쓰면 78.6%가 나옵니다. 서로 *다른 문제*의 답을 하나씩 뽑은 경우까지 성공으로 셀 수 있기 때문입니다.

```python
from fractions import Fraction
from math import comb

def pass_at_k(n, c, k):
    if not (0 <= c <= n and 1 <= k <= n):
        raise ValueError("Expected 0 <= c <= n and 1 <= k <= n")
    return 1 - Fraction(comb(n - c, k), comb(n, k))

assert 1 - pass_at_k(20, 10, 9) == Fraction(10, 167960)
assert 1 - pass_at_k(20, 10, 10) == Fraction(1, 184756)
assert pass_at_k(20, 10, 11) == 1

tasks = [(4, 4), (4, 0)]
task_mean = sum(pass_at_k(n, c, 2) for n, c in tasks) / len(tasks)
pooled = pass_at_k(8, 4, 2)
print(task_mean, pooled)  # 1/2 11/14
```

에이전트는 환경에 남긴 결과로 성공 조건을 정하세요. 예약 **한 건** 을 잡는 과제라면 재시도까지 끝난 뒤 달력을 확인합니다. 예약 중복, 시간 초과, 예산 소진을 각각 어떻게 채점할지도 정해 둡니다.

## 통계적 비교

두 시스템은 고정된 평가 하네스(evaluation harness)에서 같은 문제를 풀게 합니다. 문제별로 두 결과를 짝지어 저장하면 한 문제에서는 나아졌지만 다른 문제에서는 퇴보한 경우도 보입니다. 성능 차이의 신뢰구간을 계산할 때는 표본을 수집한 단위를 유지하세요. 한 문의를 다섯 가지로 바꿔 물었다면 문의 전체를 한 묶음으로 재표집합니다. 같은 프롬프트에서 답을 더 생성하면 그 문제에 대한 정보는 늘지만 독립적인 문제 수는 그대로입니다.

쓸모 있다고 볼 최소 개선 폭, 동점과 다중 비교 처리 방식, 표본 크기의 근거를 결과를 보기 전에 정합니다. 중요한 도메인, 언어, 안전성, 도구 사용 조건마다 불확실성과 문제 수를 함께 보고하세요. 디코딩의 무작위성이 평가 대상이라면 시드를 바꿔 반복 실행합니다.

<a id="contamination과-dynamic-test"></a>

## 평가 오염과 동적 테스트

평가용 문항과 정답뿐 아니라 채점 기준, 의미가 유사한 문항, 교사 모델이 만든 변형까지 보호합니다. 최종 학습 데이터를 렌더링하고 토큰화한 뒤에도 이 목록과 대조하세요. 새 문제는 문항 자체가 노출될 기회를 줄이지만 기존 풀이 틀이나 과거 평가 로그가 답을 암시할 수 있습니다. 시점이 기록된 비공개 평가셋과 장기 비교용 고정 문항을 함께 유지합니다. [§17.4의 평가 오염 검사](/ko/chapter-17/contamination-issues)

## 실무용 벤치마크 설계 체크리스트

점수를 배포 결정에 쓰기 전에 다른 엔지니어가 같은 조건을 재현할 수 있는지 확인하세요.

- 모델 파일, 테스트와 하네스의 버전, 평가 분할, 실행 날짜를 고정합니다.
- 시스템 프롬프트, 예시, 템플릿, 사용 가능한 도구와 문맥 제한을 보관합니다.
- 샘플링 설정, $n$과 $k$, 토큰·시간 예산, 의존성, 실행 환경, 재시도 규칙을 기록합니다.
- 원문 출력, 실패, 시간 초과, 채점 판정과 각 지표의 분모를 남깁니다. 관측값이 누락된 경우의 처리 규칙도 밝힙니다.
- 짝지은 비교의 불확실성, 조건별 문제 수, 오염 검사, 지연 시간, 비용과 오류율을 보고합니다. 실제 서비스에서 나온 비공개 사례로 후보들을 다시 비교합니다.
