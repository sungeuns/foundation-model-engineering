# 10.1 사람의 피드백을 학습에 반영하는 과정

새 모델을 배포한 뒤 ‘좋아요’가 늘었습니다. 모델이 답변을 더 잘한 걸까요, 아니면 쉬운 요청이 새 모델에 더 많이 배정된 걸까요? 이 질문에 답하려면 좋아요 개수와 함께 어떤 요청에 어떤 답변이 표시됐고, 그중 몇 건에 사용자가 아무 평가도 남기지 않았는지 알아야 합니다.

---

<a id="offline과-online-feedback"></a>

## 평가자가 남긴 피드백과 실제 사용자의 반응

**오프라인 평가** 에서는 평가자가 공통 기준에 따라 모범 답변을 직접 작성하거나, 여러 답변의 순위를 매기거나, 특정 답변의 문제점을 짚습니다. 우열을 가릴 수 없으면 동점이나 판단 보류로 기록할 수 있습니다. 같은 항목을 여러 사람에게 맡겨 판단을 비교하기도 합니다. InstructGPT 연구에서는 사람이 쓴 모범 답변과 후보 답변의 순위를 수집했고, Bai 등의 연구에서는 평가자가 어시스턴트의 답변을 서로 비교했습니다. [[1]](#ref-1) [[2]](#ref-2)

**온라인 피드백** 은 사용자가 서비스에서 실제로 겪은 문제를 드러냅니다. 어떤 답변을 보게 되는지는 모델 배정 방식과 화면의 표시 순서에 달려 있습니다. 답변을 기다리다 떠난 사용자는 투표할 기회조차 놓칩니다. 후보 답변과 실제로 표시한 답변, 표시 위치, 배정 정책, 모델 버전, 디코딩 설정, 응답 지연과 오류, 투표 여부를 함께 기록합니다. 모델을 바꾼 효과를 확인하는 무작위 A/B 실험에서는 대상 요청을 모델에 무작위로 나눠 보내고 모델별 배정 확률(propensity)도 남깁니다. 검색 결과의 순위를 비교할 때는 두 모델이 정한 순서에 따라 결과를 섞어 보여 주는 실험도 가능합니다.

<a id="feedback-exposure-example"></a>

### 요청 유형별로 동률인데 전체 좋아요 비율은 왜 80%와 50%일까?

두 모델이 각각 요청 100건에 답했다고 합시다. 요청을 어느 모델에 보냈는지에 따른 차이만 살펴보기 위해, 답변이 표시될 때마다 사용자가 ‘좋아요’나 ‘싫어요’를 한 번씩 눌렀다고 가정합니다. 표의 분자는 좋아요 수이고 분모는 표시한 답변 수입니다.

| 요청 유형 | 모델 A | 모델 B |
| --- | --- | --- |
| 정형 요청 | 72/80 (90%) | 18/20 (90%) |
| 여러 단계가 필요한 요청 | 8/20 (40%) | 32/80 (40%) |
| 전체 요청 | 80/100 (80%) | 50/100 (50%) |

유형별 좋아요 비율은 두 모델이 같습니다. 그런데 정형 요청을 A에는 80건, B에는 20건 배정했습니다. 전체에서 생긴 30%포인트 차이는 이 배정만으로 설명됩니다. 실제 비교하려는 서비스에서 두 유형이 절반씩이라면, 같은 비중을 적용한 좋아요 비율은 두 모델 모두 `0.5 × 90% + 0.5 × 40% = 65%`입니다. 실제 로그에서는 아무 평가도 남기지 않은 경우를 ‘싫어요’와 구분합니다. 요청 유형의 비중을 맞춰도 평가를 건너뛴 사용자가 그 답변을 어떻게 평가했을지는 알 수 없습니다.

학습에 쓸 답변을 고를 때도 선택 편향이 생길 수 있습니다. 아래 실습에서 점수 임계값을 8로 둔 채 **다음 후보** 를 두 번 눌러 보세요.

학습 후보에 들어가는 답변은 9.2점을 받은 첫 번째 답변뿐입니다. 9.5점을 받은 두 번째 답변은 검증을 통과하지 못했습니다. 이런 실패 사례를 남겨야 다른 답변과 비교하거나 원인을 조사할 수 있습니다. 성공한 사례만 모으면 높은 점수를 받고도 틀린 답을 낸 경우를 놓칩니다.

<a id="annotation-계약"></a>

## 평가자가 따를 기준과 기록 항목

과업별 평가 지침에는 정답과 부분 정답, 위험한 답변, 답할 수 있는데도 거절한 답변, 검증할 수 없는 답변, 과업 범위를 벗어난 답변의 예를 넣습니다. 두 답변의 수준이 같으면 **동점**, 평가할 근거나 전문 지식이 부족하면 **판단 보류** 로 기록합니다. 어느 쪽이든 억지로 승자를 고르면 잘못된 선호가 학습 데이터에 남습니다. 사람의 판단과 그 판단을 학습한 보상 모델에는 각각 한계가 있습니다. [[3]](#ref-3)

평가자가 기준을 같은 방식으로 적용하는지 확인하려면 전문가가 미리 판정한 사례를 함께 채점해 봅니다. 분야와 난이도별로 평가자 간 일치도를 구하고, 중요한 항목에서 의견이 갈리면 근거를 검토해 최종 판정을 내립니다. 평가 지침의 버전, 무작위로 정한 답변 순서, 평가자의 자격, 평가 시각, 확신도, 판정 사유를 남깁니다. 인구 집단, 언어, 접근성 요구, 분야에 따라 판단이 일관되게 달라지는지도 살핍니다. 민감한 정보는 당사자가 동의한 정책 범위에서만 사용합니다.

로그를 평가자에게 보여 주거나 학습에 쓰기 전에 수집 동의, 보관 기간, 접근 권한, 삭제 절차, 재사용 범위를 정합니다. 개인식별정보(PII), 기밀, 인증 정보, 제3자의 콘텐츠는 찾아내어 가립니다. 원본 서비스 로그는 학습 말뭉치와 분리합니다. 승인된 절차로 가공하고 데이터 목록과 버전을 기록한 뒤에야 학습 후보에 넣습니다.

<a id="feedback-loop를-만들지-않는-active-learning"></a>

## 능동 학습에서 어려운 사례만 고르게 되는 문제

사람이 검토할 수 있는 건수에는 한계가 있습니다. 모델의 판단이 불확실하거나 평가자끼리 의견이 갈린 요청, 처음 보는 유형, 트래픽 분포가 바뀐 구간, 오류의 피해가 큰 사례를 우선 검토합니다. 평소에 들어오는 요청에서도 일정 확률로 표본을 뽑습니다.

각 요청이 **검토 대상으로 뽑힐 확률** 은 **모델에 배정될 확률** 과 별개이므로 따로 기록합니다. 전체 서비스 품질을 추정할 때는 각 유형의 실제 요청 비중에 따라 결과를 합치거나, 개별 요청의 검토 확률 차이를 가중치에 반영합니다. 어려운 사례를 집중 검토하면 학습 자료를 모으기엔 좋지만, 그 사례들의 단순 평균으로는 일반 사용자가 경험하는 품질을 알기 어렵습니다.

정답을 검증할 수 있는 과업이라면 사람의 선호와 실제 결과를 대조합니다. 단위 테스트를 통과했는지, 도구 실행 뒤 상태가 맞는지, 인용한 출처가 주장을 뒷받침하는지, 실행 환경에서 목표를 달성했는지 확인합니다. 설명이 유창해 보상 모델이 높은 점수를 주었더라도 재현 가능한 검사에서 드러난 실패는 그대로 기록합니다.

## 누출 없는 실패 사례 개선 과정

서비스에서 발견한 실패는 같은 문제가 되풀이되는지 확인하는 데 유용합니다. 다만 그 사례로 학습한 뒤 표현만 바꿔 시험하면, 처음 보는 문제에도 대응할 수 있는지는 알 수 없습니다.

1. 당시의 프롬프트와 문맥, 도구 상태, 기대한 동작, 모델과 관련 파일의 버전, 실패 유형을 기록합니다.
2. 데이터를 나누기 전에 원본과 이를 바꿔 쓴 문장, 관련 대화, 같은 사례에서 생성한 변형을 하나의 군집에 묶습니다.
3. 군집 전체를 평가용으로 격리하거나 학습 후보에 넣습니다. 학습에 썼다면 원본과 변형으로 만든 회귀 검사에 모두 ‘학습에 노출됨’이라고 표시합니다.
4. 출시 평가는 별도로 보관한 미노출 군집에서 수행합니다. 이 군집의 프롬프트, 채점 기준, 교사 모델이 만든 변형도 학습에서 제외합니다.
5. 알려진 문제가 해결됐는지와 미노출 군집에서도 개선됐는지를 구분해 보고합니다. 기존 능력과 안전성이 유지되는지도 함께 봅니다.

## 데이터 채택, 학습, 출시를 판단하는 기준

데이터를 학습에 넣을 기준과 학습을 마친 모델을 배포할 기준은 따로 정합니다. 데이터는 출처별로 수집량 대비 채택 비율을 집계하고, 동점과 판단 보류의 비율, 평가자 간 일치도, 자동 평가기 간 불일치, 개인정보 때문에 제외한 건수, 주요 요청 유형이 얼마나 포함됐는지 확인합니다.

학습을 시작할 때는 데이터 목록과 버전, 군집별 분할, 참조 모델과 비교 기준 모델의 버전, 토크나이저와 템플릿, 학습 목적함수, 난수 시드를 고정합니다. 중단한 지점에서 이어갈 수 있도록 체크포인트에는 최적화기, 학습률 스케줄러, 손실 스케일러, 난수 생성기, 표본 추출기의 상태와 데이터를 읽은 위치도 저장합니다.

출시 전에는 디코딩 설정을 고정하고 같은 요청에서 나온 두 모델의 답변을 짝지어 비교합니다. 성능 차이의 불확실성도 함께 추정합니다. 목표 과업의 품질, 기존 능력 유지, 안전성과 과도한 거절, 출력 형식과 도구 사용의 정확성, 응답 시간, 비용, 오류율이 기준을 충족하는지 확인합니다. 특히 중요한 요청 유형에서 실패하면 전체 평균이 좋아도 출시를 보류합니다. 사용자에게 답변을 보여 주지 않는 병행 시험부터 소수 대상 배포, 트래픽 확대까지 각 단계에서 어떤 지표를 얼마 동안 관찰한 뒤 자동 중단할지 정합니다. 문제가 생기면 마지막으로 정상 동작을 확인한 버전으로 되돌릴 수 있도록 복구 절차를 미리 연습합니다.

<details>
<summary>Quiz 2: 평가자가 동점과 판단 보류를 구분해 기록해야 하는 이유는 무엇인가요?</summary>
*동점은 두 답변을 비교해 보니 수준이 같다는 뜻입니다. 판단 보류는 근거나 전문 지식이 부족해 우열을 가릴 수 없다는 뜻입니다. 승자를 강제로 고르면 어느 경우인지 알 수 없고 학습 데이터에는 실제로 관찰하지 않은 선호가 남습니다.*
</details>

*표현을 바꿔도 원본을 통해 알려진 정보가 남습니다. 관련 사례를 같은 군집으로 묶고 학습에 썼다면 그 회귀 검사는 이미 노출됐다고 표시합니다. 일반화 성능은 따로 보관한 미노출 군집에서 평가합니다.*

*판단이 불확실한 사례를 주로 보면 실패를 찾을 수 있지만, 그 결과를 단순 평균하면 평소 품질을 잘못 추정합니다. 일반 요청을 알려진 확률로 뽑고 평가가 누락된 경우까지 고려하면, 개선 효과가 그 요청을 보낸 사용자에게도 나타나는지 확인할 수 있습니다.*
</details>
