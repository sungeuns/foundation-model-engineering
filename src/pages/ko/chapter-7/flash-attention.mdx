# 7.4 FlashAttention 1·2·3의 메모리 접근과 병렬화

어텐션 헤드 하나가 토큰 4,096개를 처리하면 쿼리와 키 사이에 $4,096^2$개의 점수가 생깁니다. 이 행렬 하나를 FP32로 저장하면 **64 MiB** 가 필요합니다. 배치 크기 2, 헤드 수 8이면 점수 행렬만 **1 GiB** 입니다. 점수를 계산하는 연산과, 곧 버릴 전체 행렬을 메모리에 쓰고 다시 읽는 작업은 별개의 비용입니다.

FlashAttention은 어텐션의 계산 순서를 바꿔 메모리 접근을 줄입니다 [[1]](#ref-1). 빠른 온칩 메모리에서 타일 단위로 계산하고 출력을 누적해 전체 점수·확률 행렬을 GPU 고대역폭 메모리(HBM)에 저장하지 않습니다. 모든 토큰 쌍을 계산하므로 연산량은 여전히 시퀀스 길이의 제곱에 비례합니다. [키 네 개를 나누어 계산하는 예제](#online-softmax-tiles)에서 어떤 값만 남겨 두면 앞 타일을 버릴 수 있는지 확인해 보세요.

## 1. 중간 행렬과 전체 메모리를 따로 계산하기

헤드 하나에 대해 $Q,K\in\mathbb R^{L\times d}$, $V\in\mathbb R^{L\times d_v}$ 로 둡니다. $L$ 은 시퀀스 길이, $d$ 는 query/key 차원, $d_v$ 는 value 차원입니다. 마스크를 잠시 생략하면

$$
S=QK^\top/\sqrt d,\qquad P=\operatorname{softmax}(S),\qquad O=PV.
$$

Softmax는 각 query의 key 방향으로 적용합니다. 단순한 구현은 각각 $[L,L]$ 형태인 $S$ 와 $P$ 를 메모리에 만듭니다. 배치 크기 $B$, 헤드 수 $H$, 원소당 바이트 수 $s$ 일 때 이런 할당 **하나** 는 $BHL^2s$ 바이트입니다. $B=2$, $H=8$, $L=4096$, $s=4$ 이면 1,073,741,824바이트, 즉 1 GiB입니다. FP16은 이 할당의 크기를 절반으로 줄입니다. 두 행렬이 동시에 존재하면 두 배가 필요하지만, 연산 융합이나 버퍼 재사용에 따라 실제 최대 사용량은 달라집니다.

이것이 모델 전체의 메모리는 아닙니다. 파라미터, Q/K/V, 다른 활성값, 출력, 임시 버퍼와 할당자 여유 공간도 필요합니다. 학습에는 그래디언트와 옵티마이저 상태도 필요하며 샤딩·재계산 설정이 크기에 영향을 줍니다. Attention 중간 행렬을 없앴다고 전체 모델이 반드시 메모리에 들어가거나 모든 형태에서 대역폭이 병목이 되는 것은 아닙니다.

## 2. FlashAttention-1: 모든 점수를 저장하지 않고 누적하기

### 온라인 softmax: 기준점을 바꾸되 비율은 유지하기

모든 점수에서 같은 상수를 빼도 softmax 결과는 같습니다. 온라인 정규화는 점수를 나누어 처리하면서 이 성질을 활용합니다 [[5]](#ref-5). Query 하나에 대해 $z_j$ 를 스케일링된 점수, $v_j$ 를 대응하는 value 벡터라 합시다. 지금까지 처리한 key의 최댓값 $m$, 분모 $\ell$, 정규화 전 출력 벡터 $u$ 를 유지합니다. 새 타일 $T$ 를 만나면

$$
\begin{aligned}
m'&=\max\bigl(m,\max_{j\in T}z_j\bigr), & a&=e^{m-m'},\\
p_j&=e^{z_j-m'}, & \ell'&=a\ell+\sum_{j\in T}p_j,\\
u'&=au+\sum_{j\in T}p_jv_j. &&
\end{aligned}
$$

$m=-\infty$, $\ell=0$, $u=0$ 에서 시작하고 마지막에 $u/\ell$ 을 반환합니다. 뒤의 타일에서 더 큰 최댓값이 나오면 $a$ 를 곱해 기존 합 **둘 다** 새 기준점으로 옮깁니다. 각 타일이 자기 최댓값을 기준으로 구한 분모가 같더라도, 같은 기준으로 환산하면 두 타일의 비중은 달라질 수 있습니다.

### 타일별 출력을 평균내면 될까요?

쿼리 하나가 $[2,2,10,10]$이라는 값 네 개를 읽습니다. 앞쪽 키 두 개의 점수는 1000, 뒤쪽 키 두 개의 점수는 $1000+\ln 3$입니다. 지수를 취하면 뒤쪽 키 하나에 앞쪽 키의 세 배만큼 가중치가 붙습니다. 네 키를 한꺼번에 계산한 출력은 $(2+2+3\times10+3\times10)/(1+1+3+3)=8$입니다.

키를 두 개씩 묶어 봅시다. 각 타일 안에서는 두 점수가 같으므로 자기 최댓값을 빼고 계산한 분모는 양쪽 모두 2입니다. 타일별 출력은 2와 10이고, 단순 평균은 6입니다. 하지만 두 번째 타일의 실제 비중은 첫 타일의 세 배입니다. 더 큰 점수가 나오면 기준도 달라집니다. 앞에서 구한 분모 2와 분자 4에 각각 $1/3$을 곱한 뒤 두 번째 타일의 값을 더해야 합니다.

상대 가중치를 3배로 두고 타일당 키 수를 3으로 바꿔 보세요. 첫 타일의 출력은 6.8, 마지막 타일의 출력은 10이어서 단순 평균이 8.4로 바뀝니다. 키를 어떻게 나누든 네 키 전체의 출력은 8입니다.

> **의도적으로 단순화한 점화식 예제.** CPU FP64에서 query 하나와 유한한 마스크 없는 점수만 처리합니다. 점화식을 쉽게 살펴보도록 점수 한 행은 미리 저장합니다. FlashAttention GPU 구현은 아닙니다. Q/K 타일링, causal/padding 마스크, dropout, 역전파 재계산, 스케줄링, 성능 측정을 생략합니다. 전부 마스킹된 타일·행에는 별도 처리가 필요하며 이 예제에서는 거부합니다.

```python
import math
import torch

@torch.no_grad()
def online_attention_row(scores, values, tile_size=2):
    """Finite CPU FP64 scores [keys], values [keys, value_dim]; no mask."""
    if scores.ndim != 1 or values.ndim != 2 or len(scores) != len(values):
        raise ValueError("expected scores[keys], values[keys,value_dim]")
    if len(scores) == 0 or tile_size <= 0:
        raise ValueError("need at least one key and a positive tile size")
    if scores.device.type != "cpu" or values.device.type != "cpu":
        raise ValueError("this teaching example is CPU-only")
    if scores.dtype != torch.float64 or values.dtype != torch.float64:
        raise ValueError("use FP64 to check the recurrence")
    if not torch.isfinite(scores).all() or not torch.isfinite(values).all():
        raise ValueError("masked/nonfinite entries are outside this example")
    maximum = scores.new_tensor(float("-inf"))
    denominator = scores.new_zeros(())
    numerator = values.new_zeros(values.shape[1])
    for start in range(0, len(scores), tile_size):
        block = scores[start:start + tile_size]
        new_maximum = torch.maximum(maximum, block.max())
        correction = torch.exp(maximum - new_maximum)
        weights = torch.exp(block - new_maximum)
        denominator = correction * denominator + weights.sum()
        numerator = correction * numerator + weights @ values[start:start + tile_size]
        maximum = new_maximum
    return numerator / denominator

scores = torch.tensor([1000., 1000., 1000. + math.log(3), 1000. + math.log(3)], dtype=torch.float64)
values = torch.tensor([[2.], [2.], [10.], [10.]], dtype=torch.float64)
expected = torch.softmax(scores, dim=0) @ values
for tile_size in (1, 2, 3, 4):
    actual = online_attention_row(scores, values, tile_size)
    torch.testing.assert_close(actual, expected, rtol=1e-12, atol=1e-12)
print(expected.item())  # approximately 8.0
```

점수에 공통으로 들어간 1000 때문에 FP64에서도 지수를 곧바로 계산하면 오버플로가 발생합니다. 누적 최댓값을 빼면 네 가지 타일 크기에서 모두 유한한 결과가 나옵니다. 타일당 키가 세 개일 때는 마지막에 키 하나만 남는 경우도 검증합니다.

### 재계산과 ‘정확한 attention’의 의미

FlashAttention은 필요한 입력·출력·행별 통계량을 보존하고, 역전파에서 전체 $P$ 를 저장하는 대신 확률 타일을 다시 계산합니다 [[1]](#ref-1). 산술 연산을 더 수행하는 대신 HBM 이동과 저장 공간을 줄이는 교환입니다. 이 교환이 얼마나 유리한지는 워크로드에 달렸습니다.

‘정확한 attention’은 key를 일부 버리거나 softmax를 다른 함수로 근사하지 않는다는 뜻입니다. 부동소수점 구현 간 **비트 단위 동일성** 을 보장하지는 않습니다. 누적 순서와 정밀도가 달라지면 반올림도 달라질 수 있습니다. FP8 양자화는 별도의 근사 오차를 추가하므로 따로 평가해야 합니다.

## 3. FlashAttention-2: 연산 장치에 일을 더 고르게 배분하기

FlashAttention-2는 thread block과 warp 사이의 작업 배분을 바꿉니다 [[2]](#ref-2). 행렬곱 이외 연산을 줄이고, 한 헤드 안에서도 query block별로 일을 병렬화하며, warp 사이의 공유 메모리 통신을 줄입니다. 배치·헤드 방향의 병렬성만으로 GPU를 충분히 채우지 못할 때 이런 변화가 중요해집니다.

논문은 A100 실험에서 기존 FlashAttention 대비 약 두 배의 커널 속도와 이론적 최대 FLOPs/s의 50–73%를 보고합니다. 특정 구성에서 측정한 결과이며, 모든 시퀀스 길이·dtype·GPU에 대한 약속은 아닙니다. Attention 커널이 빨라져도 애플리케이션에서 그 커널이 담당하는 부분만 직접 빨라집니다.

## 4. FlashAttention-3: Hopper의 비동기 연산에 맞춘 스케줄링

FlashAttention-3는 Hopper의 비동기 데이터 이동과 행렬 연산을 활용합니다 [[3]](#ref-3). TMA는 다른 작업이 진행되는 동안 타일을 옮기고, WGMMA는 warpgroup 단위 비동기 행렬곱을 지원합니다. 데이터 전송과 계산을 겹치고 행렬곱과 softmax도 교차 실행합니다. 더 많은 지연을 숨기려는 설계이지, 모든 조건에서 I/O 대기를 완전히 없애는 보장은 아닙니다.

FP8 경로는 블록 양자화와 incoherent processing으로 수치 오차도 제어합니다. 비교 대상 FP8 attention 구현보다 수치 오차가 작다는 결과가 모든 모델 능력을 그대로 보존한다는 뜻은 아닙니다. 처리량과 별도로 수치적 일치도와 태스크 품질을 검증해야 합니다.

아래 표는 각 논문의 핵심 설계를 정리한 것입니다. 현재의 하드웨어 지원표나 서로 다른 하드웨어의 성능 비교표가 아닙니다.

| 논문 | 핵심 변화 | 이 설계만으로 보장하지 않는 것 |
|---|---|---|
| FlashAttention-1 (2022) [[1]](#ref-1) | Attention을 타일로 나누고 중간값을 재계산 | 선형 산술 연산량이나 OOM 방지 |
| FlashAttention-2 (2023) [[2]](#ref-2) | 병렬 작업 분배와 행렬곱 이외 연산 개선 | 모든 형태·애플리케이션에서 같은 속도 향상 |
| FlashAttention-3 (2024) [[3]](#ref-3) | Hopper 연산 중첩과 스케일을 제어한 FP8 경로 | 저정밀도 오차 제거나 모든 태스크 품질 보존 |

## 5. PyTorch SDPA: 실제 Flash 실행을 확인하기

**2026-11-18 기준**, PyTorch 2.15 문서는 `sdpa_kernel` 을 통한 백엔드 선택을 설명합니다 [[4]](#ref-4). 선택 결과는 설치된 소프트웨어, GPU, dtype, 텐서 형태, attention 옵션에 달렸습니다. 전역 설정에서 Flash를 켠 사실만으로 특정 연산이 Flash를 사용했다고 결론 내릴 수 없습니다.

> **CUDA 디스패치 예제이며, 이 책의 CPU smoke 실행에서는 GPU 검증하지 않았습니다.** 고정 길이 causal 추론에 FP16/BF16과 Flash 백엔드를 강제합니다. 가변 길이 padding, 학습 그래디언트, dropout, 성능 측정을 생략합니다. 지원되지 않는 입력은 오류를 내야 하며, 실행 경로가 확인되지 않은 결과로 성능을 주장하면 안 됩니다.

```python
import torch
import torch.nn.functional as F
from torch.nn.attention import SDPBackend, sdpa_kernel

if not torch.cuda.is_available():
    raise RuntimeError("Flash SDPA requires a supported CUDA GPU")

device = torch.device("cuda")
dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
batch, heads, sequence, head_dim = 2, 8, 2048, 64

q = torch.randn(batch, heads, sequence, head_dim, device=device, dtype=dtype)
k = torch.randn_like(q)
v = torch.randn_like(q)

with torch.inference_mode(), sdpa_kernel(backends=[SDPBackend.FLASH_ATTENTION]):
    output = F.scaled_dot_product_attention(
        q, k, v,
        dropout_p=0.0,
        is_causal=True,
    )

assert output.shape == q.shape
assert output.dtype == dtype and torch.isfinite(output).all()
print(torch.backends.cuda.flash_sdp_enabled(), output.shape, output.dtype)
```

출력되는 `flash_sdp_enabled()` 는 설정 플래그입니다. 실제 실행은 프로파일러나 커널 기록으로 확인합니다. 작은 텐서에서 dtype에 맞는 허용 오차로 math 백엔드와 출력을 비교하고, 학습에 쓴다면 그래디언트도 비교합니다. GPU, 프레임워크/CUDA 버전, 입력 형태, 마스크, 정밀도를 결과와 함께 기록합니다.

`dropout_p` 는 명시적으로 지정해야 합니다. SDPA는 모듈의 학습 모드와 무관하게 전달된 확률을 적용합니다. `is_causal=True` 는 가변 길이 배치의 padding을 제거하지 않습니다. 지원되는 causal/padding 결합 마스크나 가변 길이 표현을 사용하고 백엔드 실행 조건을 다시 확인합니다 [[4]](#ref-4).

시간을 측정할 때는 워밍업과 올바른 동기화를 수행하고 입력·마스크·정밀도를 맞춥니다. Prefill과 토큰별 decode는 query 형태와 병목이 다르므로 분리해서 측정합니다. 커널뿐 아니라 전체 워크로드의 지연, 처리량, 최대 메모리도 기록합니다. 목표 커널이 처리하지 못하는 구성을 위한 검증된 대체 경로를 유지합니다.

<summary>Quiz 4: 128,000토큰의 FP16 점수 행렬 하나는 32.768 GB입니다. FlashAttention이면 반드시 메모리에 들어가나요?</summary>
*그 전체 중간 행렬을 HBM에 저장하지 않지만 파라미터, Q/K/V, 출력, 다른 활성값, 작업 버퍼와 학습 상태는 여전히 메모리를 사용합니다. 조밀한 attention의 쌍별 연산량도 여전히 이차적입니다. 컨텍스트 한도를 정하기 전에 전체 워크로드를 측정해야 합니다.*
</details>

<details>
<summary>Quiz 5: `flash_sdp_enabled() == True` 이면 측정한 속도 향상이 Flash에서 나왔다고 볼 수 있나요?</summary>
*아닙니다. 백엔드가 활성화돼 있는지 알려주는 설정입니다. 필요하면 원하는 백엔드를 강제하고 실제 실행 커널을 확인한 뒤 조건을 맞춰 비교해야 합니다. 대체 경로 실행, 다른 마스크, 바뀐 dtype은 비교를 무효로 만들 수 있습니다.*
</details>
