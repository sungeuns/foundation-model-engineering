# 7.2 ZeRO로 학습 상태 분할하기

GPU 여덟 대로 학습할 때 Adam 옵티마이저도 여덟 벌 필요할까요? 일반적인 분산 데이터 병렬(DDP) 학습에서는 각 프로세스가 서로 다른 예제를 처리합니다. 그래디언트를 모아 평균을 내면 모든 프로세스가 같은 값으로 가중치 전체를 갱신합니다. GPU를 늘려 처리량을 높일 수는 있지만, GPU 한 대에 필요한 모델 상태 메모리는 그대로입니다. ZeRO는 각 상태를 맡을 프로세스(랭크)를 나눕니다. [[1]](#ref-1)

<a id="1-gpu-메모리의-해부학-the-anatomy-of-gpu-memory"></a>

## 1. 파라미터 하나당 16바이트는 어디에 쓰일까?

이 예제에서는 학습용 가중치와 그래디언트에 각각 2바이트, 옵티마이저가 갱신하는 FP32 마스터 가중치에 4바이트, Adam의 두 FP32 모멘트에 8바이트를 씁니다. 두 번째 모멘트는 그래디언트의 제곱을 추적합니다. 그래디언트 정밀도가 다르거나 별도의 마스터 가중치를 두지 않는 구현이라면 합계도 달라집니다. [[1]](#ref-1)

파라미터 수를 $\Phi$라고 하면 모델 상태는 모두 $16\Phi$바이트입니다. 이 중 마스터 가중치와 옵티마이저가 쓰는 부분이 $12\Phi$바이트입니다. 700억 파라미터라면 일반 DDP에서 **GPU 한 대마다** 1,120GB가 필요합니다. 여기서 1GB는 10억 바이트입니다. 실제 최대 메모리를 추정할 때는 시퀀스 길이, 저장할 활성값과 재계산 범위, 통신 버퍼, 메모리 할당기의 여유 공간도 따로 계산합니다.

<a id="2-zero의-철학-중복의-제거"></a>

## 2. 각 랭크는 어느 가중치를 맡을까?

<a id="zero-shard-ownership"></a>

### 네 랭크에서 5번과 6번 가중치 따라가기

가중치 여덟 개에 1번부터 8번까지 번호를 붙이고 두 개씩 나눕니다. 상태를 분할하면 랭크 0은 1·2번, 랭크 1은 3·4번, 랭크 2는 5·6번, 랭크 3은 7·8번을 맡습니다. 표는 **랭크 2에 상주하는 상태** 를 보여 줍니다. P는 가중치, G는 그래디언트, O는 마스터 가중치를 포함한 옵티마이저 상태입니다. 한 단계 내려갈 때마다 어느 열에서 1–8이 5–6으로 바뀌는지 보세요. [[1]](#ref-1)

| 단계 | P | G | O | 바이트 |
| --- | --- | --- | --- | ---: |
| DDP | 1–8 | 1–8 | 1–8 | 128 |
| ZeRO-1 | 1–8 | 1–8 | 5–6 | 56 |
| ZeRO-2 | 1–8 | 5–6 | 5–6 | 44 |
| ZeRO-3 | 5–6 | 5–6 | 5–6 | 32 |

예를 들어 ZeRO-2에서는 2바이트 가중치 여덟 개, 2바이트 그래디언트 두 개, 12바이트짜리 옵티마이저 상태 두 개가 남습니다. 합계는 $16+4+24=44$바이트입니다. 통신하는 동안에는 각 랭크가 맡은 조각보다 큰 임시 버퍼가 필요할 수 있습니다.

**CPU에서 직접 확인하기.** <a href={withBasePath('/labs/zero_shards.py')} download="zero_shards.py">네 랭크로 실행하는 PyTorch 코드</a>는 FP32 가중치 여덟 개의 초깃값을 1부터 8까지로 정합니다. 랭크 $r$은 이차 손실 $(r+1)\sum_j w_j^2/2$의 그래디언트를 구합니다. 각 랭크의 기여도는 같습니다. Reduce-scatter로 그래디언트 네 벌의 합을 구해 각 랭크에 두 개씩 나누고, 랭크 수인 4로 나누어 평균을 냅니다. 랭크 2가 받는 평균 그래디언트는 12.5와 15입니다. 학습률 0.1로 SGD를 한 번 적용하면 가중치 5와 6이 **3.75와 4.5** 가 됩니다. All-gather로 결과를 모은 뒤, 모든 랭크에서 여덟 개를 분할 없이 한 번에 갱신한 값과 비교합니다.

```bash
torchrun --standalone --nproc-per-node=4 zero_shards.py
```

Linux에서 CPU용 PyTorch 2.15.0과 Gloo 백엔드로 실행한 예제입니다. 실제 그래디언트로 두 집합 통신 연산의 동작을 확인합니다. 위 표의 바이트 수는 혼합 정밀도와 Adam을 가정해 따로 계산한 값입니다. [[4]](#ref-4)

### Stage 1: Optimizer State Partitioning ($P_{os}$)

데이터 병렬 랭크가 $N$개라면 각 랭크가 옵티마이저 상태의 $1/N$을 맡고 해당 가중치를 갱신합니다. 가중치와 그래디언트는 여전히 전부 보관합니다. 랭크당 모델 상태는 $4\Phi+12\Phi/N$바이트입니다.

### Stage 2: Gradient Partitioning ($P_{os+g}$)

그래디언트가 준비되면 묶음(버킷) 단위로 합산해 각 항목을 맡은 랭크에 보낼 수 있습니다. 각 랭크는 자기가 맡은 그래디언트만 남겨 가중치를 갱신합니다. 모델 상태는 $2\Phi+14\Phi/N$바이트로 줄어듭니다. 이상적인 스케줄에서 1·2단계의 통신량은 DDP와 같을 수 있습니다. 실제 소요 시간은 버킷 크기와 통신·계산을 얼마나 겹칠 수 있는지에 따라서도 달라집니다. [[1]](#ref-1)

### Stage 3: Parameter Partitioning ($P_{os+g+p}$)

이제 가중치 자체도 나눠 보관합니다. 층 하나를 계산할 때는 그 연산에 필요한 가중치를 각 랭크에 모읍니다. 역전파 때까지 들고 있으면 메모리를 더 쓰고, 일단 해제하면 다시 모으는 통신 비용이 듭니다. 랭크마다 상주하는 모델 상태는 $16\Phi/N$바이트입니다. 원 논문의 단순화한 스케줄에서 통신량은 DDP의 약 1.5배입니다. 실제 통신량은 그룹 크기, 미리 가져올 범위, 보관 정책에 따라 달라집니다. [[1]](#ref-1)

## 3. GPU 한 대의 80GB에 무엇이 들어갈까?

700억 파라미터, 랭크 여덟 개라는 기본 설정에서 ZeRO-3의 모델 상태는 GPU당 140GB입니다. 표에 표시된 80GB 예산을 이미 넘습니다. 랭크를 16개로 늘리면 이 값은 70GB입니다. 남은 10GB에 실제 순전파와 역전파를 담을 수 있는지는 별도로 측정해야 합니다.

## 4. GPU의 한계를 넘어서: ZeRO-Offload & ZeRO-Infinity

GPU를 더 붙일 수 없다면 상태를 어디에 보관할지 바꿀 수 있습니다. ZeRO-Offload는 옵티마이저 상태와 연산을 CPU로 옮깁니다. 이때 GPU가 기다리는 시간을 줄이려면 PCIe 전송과 CPU 갱신을 계산과 겹쳐야 합니다. 갱신을 한 스텝 늦추는 방식은 학습 알고리즘까지 바꿉니다. [[2]](#ref-2)

ZeRO-Infinity는 CPU 메모리와 NVMe도 활용해 가중치 등을 필요한 시점에 GPU로 가져옵니다. 저장 공간이 충분해도 다음 층을 계산할 때까지 전송을 끝내지 못하면 GPU가 기다립니다. [[3]](#ref-3)

## 5. 엔지니어링 구현: 초기화도 메모리 계획의 일부

**한계:** 이 간결한 DeepSpeed 예제는 초기화와 인과 손실 의미만 설명합니다. 실제 Transformer, 패딩 마스크, 혼합 정밀도 정책, 검증, 프로덕션 체크포인트 조정이 없으므로 상용 수준 코드가 아닙니다.

ZeRO-3는 전체 모델을 만드는 도중 이미 소진된 메모리를 구할 수 없습니다. 대형 파라미터를 `deepspeed.zero.Init` 안에서 인스턴스화하거나 동등한 FSDP/meta-device 초기화 경로를 사용하여 생성 시점부터 가중치를 분할합니다.

```python
import torch
import torch.nn as nn
import torch.nn.functional as F
import torch.distributed as dist
import deepspeed
from torch.utils.data import Dataset

class SimpleLLM(nn.Module):
    def __init__(self, vocab_size=32_000, d_model=4_096):
        super().__init__()
        self.embed = nn.Embedding(vocab_size, d_model)
        self.layers = nn.Sequential(*[
            nn.Linear(d_model, d_model, bias=False) for _ in range(24)
        ])
        self.lm_head = nn.Linear(d_model, vocab_size, bias=False)

    def forward(self, token_ids):
        return self.lm_head(self.layers(self.embed(token_ids)))

class TokenDataset(Dataset):
    def __len__(self): return 1_000
    def __getitem__(self, index):
        generator = torch.Generator().manual_seed(index)
        return torch.randint(0, 32_000, (513,), generator=generator)

def train():
    deepspeed.init_distributed()
    with deepspeed.zero.Init(config_dict_or_path="ds_config.json"):
        model = SimpleLLM(vocab_size=32_000, d_model=4_096)

    engine, _, loader, _ = deepspeed.initialize(
        model=model,
        model_parameters=model.parameters(),
        training_data=TokenDataset(),
        config="ds_config.json",
    )

    for tokens in loader:
        tokens = tokens.to(engine.device)
        inputs, targets = tokens[:, :-1], tokens[:, 1:]  # 인과 시프트
        logits = engine(inputs)
        loss = F.cross_entropy(logits.float().flatten(0, 1), targets.flatten())
        engine.backward(loss)
        engine.step()
        if dist.get_rank() == 0:
            print(float(loss))
        break  # All ranks stop together after this demonstration step.
```

해석된 전역 배치는 microbatch × accumulation × data-parallel 차수와 같아야 합니다. 상주 샤딩 상태 외에도 최대 all-gather 파라미터 그룹, 활성화, 임시 버퍼, 단편화, 통신 overlap을 계산합니다. 확장 전에 단일 노드와 다중 노드의 최대 메모리·스텝 시간을 비교합니다.

재개 가능한 체크포인트에는 샤딩된 모델·옵티마이저, 스케줄러, scaler/FP8 상태, 전역 토큰, RNG와 샘플러/데이터 커서, 모델/데이터/토크나이저/코드/설정 해시가 들어갑니다. 배포한 DeepSpeed 버전과 런처로 복원을 시험합니다. 가중치만 저장한 결과는 정확한 재개가 아닙니다.

무작위 입력 513개에서 다음 토큰 512개를 예측합니다. 이 예제는 한 마이크로배치만 처리합니다. 그래디언트 누적 횟수가 1보다 크면 이 시점에 가중치가 갱신되지 않을 수 있습니다. 실제 데이터로 두 단계를 비교할 때는 샘플 ID와 시퀀스 길이, 학습률, 정밀도, 누적 횟수를 고정하세요. 토큰당 검증 손실과 그래디언트 노름, 처리량, 최대 메모리, 집합 통신 대기 시간을 함께 기록합니다. 손실이 유한하지 않거나 같은 데이터 위치에서 체크포인트를 재개했을 때 다음 업데이트가 재현되지 않으면 규모를 늘리기 전에 원인을 확인합니다.

### 엔지니어링 트레이드오프 (The Engineering Trade-off)
같은 시퀀스 길이와 배치에서 ZeRO-2와 ZeRO-3의 GPU 최대 메모리와 스텝 시간을 비교하세요. 가중치를 모으느라 GPU가 기다린 시간이 늘었다면, 추가 통신이 메모리 절약과 맞바뀐 것입니다.

## Summary

어떤 단계를 쓸지는 각 랭크가 평소에 맡는 상태와 연산 중에 잠시 모으는 상태를 따로 계산해 정합니다. [7.3절](/ko/chapter-7/model-and-pipeline-parallelism/)에서는 이 분할을 텐서 병렬 및 파이프라인 병렬과 조합합니다.

<summary>Quiz 1: 이상화한 전송 바이트가 같으면 실행 시간도 같나요?</summary>
*아닙니다. Reduce-Scatter와 All-Gather의 이상화한 총 바이트는 DDP All-Reduce와 같을 수 있지만, 시작 비용·버킷 크기·순서·메모리 복사와 연산 겹침은 달라질 수 있습니다.*
</details>

<details>
<summary>Quiz 2: ZeRO-3에서 랭크 하나가 가중치의 일부만 보관한다면 어떻게 한 층의 순전파를 계산할까요?</summary>
*필요한 가중치 조각을 all-gather로 모아 계산합니다. 이후 해제해 메모리를 확보할 수도 있고, 다시 가져오는 비용을 줄이려고 역전파 때까지 보관할 수도 있습니다.*
</details>

<details>
<summary>Quiz 3: ZeRO-Offload를 사용하여 10B 파라미터 모델을 학습시키고 있습니다. GPU 활용도(MFU)가 크게 떨어지고 GPU가 자주 유휴 상태(Idle)에 빠지는 것을 발견했습니다. 시스템의 가장 가능성 높은 병목 지점은 어디인가?</summary>
*PCIe 대역폭 또는 CPU 연산 속도입니다. ZeRO-Offload는 옵티마이저 스텝 연산을 CPU로 이동시킵니다. 만약 CPU가 Adam 업데이트를 계산하는 속도가 너무 느리거나, PCIe 버스가 업데이트된 가중치를 다음 순전파가 시작되기 전까지 GPU로 충분히 빠르게 전송하지 못한다면, GPU는 CPU의 작업이 끝날 때까지 기다려야 하므로 활용도가 급격히 떨어지게 됩니다.*
</details>

<details>
<summary>Quiz 4: 이 절의 16바이트 예산에서 옵티마이저 관련 상태는 무엇인가요?</summary>
*FP32 마스터 가중치 4바이트와 두 FP32 모멘트 8바이트를 합쳐 파라미터당 12바이트입니다. 이는 예시 구현의 회계이며 Adam 자체가 모든 환경에서 별도 FP32 마스터 복사본을 요구하는 것은 아닙니다.*
</details>
