# 14.1 From Lexical to Semantic Search

A support desk has two requests. One customer writes *flat tire*, while the repair manual says *patch punctured wheels*. Another sends only the activation code `XJ-992-B`. The repair search needs to bridge a vocabulary gap. The code search needs to preserve every character. In a retrieval-augmented generation (RAG) system, the passages that survive this first search determine which evidence the generator can cite.

## 1. The Limits of Keyword Search

### A. The Synonym Problem (Vocabulary Mismatch)

A lexical index maps terms to the documents that contain them. If the analyzer leaves *flat tire* and *punctured wheels* as four different terms, their BM25 overlap is zero. A synonym dictionary could bridge the gap. It needs to cover the vocabulary your readers actually use.

### B. Polysemy (Context Blindness)

A query for *bank* alone leaves a lexical retriever with both financial and riverbank documents. Adding *flood* can change a term-based ranking as well as a vector ranking. An ambiguous query can remain ambiguous in either representation.

### C. Cross-Lingual Limitations

A Korean support request can refer to an English manual with no shared words. Translation or a multilingual encoder supplies a bridge. A part number can already match across both languages, provided the analyzer preserves it as a searchable unit.

### D. The Solution: Vector Embeddings

A dense retriever learns to map a query and a passage to vectors. Karpukhin et al. trained separate query and passage encoders to give answer-bearing passages a higher dot product than competing passages [[3]](#ref-3). Whether a new pair of expressions lands close together is a question for an evaluation set.

### The Keyword Stronghold: Precision on Specifics

In the [product-code example](#lexical-product-code), the rare code earns a larger BM25 contribution than the shared word *activation*. For a term found in $f$ of $N$ titles, the exercise uses $\mathrm{IDF}(f)=\ln(1+(N-f+0.5)/(f+0.5))$ [[4]](#ref-4). BM25 uses $k_1=1.2$ for term-frequency saturation and $b=0.75$ for length normalization. Each distinct query term contributes once. All titles are three terms long and no title repeats a term, so the usual factor $(k_1+1)\,\mathrm{tf}/(\mathrm{tf}+k_1(1-b+bL/\overline L))$ equals 1 for each match. Here $L$ is title length, $\overline L$ is mean title length and $\mathrm{tf}$ is the term's frequency in that title.

A scores $\mathrm{IDF}(2)=0.693$ and B adds $\mathrm{IDF}(1)=1.204$ to reach **1.897** (rounded). Their topic vectors are identical, so both cosine scores equal 1. With the code alone, B still matches lexically. The dictionary has no entry for the code, so the query vector has zero length and cosine is undefined. A dash in the table marks that case. Query and title tokens are converted to lowercase, keep internal hyphens, and use no stemming or morphological analysis.

Follow the [*flat tire* example](#lexical-paraphrase) to see the other failure. No title contains either term, so all four BM25 scores are zero. The dictionary gives the query and title C, *Patch punctured wheels*, the same direction, for a cosine of 1. Type *tire activation* and C shares just one of the two query coordinates. Its cosine drops to $2/(\sqrt{2}\times 2)\approx0.707$.

**Reproduce the scores in Python.** The example uses the standard library and the four-title corpus statistics above.

```python
from math import hypot, isclose, log1p

# Four three-token titles. Each matched term occurs once, so its BM25
# contribution here is its inverse document frequency.
def idf(df):
    return log1p((4 - df + 0.5) / (df + 0.5))

def cosine(q, d):
    norm = hypot(*q) * hypot(*d)
    return sum(a * b for a, b in zip(q, d)) / norm if norm else None

general = idf(2)
specific = idf(2) + idf(1)
print(round(general, 3), round(specific, 3))  # 0.693 1.897
assert isclose(cosine([1, 1, 0], [2, 0, 0]), 2**-0.5)
assert cosine([0, 0, 0], [0, 1, 0]) is None
```

A held-out set for a support search should include paraphrases and exact codes with labeled answer-bearing passages. Count how often each retriever includes that passage within the same candidate budget. ## 3. Advanced Chunking Strategies

### A. Naive (Fixed-Size) Chunking

Suppose a manual puts *XJ-992-B* at the end of one paragraph and its reset procedure in the next. A fixed 256-token boundary can separate the identifier from the instructions. An overlap of 20 tokens helps only if it preserves enough of the connection. Inspect the actual returned span.

### B. Hierarchical Chunking

One option is to index section summaries, then search passages within a selected section. This saves work once the right section is selected. A missing detail in the summary can send the query to the wrong section before any passage is scored.

### C. Parent-Child (Small-to-Large) Chunking

Index a short passage that names the code, then expand its source ID to the surrounding section before generating an answer. Retain the matched span, source revision and access rules when expanding. Evaluate passage recall and the fraction of final contexts that contain the complete procedure. The second measure catches a correct hit followed by a truncated answer.

## 4. The Mathematics of Semantic Space (InfoNCE and Matryoshka)

### Contrastive Learning and InfoNCE Loss

For a batch of $N$ query–passage pairs, suppose passage $d_i$ is labeled relevant to query $q_i$. An in-batch contrastive loss compares it against all $d_j$ in the batch. With similarity function $s$ and positive temperature $\tau$, one common form is

$$
\mathcal L=-\frac1N\sum_{i=1}^N\log\frac{\exp(s(q_i,d_i)/\tau)}{\sum_{j=1}^N\exp(s(q_i,d_j)/\tau)}.
$$

The softmax normalizes the scores for one query across the batch. If another passage in the batch also answers that query, treating it as a negative sends the wrong training signal. Check labels and near duplicates when constructing the batch. Dense Passage Retrieval uses in-batch negatives and also studies harder negatives drawn from a lexical retriever [[3]](#ref-3).

### Matryoshka Representation Learning (MRL)

Matryoshka training puts an objective on several prefixes of a representation [[1]](#ref-1). Keeping 128 of 768 coordinates reduces raw coordinate storage sixfold at fixed precision. An arbitrary embedding can lose its most useful coordinates when truncated. For a model trained for nested dimensions, measure quality at each supported prefix and apply the required normalization after truncation.

## October Update: Embeddings Across Modalities

**As of 2026-11-25**, Google's October 6 release describes EmbeddingGemma 2 embeddings for text, images, audio and video, with supported dimensions down to 128 from 768 [[2]](#ref-2). For example, a support query can retrieve a repair video. To cite the result, retain the video revision and time span along with the vector. Changing the encoder, dimension, preprocessing or normalization requires a compatible index and a fresh evaluation on each modality you serve.
