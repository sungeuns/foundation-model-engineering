# 14.2 Vector Indexing & DB Solutions

After choosing an embedding, the next question is how to find useful neighbors within a latency and memory budget. Exact search is an important quality reference and can be practical with batching or a selective filter. Approximate nearest-neighbor (ANN) indexes reduce search work at the cost of a workload-dependent recall trade-off. Neither “sub-millisecond” latency nor negligible recall loss follows from choosing an index name.

## 1. Start with an Exact Reference

For $N$ vectors of dimension $d$, a flat distance scan performs $O(Nd)$ coordinate work. Real latency also depends on memory traffic, metric, batching, hardware and concurrency. A billion FP32 vectors with $d=768$ need $N d\times4=3.072$ TB for the vectors alone, before identifiers, replicas, metadata and temporary buffers.

Use exact top-k results to define ANN recall on a sampled, authorized corpus, and use human relevance labels to assess whether embedding neighbors are useful. High ANN recall only means agreement with the exact metric search; it does not validate the embedding, evidence freshness, or answer quality.

## 2. HNSW: Hierarchy and a Candidate Budget

HNSW builds nested proximity graphs, with all vectors in the bottom layer and progressively fewer in upper layers [[1]](#ref-1). Bottom-layer connectivity remains sparse, not a complete dense graph. Search uses sparse upper layers to approach a promising region, then explores a bounded candidate set near the bottom.

Distinguish construction parameters from query parameters. `M` influences connectivity and graph memory; `efConstruction` influences build work and graph quality; `efSearch` controls the query exploration budget. Raising a budget may improve recall while increasing distance evaluations and latency. Deletions, filters, data clustering, insertion order and dimension affect the curve. Empirical logarithmic scaling is not a worst-case guarantee for every dataset or configuration.

## 3. Quantization, IVF and ScaNN

Different index mechanisms can be combined; “graph” and “quantized” are not mutually exclusive categories.

| Mechanism | What it changes | Engineering cost to measure |
|---|---|---|
| Flat exact scan | Evaluates every eligible vector | Vector traffic, batching, candidate population |
| HNSW graph | Visits connected candidate neighborhoods | Graph links, construction, exploration, update behavior |
| IVF partitioning | Searches selected coarse clusters | Training, cluster imbalance, number of probes, missed clusters |
| Product quantization (PQ) | Stores codebook indices instead of full vectors | Codebooks, approximate distances, optional exact refinement |
| ScaNN-style search | Combines search stages with quantization tailored to scoring | Training, scoring/refinement budget, hardware and metric |

Guo et al.'s anisotropic quantization penalizes components of reconstruction error differently to better preserve high inner-product scores [[2]](#ref-2). This is more specific than saying that keeping a vector's direction always preserves ranking: norms matter in unnormalized maximum-inner-product search. Cosine similarity is equivalent to inner product only with appropriate normalization. Compare full systems at matched recall and throughput rather than declare one algorithm universally faster.

For a storage example, PQ with $M=96$ subspaces and 256 centroids uses 8 bits per subspace, hence 96 code bytes per vector. One million vectors require 96 MB for codes. With dimension 768 and FP32 codebooks, centroids add $96\times256\times8\times4=786{,}432$ bytes. IDs, coarse centroids, graph links, alignment, metadata, replicas, and optional full-vector refinement are additional. A code-size reduction is not the same as a total service-memory reduction.

## 4. Filters Are Part of Retrieval and Authorization

A relevant HR document must not reach a user who lacks permission. Keep tenant identity, ACL version and retention/deletion state attached to the source and every derived representation. A metadata field alone does not enforce authorization: the query service must verify and apply the policy before content, snippets, caches or logs become visible.

Post-filtering a fixed ANN candidate list can leave too few eligible results. Restricting traversal to eligible graph nodes can disconnect useful paths. Implementations may traverse ineligible nodes without returning their content, use filter-aware edges, choose a filtered exact scan, or adapt their search plan. Qdrant's discussion illustrates implementation-specific techniques; it is not evidence that all databases share one filtering algorithm [[4]](#ref-4).

Evaluate recall **within the eligible population**, result completeness, latency and information leakage across low/high-selectivity filters. Test negative permissions, stale ACL caches, tenant isolation, deletion, replicas, and restored snapshots. A correct top-k list with unauthorized evidence is still a failed retrieval system.

## 5. From an Index to a Service

**As of 2026-10-25**, the FAISS maintainers' selection guide distinguishes exact, graph, partitioned and compressed choices by constraints such as training, storage and search work [[3]](#ref-3). A library provides algorithms; a managed or self-hosted service must additionally provide durability, concurrent updates, filtering, backup/restore and operational visibility. Product names alone do not establish those guarantees.

Benchmark the intended corpus, query distribution, dimensions, metric, batch size, concurrent load, hardware, filters and update churn. Record index version, build seed/order, embeddings/tokenizer, distance settings and search parameters. Report recall–latency curves, p50/p95/p99 latency, build time, memory/storage with replicas, ingestion lag, deleted-record exposure and error rates. Include a filtered exact baseline where feasible.

Promote a new index using a shadow route and a versioned cutover. Require paired quality evidence, critical authorization/deletion gates and an owner with explicit abort thresholds. Keep the last-known-good route and rehearse restore and rollback with deletion tombstones preserved. Section 14.3 then combines retrieval signals and spends reranking computation on the resulting candidates.

## Quizzes

<details>
<summary>Quiz 1: Why retain an exact baseline for ANN?</summary>
*It isolates index approximation error from embedding relevance error. Compare eligible populations under the same metric and filters.*
</details>

<details>
<summary>Quiz 2: Why is HNSW not a complete dense graph at layer zero?</summary>
*It stores bounded proximity links for navigation. Full connectivity would destroy the intended graph storage and search trade-off.*
</details>

<details>
<summary>Quiz 3: Does a 32× reduction in PQ code bytes imply 32× less service memory?</summary>
*No. Codebooks, identifiers, graph/coarse index data, metadata, replicas, buffers and optional refinement vectors remain.*
</details>

<details>
<summary>Quiz 4: Why can filtering change ANN recall?</summary>
*Post-filtering can exhaust candidates, while constrained graph traversal can lose routes. Evaluate the implementation within the eligible population and enforce authorization separately.*
</details>

<details>
<summary>Quiz 5: What must a rollback preserve besides vectors?</summary>
*Versioned embeddings, metric and search settings, ACLs, provenance and deletion tombstones must remain consistent. Restoring a snapshot must not resurrect deleted or unauthorized evidence.*
</details>
