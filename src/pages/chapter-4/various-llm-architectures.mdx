# 4.5 Various LLM Architectures

You have room for the weights, but does another pass through the same layers need more memory? In the CPU experiment below, 24 decoder layers run 72 times. There is still one copy of each layer, yet each repeat leaves new keys and values for the next token to read.

This chapter follows three design decisions through an inference request. Which earlier tokens can a layer see? Which parameters does it touch? What stays in memory after the request advances by one token?

## Why Architectures Keep Diverging

Chapter 3 gave us the canonical Transformer. Real systems, however, run into recurring pressure points:

1. Long contexts make full attention expensive.
2. KV caches become costly during autoregressive serving.
3. Dense feed-forward layers scale poorly as models get larger.
4. Training objectives that work for next-token prediction are not always optimal for throughput or reasoning.

Most modern architectural changes can be understood as responses to one or more of these bottlenecks.

### 1. Hybrid and Linear Attention
Standard self-attention has quadratic cost in sequence length, so it becomes expensive when context grows. One increasingly common response is a **hybrid attention stack**.

Instead of using full attention in every layer, hybrid models mix expensive but expressive attention layers with cheaper mechanisms such as linear attention, local attention, or state-space style updates. The intuition is simple: not every layer needs to perform global token-to-token lookup with the same fidelity.

This is a recurring pattern in modern model design. Keep some layers that are excellent at exact retrieval and composition, then use cheaper layers elsewhere to carry longer-range state at lower cost.

Recent open-weight releases make this trend concrete. MiniMax-Text-01 scaled a hybrid stack where seven Lightning Attention layers are followed by one Softmax attention layer, combined with MoE, to support very long contexts [[4]](#ref-4). Kimi Linear then pushed the idea further with **Kimi Delta Attention (KDA)**, a refined gated-delta linear attention module, interleaved with global MLA layers in a 3:1 ratio; its model card reports up to 75% KV-cache reduction and up to 6x decoding throughput at 1M context [[5]](#ref-5). Qwen3.6-35B-A3B shows the same direction in a smaller open-weight package: 35B total parameters, 3B active, a repeated `3 x Gated DeltaNet + 1 x Gated Attention` layout, MoE after each attention block, multi-token prediction, and native 262K context extendable to about 1M tokens [[6]](#ref-6). Ling-2.6-flash, released as an open model in April 2026, is another recent example: it upgrades a GQA design into a 1:7 MLA + Lightning Linear hybrid with highly sparse MoE, targeting faster agent-style inference rather than simply longer chain-of-thought outputs [[7]](#ref-7).

The important update is not that softmax attention disappeared. It has not. The newer pattern is **selective full attention**: keep a small number of global attention layers as high-fidelity retrieval/composition checkpoints, and let linear-attention layers carry most of the long-context state. This makes hybrid linear attention look less like an exotic research branch and more like a practical production architecture for agentic and long-context workloads.

### 2. KV-Cache Compression and Memory-Aware Attention
For autoregressive models, serving cost is often dominated not just by compute, but by memory movement. Every generated token extends the KV cache, and that cache must be read repeatedly during inference.

DeepSeek-V3’s **Multi-head Latent Attention (MLA)** caches a shared content vector and a separate positional key per token. Each head reads that state through its own projections. [Count the bytes for a 4,096-token request and compare two ways to read the same cache](#mla-cache-example) [[1]](#ref-1).

### 3. Mixture of Experts in the Feed-Forward Stack
Another major lever is the feed-forward block. Dense FFNs scale cost with the full parameter count, while **Mixture of Experts (MoE)** activates only a subset of experts for each token.

MoE is attractive because it increases total model capacity without paying the full inference cost of a dense model of the same size. The trade-off is engineering complexity: routing, load balancing, expert parallelism, and communication overhead become first-class concerns. In other words, MoE often trades arithmetic cost for systems complexity.

### 4. Multi-Token Prediction (MTP)
Most language models are trained to predict exactly one next token. **Multi-token prediction (MTP)** changes the objective so that the model predicts several future positions at once.

This can improve training efficiency and create a cleaner path to faster inference schemes such as speculative decoding. Conceptually, it is a reminder that architecture is not only about layers and blocks. Training objectives also shape which serving optimizations become natural later.

### 5. Optical Context Compression
The previous examples change how the model processes tokens once they are already inside the Transformer. A newer line of work asks a stranger question: what if a long text context should not enter the model as a long 1D token sequence at all?

DeepSeek-OCR is an example of this idea. Despite the name, its most interesting contribution is not simply "better OCR." It investigates **contexts optical compression**: mapping text-heavy documents into a 2D visual representation, encoding that page image into a small number of vision tokens, and then using a language decoder to recover or reason over the content [[3]](#ref-3). A page full of text can sometimes be cheaper to pass through a vision encoder than to feed as thousands of text tokens.

The intuition is familiar if you have ever screenshotted a long paragraph. A screenshot preserves line breaks, tables, mathematical notation, and spatial layout in one compact object. DeepSeek-OCR turns that intuition into a model pipeline:

1. Render or receive the document as an image-like 2D signal.
2. Compress the page with a vision encoder, DeepEncoder, into a bounded number of vision tokens.
3. Decode the compressed representation with a DeepSeek3B-MoE-A570M language decoder.
4. Produce OCR text, markdown, layout-aware outputs, or document-grounded responses.

This does not mean the system has abandoned text. The output is still text, and the decoder is still a language model. The architectural shift is at the input boundary: text is treated as something that can be optically compressed before it becomes model context.

For practitioners, the key quantity is the compression ratio:

$$
r = \frac{N_{\text{text tokens}}}{N_{\text{vision tokens}}}
$$

If a document would normally consume 2,000 text tokens but can be represented by 200 vision tokens, then $r = 10$. The DeepSeek-OCR paper reports that when this ratio stays below about $10\times$, OCR precision remains around 97%; at roughly $20\times$, accuracy falls to about 60% [[3]](#ref-3). That trade-off is the whole story: optical compression can buy context length, but it is not a lossless replacement for text tokenization.

Technically, this moves some of the burden from sequence modeling into visual representation learning. The encoder must preserve fine-grained glyph identity, reading order, table structure, and layout geometry while producing far fewer tokens than a conventional OCR or document parsing pipeline. The decoder then has to turn those compressed visual tokens back into exact symbols or structured text. This is very different from ordinary image captioning: a one-character error in code, math, legal text, or a table cell may be unacceptable.

The deeper implication is that "context length" is no longer only an attention problem. Long-context systems can be attacked at several levels:

- make attention cheaper over long token sequences with hybrid linear attention;
- make the KV cache cheaper during generation;
- route computation sparsely with MoE;
- predict or verify multiple tokens at once;
- or compress the input representation before it becomes a token sequence.

Optical context compression belongs to the last category. It is promising for scanned documents, PDFs, tables, receipts, historical archives, and layout-rich corpora. It is riskier for workloads where exact byte-level fidelity matters, such as source code patches, formal proofs, contracts, and safety-critical numeric tables. A robust production system would often pair it with confidence scoring, selective fallback to text OCR, or verification against the original document image.

### GLM-5.2: sharing the indexer, not the attention result

GLM-5.2's most interesting long-context idea is **IndexShare**. Sparse attention normally needs an indexer to decide which historical positions deserve expensive attention. GLM-5.2 shares one learned sparse indexer across a group of four layers. The selected positions can still be processed by each layer's own attention projections; it is the retrieval *decision machinery* that is amortized. Z.ai reports 2.9× lower per-token FLOPs for this long-context path at 1M tokens [[8]](#ref-8).

The configuration reveals an intentionally staged stack: three dense layers establish early representations, then the remaining layers use fine-grained MoE with one always-on shared expert and eight selected routed experts. One MTP layer supplies a draft signal for speculative decoding. The launch report also describes IndexShare/KVShare, rejection sampling, and an end-to-end total-variation objective that raised average accepted speculative length from 4.56 to 5.47 tokens [[8]](#ref-8). That is roughly a 20% gain in accepted draft length—not automatically a 20% end-to-end latency reduction, because verification, memory traffic, batching, and scheduler overhead remain.

The post-training pipeline is equally instructive. Z.ai describes parallel on-policy distillation that merges more than ten expert policies in roughly two days, critic-based PPO for compacted long trajectories, token-level loss normalization for imbalanced trajectory lengths, and a two-stage anti-reward-hacking filter. When a suspicious tool call is blocked, the rollout receives a dummy result and continues. This creates training data for recovery behavior instead of simply deleting the episode [[8]](#ref-8). The broader lesson is that an “agent model” is increasingly a coupling of architecture, rollout compression, verifier design, and serving kernels.

### Kimi K3: three disclosed ideas, one important denominator

K3 combines Kimi Delta Attention (a recurrent/linear attention path), Attention Residuals (cross-layer attention-style residual mixing), and Stable LatentMoE. Its router selects 16 of 896 experts per token. That is about **1.8% of the expert pool**, not proof that only 1.8% of the model's total parameters are active: embeddings, attention, shared components, and expert sizes all affect the true active-parameter ratio. Moonshot reports 2.5× scaling efficiency over K2; the subsequently released technical artifacts make the architecture and systems claim inspectable, while the exact training-data mixture is still undisclosed [[11]](#ref-11) [[14]](#ref-14).

K3 also exposes a subtle product constraint: a reasoning session should preserve its thinking history. Switching modes mid-session can destabilize the trajectory. That is an architectural clue with operational consequences—conversation state is part of the inference contract, not merely UI decoration.

### Qwen3.8: artifact arrival changes the claim boundary

Qwen3.8 is valuable precisely because its release history teaches evidence discipline. At preview time, Alibaba had announced a 2.4T model and future open weights, so its internals had to remain **undisclosed** rather than inherit Qwen3.7 details [[13]](#ref-13). The later Qwen3.8-2.4T-A95B repository changed that boundary: weights and configuration now support claims about total and active parameters and the documented native/extended context distinction [[15]](#ref-15). They still do not disclose the exact corpus mixture or complete filtering and post-training recipes. A living technical comparison must change when the artifact changes—not when a future promise is first published.

### Autoregressive does not mean decoder-only

V4.1 Flash uses a causal encoder followed by a decoder. Its card explains that global decoder KV is projected from the encoder's final states, rather than rebuilt independently from each decoder layer [[16]](#ref-16). ### Conditional memory is a different sparsity axis

Engram studies token-conditioned lookup as a complement to MoE computation [[21]](#ref-21). A deterministic address can enable prefetching, but a lookup is not free: storage capacity, host bandwidth, transfer overlap, and miss behavior matter. It is also not the external, refreshable document index of RAG. For a deployment comparison, separate neural compute, lookup storage, KV state, and communication; one active-parameter ratio cannot describe all four.

## A Better Way to Compare Modern Architectures

Rather than memorizing product names, it is more useful to compare architectures by the bottleneck they target.

| Design Pressure | Common Architectural Response | What You Gain | What You Give Up |
| :--- | :--- | :--- | :--- |
| Long contexts | Hybrid linear attention, local attention, sparse attention | Lower asymptotic attention cost | Less uniform behavior across layers and more custom kernels |
| KV-cache growth | GQA, MQA, MLA, sliding windows | Lower memory traffic during serving | More specialized implementation details |
| Massive parameter counts | MoE layers | Higher capacity per unit inference compute | Routing and load-balancing complexity |
| More computation without duplicating a layer block | Shared-depth loops | More transformations using the same block weights | Repeated computation, state management, and stability checks |
| Throughput during decoding | MTP, speculative-friendly objectives | Faster generation paths | More training and serving coordination |
| Input context token growth | Optical 2D mapping, vision-token compression | Large documents fit into fewer context tokens | OCR errors, layout dependence, and verification burden |
| Long-context stability | QK-Norm, RoPE variants, windowing | Better optimization at scale | Extra design tuning and validation |

This lens also explains why there is no single “best” modern architecture. A model optimized for short, frequent chat requests may choose very different internals from one optimized for long-context document work or large-scale coding assistance.

## What does a DeepSeek-V3 attention layer keep for the next token?

Suppose one request already has 4,096 tokens in its cache. For each token, DeepSeek-V3 keeps a 512-coordinate vector that encodes the content keys and values, plus a 64-coordinate key carrying rotary position information. All 128 heads in the layer share these two stored vectors. At two bytes per coordinate, the persistent attention payload for this **one layer and one request** is $4096 \times (512+64) \times 2 = 4{,}718{,}592$ bytes, or **4.5 MiB**. Counting only the compressed content misses half a MiB. The dimensions and the two tensors to cache come from sections 2.1.1 and 4.2 of the DeepSeek-V3 report [[1]](#ref-1).

How can the heads still return different answers? Let $C$ hold one latent row per cached position, $U_K$ and $U_V$ be one head’s key and value projections, and $q$ its content query. The head can compute the same content scores as $(CU_K)q$ by first projecting the query and then reading the latents, $C(U_Kq)$. Add the positional scores before scaling and softmax. Once softmax gives weights $a$, the head can project the weighted latent $(a^T C)U_V$ to obtain the same output as $a^T(CU_V)$.

> **Scope of the CPU example.** One unpadded sequence grows one position at a time. The FP32 tensors stand in for the outputs of the trained projections and RoPE. The code compares the two evaluation orders for each head. It omits weight loading, the final output projection, allocator overhead and optimized kernels. Appending with `torch.cat` copies tensors.

```python
import math
import torch

rng = torch.Generator().manual_seed(7)

def sample(*shape):
    return torch.randn(*shape, generator=rng, dtype=torch.float32, device="cpu")

# Two heads, each projecting a 3-coordinate latent to 4 content coordinates.
key_up = sample(2, 3, 4)
value_up = sample(2, 3, 4)
latent = sample(0, 3)
position_keys = sample(0, 2)
scale = math.sqrt(4 + 2)

for _ in range(4):
    latent = torch.cat((latent, sample(1, 3)))
    position_keys = torch.cat((position_keys, sample(1, 2)))
    for wk, wv in zip(key_up, value_up):
        query = sample(4)
        position_scores = position_keys @ sample(2)
        keys, values = latent @ wk, latent @ wv
        weights = (((keys @ query) + position_scores) / scale).softmax(dim=0)
        reference = weights @ values

        latent_query = wk @ query
        weights = ((latent @ latent_query + position_scores) / scale).softmax(dim=0)
        result = (weights @ latent) @ wv
        torch.testing.assert_close(result, reference, atol=1e-5, rtol=1e-5)

print(tuple(latent.shape), tuple(position_keys.shape), latent.nbytes + position_keys.nbytes)
```

The script prints `(4, 3) (4, 2) 80`. Four positions each hold three content coordinates and two positional coordinates, all in FP32. The explicit keys and values in the reference calculation are temporary. Each of the eight head outputs (two heads after each of four appends) must match before the shapes are printed.

## GLM-5.4: Reusing Layers Separates Depth from Capacity

**As of 2026-11-24.** Z.ai's November 23 announcement describes a **750B-scale** Loop Transformer adapted from a pretrained GLM-5 base, with **28 shared layers executed twice** [[37]](#ref-37). Exact total/active parameter counts, the complete training mixture and a future weight license remain undisclosed.

Think of applying the same editing procedure to a revised draft. The procedure is reused, but its second application sees a changed representation and still takes work. A simple execution count makes this distinction concrete. Let $L$ be the original number of layers, $k$ the size of the shared block, and $r$ its iteration count. If all other layers execute once, the number of layer executions per forward pass is

$$
D = (L-k) + rk = L + (r-1)k.
$$

Here $D$ counts executions, not separately stored layer weights. With the disclosed $k=28$ and $r=2$, the count is $L+28$; this does not establish the model's full layer count. It also does not give a FLOP multiplier: attention, expert routing, gates, cache reads and kernel execution have different costs. Reusing a matrix saves duplication of that matrix, not the arithmetic needed to apply it again.

The announcement identifies three supporting mechanisms [[37]](#ref-37):

| Mechanism | Disclosed operation |
|---|---|
| Per-iteration, per-token gates | Control residual updates to stabilize repeated computation |
| Shared global KV plus a local window | The second pass reuses first-pass sparse KV and retains its own sliding-window KV |
| Sparse index reuse | The second pass reuses first-pass retrieval indices |

The reported controlled ablation uses a **30B model**, with about **10% more training compute**, after **200K-context SFT** with thinking enabled. It is not a flagship benchmark result. Adaptive iteration counts remain future work [[37]](#ref-37). For a private evaluation, hold tool access, effort, context and stopping rules fixed; measure task success, total generated tokens, tail latency and budget exhaustion. Fewer output tokens need not mean less internal computation.

**Access boundary:** Coding Plan, ZCode and Z.ai Chat are live; the standard pay-as-you-go API and weights remain planned [[37]](#ref-37). Coding Plan integration documents **1M context**, image input and low/high/max effort; disabling thinking maps to low [[38]](#ref-38). This is a hosted serving contract, not a downloadable configuration. [Section 17.6](/chapter-17/commercial-model-benchmarks) tracks release and evaluation evidence separately.

### Why can one token position contribute two cache entries?

Z.ai’s architecture guide says the second pass can attend to a first-pass representation and its updated local representation at the same position (as of 2026-11-25) [[43]](#ref-43). Suppose the first-pass index picks positions **1, 5 and 7**, and the second pass reads a local window covering **6 and 7**. These positions are an example chosen for the calculation.

| Source of keys and values | Positions read by this query |
| --- | --- |
| Reused first-pass entries | 1, 5, 7 |
| Local second-pass entries | 6, 7 |

The query sees **five entries at four positions**. If a cache keeps only the latest entry for position 7, the second pass loses access to the earlier representation. This count describes one query’s reads. To budget resident memory you would also need the sizes and lifetimes of the underlying buffers. Compare it with the [dense SmolLM2 cache measurement](/chapter-12/kv-cache-management/#kv-batch-padding), where every layer stores one key and one value for each allocated batch position.

### How can 24 decoder layers execute 72 times?

Thinking Machines Lab released the weights of a separate variable-depth research model on November 20. Its checkpoint, `TML-d24-varloop-research`, lets you choose how often the middle of the decoder runs. As of 2026-11-25, the public configuration specifies 24 text layers and a default of three passes. You can inspect the execution order with Python’s standard library by downloading just the configuration. [[44]](#ref-44) [[45]](#ref-45)

```python
import json
from urllib.request import urlopen

repo = "thinkingmachines/TML-d24-varloop-research"

url = f"https://huggingface.co/{repo}/resolve/{revision}/config.json"
with urlopen(url, timeout=15) as response:
    config = json.load(response)["text_config"]

layers = list(range(config["num_hidden_layers"]))
loop = config["loop_config"]
start, end = loop["core_start"], loop["core_end"]
for passes in (1, loop["num_passes"], 5):
    schedule = layers[:start] + layers[start:end] * passes + layers[end:]
    print(passes, len(schedule), len(set(schedule)))
```

The columns are passes, layer executions per token, and distinct decoder layers. The script prints `1 24 24`, `3 48 24`, and `5 72 24`. Layers 0–5 run once, layers 6–17 repeat, and layers 18–23 run once. At five passes the middle block does 60 executions. Reusing its weights still costs memory during decoding. The Transformers implementation gives each extra pass its own cache entries for those 12 layers. [[46]](#ref-46)

What would a quality comparison at one and five passes tell you? It holds the checkpoint fixed, but training favored three passes. The lab sampled one through five passes in a 1:2:6:2:1 ratio during later midtraining and used three during post-training. A test on the same prompts shows what changing depth buys **on this checkpoint**. A claim about the best depth to train from scratch needs a separate experiment. [[44]](#ref-44)

### One more token, less KV backing storage

Run the 24-layer schedule in the `Inkling2LoopTextModel` implementation with small, randomly initialized weights. The 232,704 parameters fit on a CPU. Twenty layers use a four-token attention window and four use full attention. Give the model six tokens, measure its keys and values, then decode a seventh. The code runs the seven-token sequence from scratch as a check on the cached result. [[46]](#ref-46)

| Passes | Layer calls at prefill | KV payload after six tokens | KV backing storage after six | KV backing storage after seven |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 24 | 10.5 KiB | 18 KiB | 13.5 KiB |
| 3 | 48 | 21 KiB | 36 KiB | 27 KiB |
| 5 | 72 | 31.5 KiB | 54 KiB | 40.5 KiB |

Why does storage fall when the sequence grows? Look at one sliding layer. After prefill it keeps the last three keys for the next query. Their 192-byte tensor is a view into a 384-byte allocation holding all six keys. Decoding appends the seventh key to those three. The next three-key view occupies the same 192 logical bytes, now backed by a 256-byte allocation. The four full-attention layers grow with the sequence, but here the savings across the sliding layers outweigh that growth. [[47]](#ref-47)

You can see the difference with a single key tensor.

```python
import torch

kept = torch.zeros(1, 2, 6, 8, dtype=torch.float32)[:, :, -3:, :]
print(kept.nbytes, kept.untyped_storage().nbytes())       # 192 384
next_key = torch.ones(1, 2, 1, 8, dtype=kept.dtype)
kept = torch.cat([kept, next_key], dim=2)[:, :, -3:, :]
print(kept.nbytes, kept.untyped_storage().nbytes())       # 192 256
```

## GPT-6.2: Documented Interfaces and Undisclosed Internals

**As of 2026-11-25.** OpenAI released **GPT-6.2 Astra** and **GPT-6.2 Sol** on November 17 through its API, ChatGPT Work and Codex. The weights remain undisclosed. [[42]](#ref-42) Both models accept text or images and return text. The API supports Responses and Chat Completions, with tool calling available through Responses. These interfaces tell us little about the attention layers, expert routing, parameter counts or training mixture. [[39]](#ref-39) [[40]](#ref-40) [[41]](#ref-41)

Both model pages distinguish a **1,050,000-token context window**, **922,000 maximum input tokens** and **128,000 maximum output tokens**. Both reject reasoning effort `none` [[39]](#ref-39) [[40]](#ref-40). These are useful integration constraints, but they cannot identify an architecture from outside the service. Similarly, subagent delegation is a documented Responses capability, not evidence for a particular arrangement of experts inside the model.

For an agent comparison, record whether a result used a single model call or orchestration, then pin the model ID, reasoning effort, tools, scaffold, context management, retries and grader. A system result cannot isolate a backbone improvement unless those factors are controlled. The practical comparison with GLM-5.4 is therefore about evidence: use the architectural mechanisms a provider actually discloses, and evaluate the complete deployed system where internals remain undisclosed.

## Quizzes

<details>
<summary>Quiz 1: Why would a model designer choose a hybrid attention stack instead of using full self-attention in every layer?</summary>
*Because full self-attention gives strong token-to-token interaction but becomes expensive at long sequence lengths. A hybrid stack keeps some layers that are good at exact global retrieval while replacing other layers with cheaper mechanisms such as local, linear, or state-space style updates. The goal is to preserve enough expressiveness while reducing cost.*
</details>

<details>
<summary>Quiz 2: At two bytes per coordinate, why does a 4,096-token request need more than 4 MiB of MLA cache in one DeepSeek-V3 layer?</summary>
*The 512 content coordinates account for 4 MiB. The shared 64-coordinate positional key adds 0.5 MiB for the same positions. The resulting 4.5 MiB is the persistent tensor payload under the assumed precision.*
</details>

<details>
<summary>Quiz 3: Why do long-context models often introduce stabilizers such as QK-Norm or attention windowing?</summary>
*As sequence length grows, attention scores and memory use can become harder to control. Stabilizers such as QK-Norm help keep attention values numerically well-behaved during training, while windowing reduces how much context each layer must process at once. Together they make long-context optimization more practical.*
</details>

<details>
<summary>Quiz 4: Why is optical context compression not equivalent to simply increasing a model's text context window?</summary>
*Increasing the text context window preserves the input as discrete text tokens and asks attention and KV-cache systems to handle more positions. Optical compression changes the representation before the model sees it: text and layout are encoded as vision tokens. This can reduce token count, but it introduces a lossy reconstruction problem, layout sensitivity, and the need to verify exact symbols when precision matters.*
</details>

<details>
<summary>Quiz 5: A block of 28 layers runs twice with shared weights. Does that double parameter storage or make the extra computation free?</summary>
*Neither follows. The block's main weights can be stored once, while its transformations execute twice; additional gates and state also require accounting. The execution count grows by 28 under the stated assumptions, but full FLOPs, memory and latency require the actual implementation.*
</details>

<details>
<summary>Quiz 6: Can a 30B loop ablation or a hosted agent score establish which flagship backbone is better?</summary>
*The ablation supports a conclusion about its tested model scale, training compute and evaluation setup. A hosted agent score measures the model together with effort, tools and orchestration. Neither supplies an uncontrolled model-to-model comparison or reveals undisclosed internals; use matched system evaluations and keep the evidence boundaries explicit.*
</details>
